# Day 17 가이드 — WAS → Kafka → FastAPI 전 구간 E2E 와 202 Accepted

> 상태: 완료(2026-10-12). ①~③ 실행해 확인했고 선택 항목 ④~⑥ 은 아직 하지 않았다. 실행하면 [DAY17_RESULT.md](DAY17_RESULT.md) 에 결과를 적는다.
> 포트: **8080 = Spring WAS**, **8000 = FastAPI**, 9092 = Kafka, 8090 = kafka-ui.


## 1. 오늘 목표

Spring(8080) → Kafka → FastAPI(8000) → 에이전트까지 이어진 전체 흐름을 **스크립트 한 번으로** 확인한다. 지금까지는 Postman 과 curl 로 한 건씩 손으로 보냈고, 요청이 끝까지 처리됐는지는 사람이 로그를 보고 판단했다. 이를 반복 가능한 검사로 바꾸는 것이 Day 17 이다. 부하 시험(Day 25~)에서도 같은 방식으로 요청을 보내고 완료를 센다.

```
[스크립트] -POST-> [Spring :8080] -202-> [스크립트]   (접수. 에이전트를 기다리지 않는다)
                        |
                        v
                [Kafka agent.requests]
                        |
                        v
        [FastAPI :8000 워커] -> run_agent() -> commit
                        |
[스크립트] <-GET /health------------------- (received, committed, current_request_id)
[스크립트] <-GET /api/v1/agent/results/{id} -- (status, answer)   ← Day 17 에서 추가한 임시 조회
```

| 위 전체를 **스크립트로 자동 확인**               | 오늘 (이 문서의 실행 부분)                                             |
| 여러 건을 연속으로 보냈을 때 모두 처리되는지     | 오늘                                                                   |
| requestId 로 답을 조회                           | 오늘 (메모리에 임시로 보관. 제대로 된 저장은 4주차 Redis)               |
| 202 응답 시간과 처리 완료까지 걸린 시간의 분리   | 오늘 (응답은 수십 ms, 처리는 요청당 수 초 단위로 기대. 확인 전 예상)   |


## 3. 결정: 메모리에 임시로 보관하고 FastAPI(8000)에서 조회한다

접수는 비동기이므로 사용자는 답을 받으려면 따로 조회해야 한다. 지금까지는 답이 FastAPI(8000)의 로그에만 남았다. 저장소는 4주차에 Redis 로 제대로 만들지만, 그 전에 WAS → Kafka → FastAPI 를 끝까지 확인할 수 있어야 해서 **프로세스 메모리에 임시로** 보관하고 조회 API 를 둔다. 4주차에 같은 인터페이스를 Redis 로 바꾼다.

| 결정                         | 이유                                                                                                       |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 조회 API 는 FastAPI(8000)에  | 답을 만드는 곳이 FastAPI 라서 저장소도 거기 있다. Spring(8080)이 중계하는 구조는 저장소가 공유되는 4주차에 |
| 상태는 3가지                 | `PROCESSING`(워커가 받아 에이전트 호출 중), `DONE`(답 있음), `FAILED`(실패, 타임아웃 포함)                  |
| 없으면 404                   | 없는 id, 아직 워커가 안 받음, 서버 재시작으로 지워짐을 구분하지 못한다                                     |
| 최대 1000건, 오래된 것부터 삭제 | 메모리가 무한히 늘지 않게 한다. `RESULT_STORE_MAX` 로 바꿀 수 있다                                      |

임시 구현이라 알고 쓰는 한계가 있다.

| 한계                         | 내용                                                                                                     |
| ---------------------------- | -------------------------------------------------------------------------------------------------------- |
| 재시작하면 사라진다          | 서버를 끄면 저장된 답이 모두 지워진다. 재시작 후 Kafka 에서 다시 받은 요청은 `PROCESSING` 부터 다시 시작한다 |
| 워커가 둘 이상이면 못 본다   | Day 18 의 멀티 컨슈머, 또는 uvicorn 프로세스가 여러 개면 서로의 결과를 보지 못한다                       |
| 답 전체가 메모리에 올라간다  | 건당 크기가 작아서 1000건이면 문제가 없지만 측정하지는 않았다                                            |

완료 판정은 두 가지를 같이 쓴다. `/health` 의 건수로 "N건이 모두 처리됐는가"를 보고, 결과 조회로 "각 요청의 상태와 답"을 읽는다.

| `/health` 필드       | 완료 판정에서의 쓰임                                                                |
| -------------------- | ----------------------------------------------------------------------------------- |
| `received`           | 처리에 성공한 건수                                                                  |
| `failed`, `skipped`  | 실패한 건수, 해석하지 못해 건너뛴 건수. 성공과 합쳐서 "처리가 끝난 건수"로 센다     |
| `committed`          | `manual` 모드에서 commit 한 건수. 보낸 건수만큼 늘어야 한다                         |
| `current_request_id` | 처리 중인 요청의 id. 모두 끝나면 `null`                                             |

## 5. 스크립트

`scripts/day17_e2e.sh` (bash, curl 만 사용. jq 불필요).

| 단계 | 하는 일                                                                                                          |
| ---- | ---------------------------------------------------------------------------------------------------------------- |
| 1    | FastAPI(8000)의 `/health` 로 시작 시점의 `received`, `failed`, `skipped`, `committed` 를 읽는다                   |
| 2    | Spring(8080)에 요청 N건을 순서대로 보낸다. 응답이 202 이고 `requestId` 가 있는지, 응답 시간(초)을 출력한다        |
| 3    | `/health` 를 1초마다 읽어, 시작 대비 처리된 건수가 N 이 되고 `current_request_id` 가 `null` 이 될 때까지 기다린다 |
| 4    | 요청마다 `GET /api/v1/agent/results/{requestId}` 로 상태(`DONE`, `FAILED`)와 답(앞 60자)을 읽는다                |
| 5    | PASS/FAIL 과 처리 완료까지 걸린 시간을 출력한다. 종료 코드는 PASS 0, FAIL 1                                      |

| 인자/환경변수       | 기본값           | 의미                                                  |
| ------------------- | ---------------- | ----------------------------------------------------- |
| 첫 번째 인자        | 3                | 보낼 요청 건수                                        |
| `SPRING`            | `localhost:8080` | Spring WAS 주소                                       |
| `FASTAPI`           | `localhost:8000` | FastAPI 주소                                          |
| `PROVIDER`          | `gemini`         | 요청의 provider                                       |
| `E2E_TIMEOUT_SEC`   | 180              | 처리 완료를 기다리는 최대 시간(초)                    |

FAIL 이 되는 경우: FastAPI 에 연결할 수 없음, 결과 조회가 200 이 아니거나 `DONE`/`FAILED` 가 아님, `/health` 를 해석하지 못함, 202 가 아니거나 requestId 가 없음, 제한 시간 안에 처리가 끝나지 않음.


## 6. 준비

1. Kafka, Qdrant 컨테이너를 켠다(Day 16 과 같다).
2. Spring(8080)을 켠다. Kafka 가 먼저 켜져 있어야 한다(Day 14 에서 확인한 순서).
3. FastAPI(8000)를 `source run.sh` 로 켠다. 이전 실험의 환경변수가 남아 있으면 지운다.
   ```bash
   unset KAFKA_HANDLER KAFKA_COMMIT_MODE AGENT_DEBUG_DELAY_SEC
   ```
4. `curl -s localhost:8000/health` 에서 `commit_mode: manual`, `current_request_id: null` 인지 본다.
5. 다른 요청이 들어오지 않게 Postman 등은 쓰지 않는다. 스크립트는 `/health` 의 증가량으로 판정하므로 다른 요청이 섞이면 틀어진다.


## 7. 실행과 확인

### ① 1건

```bash
bash scripts/day17_e2e.sh 1
```

기대(확인 전 예상): `[1] 202 0.0xs requestId=...`, 이어서 수 초 동안 `current=<requestId>` 가 보이다가 `processed=1/1 committed=1 current=null`, 단계 4 에 `[1] DONE <ms>ms answer=...`, 마지막에 `RESULT: PASS`. FastAPI(8000) 로그에는 같은 requestId 로 `[agent] 시작` → `완료` 가 찍힌다.

### ② 3건 연속 (기본)

```bash
bash scripts/day17_e2e.sh
```

기대(확인 전 예상): 세 요청이 모두 즉시 202 로 접수된다. 처리는 한 건씩 순서대로 진행되므로(순차 처리, Day 18 에서 병렬 실험) `current` 가 requestId 를 차례로 바꾸고, 전체 완료까지는 요청당 처리 시간(Day 16 에서 7.6초 한 번 잰 값)의 3배쯤 걸린다. 스크립트가 출력한 requestId 순서와 FastAPI 로그의 `[agent] 시작` 순서가 같은지 본다.

### ③ 202 응답 시간과 처리 시간 비교

①, ② 출력에서 다음 값을 적어 둔다.

| 값                        | 어디서                                        |
| ------------------------- | --------------------------------------------- |
| 202 응답 시간             | 단계 2 의 `202 0.0xs`                         |
| 처리 완료까지 걸린 시간   | 단계 5 의 `처리 완료: N초`                    |
| 에이전트 처리 시간        | 단계 4 의 `DONE ...ms` (서버가 잰 값)         |

이 차이가 비동기로 바꾼 이유이고, README 실험 보고서(sync 와 async 비교)의 첫 근거가 된다. 한 번 잰 값이므로 부하 시험(Day 25~)에서 다시 잰다.

### ④ (선택) 실패 요청이 섞이면

```bash
PROVIDER=invalid bash scripts/day17_e2e.sh 1
```

기대(확인 전 예상): 202 는 정상이고(Spring 은 provider 를 검증하지 않는다, Day 16), 처리 후 `failed` 가 1 늘고, 단계 4 에 `[1] FAILED error=...` 가 보이며 `실패 1건` 이 출력되고 PASS 이다. 실패가 PASS 로 나오는 것은 의도다. 이 스크립트는 "끝까지 처리했는가"를 보고 "답이 성공인가"는 보지 않는다.

### ⑤ (선택) 서버를 끈 상태

FastAPI(8000)를 끄고 실행하면 첫 단계에서 `FAIL: FastAPI(...)에 연결할 수 없다` 로 끝나야 한다. Spring(8080)을 끄면 단계 2 에서 FAIL 이어야 한다.

### ⑥ (선택) 조회 API 를 직접 호출

스크립트 없이 curl 로 확인한다. ① 이후에 출력된 requestId 를 쓴다.

```bash
# 8000 = FastAPI 의 결과 조회

# 저장된 requestId 로 조회: 상태(DONE 등)와 답을 JSON 으로 받는다
curl -s localhost:8000/api/v1/agent/results/<requestId>

# 저장된 적 없는 id 로 조회해서 404 가 나오는지 확인한다
#   -s              진행 표시 없이 조용히 호출
#   -o /dev/null    응답 본문은 버린다
#   -w "%{http_code}\n"   대신 HTTP 상태 코드만 출력한다 (기대: 404 한 줄)
#   없는-id          아무 문자열이나 된다. 일부러 존재하지 않는 값을 넣은 것이다
# 본문까지 보려면 -o 와 -w 를 빼고 호출한다 (기대: {"detail":"결과가 없다. ..."})
curl -s -o /dev/null -w "%{http_code}\n" localhost:8000/api/v1/agent/results/없는-id
```

기대(확인 전 예상): 첫 번째는 `status DONE`, `answer`, `elapsedMs`. 두 번째는 `404`. 처리 중인 상태(`PROCESSING`)는 `export AGENT_DEBUG_DELAY_SEC=30` 으로 서버를 켜고 요청을 보낸 직후 조회하면 볼 수 있다(끝나면 `unset AGENT_DEBUG_DELAY_SEC`). 서버를 껐다 켜면 같은 id 가 404 가 되는 것도 확인할 수 있다(메모리 임시 저장).


## 8. 작성 중 확인한 것과 확인하지 않은 것

| 구분          | 내용                                                                                                                                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 확인함        | `result_store`, `agent_handler`, `routers/results.py` 를 작성 환경에서 가짜 `run_agent` 로 시험: 성공은 `DONE` 과 답, 실패는 `FAILED` 와 사유(워커의 `failed` 가 오르는 것은 그대로), 처리 중에는 `PROCESSING`, 타임아웃은 `FAILED`, 모르는 id 는 404, 같은 id 를 다시 받으면 `PROCESSING` 으로 덮어씀, 1000건 한도에서 오래된 것부터 삭제. 스크립트는 문법 검사(`bash -n`)와 작성 환경에서 가짜 서버(202 와 `/health` 를 흉내 내는 파이썬 서버)를 띄워, 3건 처리 후 PASS, 제한 시간 초과 시 FAIL, 서버가 없을 때 FAIL, 응답 해석 실패 시 FAIL 로 끝나는 것 |
| 확인하지 않음 | 실제 에이전트(Qdrant, Gemini)가 낸 답이 저장되고 조회되는 것, 실제 `main.py` 기동에서 라우터가 등록되는 것(작성 환경에는 에이전트 라이브러리가 없어 `main.py` 를 import 하지 못했다). 실제 Spring(8080), Kafka, FastAPI(8000)로 스크립트를 돌리는 것. 가짜 서버는 내가 만든 것이라 실제 응답 형식과 다를 수 있다(실제 `/health` 는 공백 없는 JSON, 가짜는 공백 있는 JSON 으로 둘 다 읽히게 했다) |
| 확인하지 않음 | macOS 기본 bash(3.2)에서의 동작. 배열과 `$(( ))` 만 써서 되어야 하지만 직접 돌리지 않았다                                                                                                         |
