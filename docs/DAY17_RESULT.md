# Day 17 결과 — WAS → Kafka → FastAPI 전 구간 E2E 와 임시 결과 조회

> 구현과 실행 방법은 [DAY17_GUIDE.md](DAY17_GUIDE.md). 이 문서는 실행 결과와 해석을 담는다.
> 상태: 핵심(1건, 3건 E2E, 조회 API)은 실행해 확인함(2026-10-12). 선택 항목은 아직 하지 않았고 6번에 적었다.
> 포트: **8080 = Spring WAS**, **8000 = FastAPI**.

**전체 목적:** Spring(8080) → Kafka → FastAPI(8000) → 에이전트까지 이어진 흐름을 스크립트(`scripts/day17_e2e.sh`)로 한 번에 확인하고, 처리 결과를 `requestId` 로 조회하는 임시 API(메모리 저장)가 동작하는지 본다. 응답(202)과 처리 완료가 얼마나 떨어져 있는지도 잰다. 부하 시험(Day 25~)과 README 실험 보고서의 첫 근거가 된다.

## 3. 확인된 결과

### 3-1. 1건 E2E

**목적:** 요청 1건이 Spring(8080)의 202 응답부터 FastAPI(8000)의 에이전트 처리, 조회까지 이어지는지 확인한다.

| 확인한 것                     | 값                                                                                                  |
| ----------------------------- | --------------------------------------------------------------------------------------------------- |
| 시작 전 `/health`             | `received 0`, `failed 0`, `skipped 0`, `committed 0`, `commit_mode manual`                          |
| Spring(8080)의 응답           | `202`, 0.047초, `requestId=d6139305-8056-452b-ac07-b435ba7ef37d`                                    |
| 처리 중 `/health`             | 29초 동안 `current_request_id` 에 위 requestId 가 보였고, 끝나자 `processed 1/1 committed 1 current null` |
| 결과 조회                     | `DONE`, `elapsedMs 28702`, 답: 단순 변심으로 인한 환불 시 왕복 배송비는 고객님께서 부담하셔야 합니다.  |
| 스크립트 판정                 | `RESULT: PASS`, 처리 완료까지 29초                                                                  |

접수는 47ms 에 끝났지만 에이전트 처리는 약 28.7초가 걸렸다. 요청 스레드가 에이전트를 기다리지 않는다는 것이 이 차이로 보인다.


### 3-2. 3건 연속 E2E

**목적:** 여러 건을 연달아 보냈을 때 모두 접수되고, 보낸 순서대로 처리되며, 조회 API 에서 각각의 답을 읽을 수 있는지 확인한다.

질문은 스크립트의 기본 질문 3개다.

| 순번 | 질문                                    | 202 응답 | requestId       | 처리 시간(`elapsedMs`) | 조회 결과 |
| ---- | --------------------------------------- | -------- | --------------- | ---------------------- | --------- |
| 1    | 단순 변심으로 환불하면 배송비는 누가 내요? | 0.044초  | `1e07d4ba-...`  | 24824 ms               | `DONE`    |
| 2    | 환불은 며칠 안에 신청해야 하나요?        | 0.012초  | `fb0834f2-...`  | 27547 ms               | `DONE`    |
| 3    | 교환 시 배송비는 누가 부담하나요?        | 0.010초  | `7aef61b4-...`  | 22193 ms               | `DONE`    |

시작 전 `/health` 는 `received 1`, `committed 1` (직전 1건 실행의 값)이었고, 스크립트는 이 값에서의 증가량으로 판정해 `processed 3/3 committed 3` 에서 끝났다. 처리 완료까지 75초, 실패와 건너뜀은 0건이다.

**처리 순서:** `/health` 의 `current_request_id` 가 1 → 2 → 3 순서로 바뀌었다. 바뀐 시점은 25초, 53초 부근이다.

| 시점(스크립트 기준) | `processed` | `current_request_id` |
| ------------------- | ----------- | -------------------- |
| 0~24초              | 0/3         | `1e07d4ba-...` (1번) |
| 25~52초             | 1/3         | `fb0834f2-...` (2번) |
| 53~74초             | 2/3         | `7aef61b4-...` (3번) |
| 75초                | 3/3         | `null`               |

세 요청의 처리 시간 합은 24824 + 27547 + 22193 = 74564 ms 로 전체 75초와 거의 같다. 한 건씩 차례로 처리되고 있다는 뜻이다(Day 16 에서 순차 처리로 설계한 대로다). 3번은 접수된 뒤 약 53초를 기다렸다가 처리가 시작됐다.

**조회 API:** 세 requestId 모두 `curl` 로 직접 조회해 `status DONE`, `error null`, 위 `elapsedMs`, 질문에 맞는 답이 나왔다(세 질문의 답이 서로 다르다). 응답 JSON 에서 한글은 깨지지 않았다.

| 질문 | 조회로 읽은 답                                                                                       |
| ---- | ---------------------------------------------------------------------------------------------------- |
| 1    | 단순 변심으로 인한 환불 시 왕복 배송비는 고객님께서 부담하셔야 합니다. 추가 문의가 있으시면 고객센터로 연락해 주세요. |
| 2    | 환불은 상품 수령 후 7일 이내(단순 변심) 또는 30일 이내(상품 하자 및 오배송)에 신청하실 수 있습니다.     |
| 3    | 사이즈나 색상 교환 시 발생하는 배송비는 고객님께서 부담하셔야 합니다. 교환은 수령 후 7일 이내에 1회에 한해 가능합니다. |

## 5. 해석

| 확인한 것                                                                        | 의미                                                                                                                                                  |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 202 응답은 10~47ms, 에이전트 처리는 22~29초                                      | 접수와 처리가 분리되어 있다. 요청 스레드는 에이전트를 기다리지 않는다. 같은 요청을 동기로 처리하면 요청 하나가 20초 넘게 스레드를 잡을 것으로 보인다(이번에 동기 방식은 재지 않았다) |
| 3건의 처리 시간 합(74.6초) ≈ 전체 완료 시간(75초), 3번은 약 53초 뒤에 시작        | 워커는 한 건씩 순차 처리한다. 요청이 몰리면 뒤의 요청일수록 오래 기다린다. Day 18 의 멀티 컨슈머 실험과 Day 25~ 부하 시험의 출발점이다                  |
| 처리 순서가 보낸 순서와 같음                                                     | 파티션이 1개이고 워커가 하나라 순서가 유지된다. 파티션이나 워커가 늘면 순서가 달라질 수 있다(Day 18)                                                   |
| `committed` 가 처리 건수만큼 증가                                                | 수동 commit(처리 후)이 건마다 일어난다                                                                                                                |
| 조회 API 에서 상태, 답, 처리 시간을 읽음                                         | 메모리 임시 저장이 동작한다. 4주차에 Redis 로 바꿀 자리가 정해졌다                                                                                    |
| 처리 시간이 7.6초에서 22~29초로 바뀜                                             | Day 16 의 7.6초는 한 번 잰 값이었다. 부하 시험의 기준으로 쓰기 전에 다시 재야 한다. 원인은 모른다(LLM 응답 시간 변동, 질문 차이 등을 생각할 수 있으나 확인하지 않았다) |


## 6. 확인하지 않은 것

아래는 모두 선택 항목이라 하지 않아도 Day 17 의 핵심은 완료다. 방법은 가이드 7번(실행과 확인)에 있다.

| 항목                                          | 내용                                                                                                                  |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 없는 id 조회가 404 인지 (가이드 ⑥)            | `curl ... /results/없는-id` 를 아직 하지 않았다                                                                       |
| 처리 중 `PROCESSING` 상태 (가이드 ⑥)          | `AGENT_DEBUG_DELAY_SEC` 로 대기시킨 뒤 조회해 보지 않았다. 스크립트 출력에서는 `PROCESSING` 을 직접 보지 못했다       |
| 서버 재시작 뒤 조회가 404 인지 (가이드 ⑥)     | 메모리 저장이라 사라질 것으로 예상하지만 확인하지 않았다                                                              |
| 실패 요청이 섞인 경우 (가이드 ④)              | `PROVIDER=invalid` 로 `FAILED` 와 사유가 조회되는지 확인하지 않았다                                                   |
| 서버를 끈 상태의 스크립트 동작 (가이드 ⑤)     | FAIL 로 끝나는지 확인하지 않았다                                                                                      |
| 스크립트 출력 순서와 FastAPI 로그 순서        | `[agent] 시작` 로그의 순서를 대조하지 않았다. 순서는 `/health` 의 `current_request_id` 변화로만 확인했다               |
| 처리 시간이 길어진 원인                       | 7.6초(Day 16)와 22~29초(Day 17)의 차이 원인을 확인하지 않았다                                                         |
| macOS bash 버전                               | 어느 버전의 bash 로 돌렸는지 확인하지 않았다(변수 뒤 한글 문제가 난 것으로 미루어 구버전일 수 있다)                   |
| 실제 `main.py` 에서 라우터 등록 확인          | 실행한 결과로는 조회 API 가 응답했으므로 등록은 된 것이다(별도로 확인한 항목은 아님)                                  |
