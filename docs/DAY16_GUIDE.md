# Day 16 가이드 — Kafka Consumer 와 에이전트 연결, commit 시점 결정

> 상태: 완료(2026-10-12), 실행 결과는 [DAY16_RESULT.md](DAY16_RESULT.md). 아래는 작성 당시 안내다.

## 1. 오늘 목표

Day 15 에서 로그만 남기던 자리에서 **에이전트(`run_agent`)를 호출**한다. 그리고 Day 13 부터 미뤄 둔 결정, **언제 commit 할 것인가**를 정하고 그 차이를 실험으로 확인한다.

```
[Spring WAS :8080] -> [Kafka agent.requests] -> [FastAPI :8000 의 워커] -> run_agent() -> (답) 로그
                                                  └ 처리가 끝난 뒤에 commit
```

결과(답)는 아직 어디에도 저장하지 않고 로그로만 남긴다. 저장과 조회는 Redis 를 붙이는 4주차.

## 3. 결정: commit 은 처리가 끝난 뒤에 한다

이때 `commit` 은 **Kafka 의 offset commit** 이다. git 커밋(코드 저장)과 이름만 같다.

| 구분            | Kafka 의 commit                                                                                            | git 커밋   |
| --------------- | ---------------------------------------------------------------------------------------------------------- | ---------- |
| 저장하는 것     | "이 컨슈머 그룹은 offset 43 까지 처리했다"는 위치(책갈피)                                                  | 코드 변경  |
| 저장되는 곳     | Kafka 의 `__consumer_offsets` (Day 13)                                                                     | git 저장소 |
| 메시지를 지우나 | 지우지 않는다. 위치만 저장한다                                                                             | -          |
| 효과            | 서버를 껐다 켜도 저장된 위치부터 이어서 읽는다. Day 15 에서 서버를 다시 켰을 때 offset 42 부터만 나온 이유 | -          |

Day 16 에서 정하는 것은 **이 책갈피를 언제 저장하느냐**다.

예: 요청 X 를 읽고 에이전트가 10초 걸리는 중에 서버가 죽었다.

| 방식                | 다시 켜면                                                   | 결과                                              |
| ------------------- | ----------------------------------------------------------- | ------------------------------------------------- |
| 자동 commit         | 읽을 때 "X 까지 읽음"이 저장돼 있어서 X 다음부터 읽는다     | X 는 처리되지 않은 채 **사라진다**                |
| 처리 후 수동 commit | "X 까지 처리함"이 아직 저장되지 않아서 X 부터 다시 처리한다 | X 가 **두 번 처리될 수는 있지만 사라지지 않는다** |

commit 은 "여기까지 읽었다"는 책갈피(offset)를 Kafka 에 저장하는 것이다. 저장 시점에 따라 서버가 죽었을 때 결과가 달라진다.

| 방식                           | 처리 도중 서버가 죽으면                                                                        | 대가                                                                          |
| ------------------------------ | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 자동 commit (Day 13/15)        | 읽은 직후(주기적으로) 위치가 저장되므로 그 메시지는 **다시 오지 않을 수 있다 → 요청 유실**     | 설정이 가장 쉽다. 에이전트 요청에는 부적합                                    |
| **처리 후 수동 commit (채택)** | commit 전이라 **다음에 같은 메시지를 다시 받는다 → 유실 없음, 중복 처리 가능** (at-least-once) | 같은 요청이 두 번 처리될 수 있다. LLM 호출이 두 번 나가고, 중복을 걸러야 한다 |
| 처리 전 수동 commit            | 위치가 먼저 저장되므로 유실될 수 있다                                                          | 자동 commit 과 비슷한 위험이라 채택하지 않음                                  |

채택 이유: 이 프로젝트에서 요청 유실은 사용자가 답을 영영 못 받는 것이고, 중복 처리는 비용과 시간이 더 드는 것이다. 유실보다 중복을 택했다. 중복을 걸러내는 일(`requestId` 로 이미 처리했는지 확인)은 Redis 를 붙이는 4주차에서 다룬다.

### 에이전트가 실패하면

| 선택지                                           | 결과                                                                                                |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| 실패해도 commit 하지 않고 계속 재시도            | 그 메시지 하나가 풀리지 않으면 **뒤의 요청이 모두 막힌다**                                          |
| **실패로 기록하고 commit, 다음 메시지로 (채택)** | 워커는 계속 돈다. 실패한 요청은 `failed` 로 세고 로그에 남긴다. 사용자는 아직 실패를 알 방법이 없다 |

실패한 요청을 따로 보관하고 재처리하는 DLQ 는 Day 32 에서 한다. 해석할 수 없는 메시지(JSON 이 깨졌거나 필드가 없음)도 같은 이유로 건너뛰고 commit 한다.

### 서버를 끄는 경우

처리 중에 서버를 끄면(`Ctrl+C`) 처리 중이던 메시지는 commit 되지 않는다. 다시 켜면 그 메시지를 처음부터 처리한다. 아래 실험 ⑥에서 확인한다.

## 4. 환경변수

| 이름                    | 기본값         | 의미                                                                                                                                                                                                     |
| ----------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `KAFKA_COMMIT_MODE`     | `manual`       | `manual` = 처리 후 commit, `auto` = 자동 commit (비교 실험용)                                                                                                                                            |
| `KAFKA_HANDLER`         | `agent`        | `log` 로 바꾸면 Day 15 처럼 받았다는 로그만 남긴다 (LLM 호출 없음)                                                                                                                                       |
| `AGENT_TIMEOUT_SEC`     | `120`          | 에이전트 한 건 최대 시간. 넘으면 실패로 처리                                                                                                                                                             |
| `AGENT_DEBUG_DELAY_SEC` | `0`            | 실험용. 에이전트를 부르기 전에 이만큼 기다려 "처리 중" 상태를 길게 만든다                                                                                                                                |
| `KAFKA_OFFSET_RESET`    | `latest`       | **Day 15 의 `earliest` 에서 바꿨다.** 새 그룹이 토픽 전체를 읽어 옛 메시지마다 LLM 을 호출하는 것을 막으려고. 이미 commit 된 위치가 있는 그룹(`agent-workers`)은 이 값과 무관하게 저장된 위치부터 읽는다 |
| 그 외                   | Day 15 와 같음 | `KAFKA_BOOTSTRAP`, `KAFKA_TOPIC`, `KAFKA_GROUP`, `KAFKA_RETRY_SEC`, `KAFKA_CONSUMER_ENABLED`                                                                                                             |

## 7. 실행과 확인

### ① 서버 기동 (`d2-ai-python`, 가상환경 켠 상태)

```bash
source run.sh
```

기대: `워커 시작 요청 ...`, `Kafka 접속 완료, 수신 대기`. `curl -s localhost:8000/health` (**FastAPI**, 8000) 의 `kafka_consumer` 에 `commit_mode: manual`, `failed: 0`, `committed: 0`.

### ② 정상 요청 (에이전트까지)

```bash
# 8080 = Spring WAS 로 보낸다
curl -i -X POST http://localhost:8080/api/agent/requests \
  -H 'Content-Type: application/json' \
  -d '{"question":"단순 변심으로 환불하면 배송비는 누가 내요?","provider":"gemini"}'
```

기대: Spring 이 `202` 와 `requestId` 를 돌려주고, FastAPI 로그에 같은 `requestId` 로 `[agent] 시작` → 몇 초 뒤 `[agent] 완료 ... elapsed_ms=... answer=...`. `/health` 의 `received`, `committed` 가 1 씩 늘어난다. 처리 중에 `/health` 를 보면 `current_request_id` 에 그 requestId 가 보인다.

### ③ 실패 처리 (LLM 호출 없이)

```bash
# 8080 = Spring WAS 로 보낸다
curl -i -X POST http://localhost:8080/api/agent/requests \
  -H 'Content-Type: application/json' \
  -d '{"question":"실패 테스트","provider":"invalid"}'
```

기대: 지원하지 않는 provider 라는 예외가 나서 FastAPI 로그에 `처리 실패, 건너뜀 requestId=...` 와 에러가 찍히지만 **워커는 계속 돈다**. `/health` 의 `failed` 와 `committed` 가 1 씩 늘고 `state` 는 `running`. 이어서 ②를 다시 보내 정상 처리되는지 본다(실패 한 건이 뒤의 요청을 막지 않는다).

### ④ 핵심 실험: 처리 중에 서버를 끄면 (수동 commit)

1. `Ctrl+C` 로 서버를 끄고, 처리 시간을 길게 만들어 다시 켠다.
    ```bash
    export AGENT_DEBUG_DELAY_SEC=30
    source run.sh
    ```
2. ② 의 curl 을 보낸다. FastAPI 로그에 `[agent] 시작 requestId=X` 가 뜨면, 30초가 지나기 전에 `Ctrl+C` 로 서버를 끈다.
3. 지연을 없애고 다시 켠다.
    ```bash
    unset AGENT_DEBUG_DELAY_SEC
    source run.sh
    ```
4. 기대: 같은 `requestId=X` 로 `[agent] 시작` 이 **다시** 찍히고 `완료` 까지 간다(commit 하지 못했으므로 다시 받음). kafka-ui 의 `agent-workers` 그룹 Lag 이 서버를 끈 동안 1 이었다가 처리 후 0 이 되는지도 볼 수 있다.

### ⑤ 비교 실험: 자동 commit 이면

```bash
export KAFKA_COMMIT_MODE=auto
export AGENT_DEBUG_DELAY_SEC=30
source run.sh
```

④의 1~3 을 똑같이 한다. 결과: 자동 commit 은 `stop()` 때 앱에 전달된 메시지까지 마지막으로 commit 하므로, 보낸 직후에 꺼도 같은 메시지가 **다시 나오지 않는다 = 요청 유실**(결과는 DAY16_RESULT 3-4). 끝나면 `unset KAFKA_COMMIT_MODE AGENT_DEBUG_DELAY_SEC`.

- 강제 종료도 테스트(ctrl + c 아닌)

```
# 실행중 port 검색
lsof -i :8000

# 강제 종료. 예시) kill-9 123 1456
kill -9 <pid> </pid>
```

### ⑥ 배선만 보기 (선택, LLM 호출 없음)

`export KAFKA_HANDLER=log` 후 서버를 켜고 ②를 보내면 에이전트 호출 없이 `[recv]` 로그만 나온다. 끝나면 `unset KAFKA_HANDLER`.

### ⑦ 처리 중에 FastAPI(8000)가 응답하는지 (선택)

에이전트가 처리하는 약 7초 동안 `/health` 가 응답하고 `current_request_id` 가 보이는지 확인한다. 에이전트를 별도 스레드로 돌린 설계가 실제로 이벤트 루프를 막지 않는지 보는 것이다. `AGENT_DEBUG_DELAY_SEC` 는 설정하지 않은 상태에서 한다.

1. 터미널 A 에서 아래를 먼저 입력해 두고 (아직 Enter 는 누르지 않는다):

    ```bash
    # 8000 = FastAPI 의 /health 를 1초 간격으로 8번 확인
    for i in $(seq 1 8); do curl -s localhost:8000/health; echo; sleep 1; done
    ```

2. Postman 으로 Spring(8080)에 정상 요청을 보내고 곧바로 터미널 A 에서 Enter 를 누른다.
3. 기대(확인 전 예상): `/health` 가 끊기지 않고 매초 응답하고, 처리 중인 동안의 줄에는 `current_request_id` 에 requestId 가, 끝난 뒤에는 `null` 이 보인다. `received`, `committed` 가 1 늘어난다. 응답이 처리가 끝날 때까지 멈춘다면 에이전트가 이벤트 루프를 막고 있다는 뜻이다.

### ⑧ 에이전트 호출 도중에 서버를 끄면 (선택)

`AGENT_DEBUG_DELAY_SEC` 를 설정하지 않은 상태에서, LLM 응답을 기다리는 중에 `Ctrl+C` 를 누른다.

1. 서버를 켜고 Postman 으로 정상 요청을 보낸다.
2. FastAPI 로그에 `[agent] 시작` 이 뜨면 바로(약 7초 안에) `Ctrl+C` 를 누른다.
3. 확인할 것: (a) 종료가 바로 되는지, 아니면 `Waiting for application shutdown.` 에서 한동안 멈추는지(대략 몇 초인지 적어 둔다), (b) 다시 켰을 때 같은 requestId 가 다시 처리되는지.
4. 주의: 에이전트 호출은 별도 스레드에서 돌고 있어서 종료가 그 호출이 끝날 때까지 기다릴 수 있다. 너무 오래 멈추면 `Ctrl+C` 를 한 번 더 눌러 강제로 끈다. 이 경우 그 사실도 결과에 적는다.

### ⑨ 서버가 꺼진 동안 쌓인 요청 (선택)

1. FastAPI(8000)를 `Ctrl+C` 로 끈다. Kafka 와 Spring(8080)은 켜 둔다.
2. Postman 으로 Spring 에 **서로 다른 질문** 3건을 순서대로 보낸다 (각 요청의 requestId 를 적어 둔다). 질문이 달라야 로그에서 순서를 구분할 수 있다.
3. (선택) kafka-ui(8090)에서 `agent-workers` 그룹의 Lag 이 3 인지 본다.
4. FastAPI 를 켠다. 기대: 3건이 보낸 순서(offset 순서)대로 `[agent] 시작` → `완료` 가 이어진다. 끝난 뒤 `/health` 의 `received`, `committed` 가 3 늘어난다. 요청 3건이 LLM 호출 3번이라는 점에 유의한다.

## 8. 작성 중 확인한 것과 확인하지 않은 것

| 구분          | 내용                                                                                                                                                                                                                                                                          |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 확인함        | Kafka 없이 `_handle` 단독 시험: 성공 시 `received` 증가, handler 예외 시 `failed` 증가와 워커 유지(예외 전파 없음), 깨진 JSON 은 `skipped` 증가, 서버 종료(`CancelledError`)는 삼키지 않고 전파되며 `failed` 로 세지 않음. 기본값 `OFFSET_RESET=latest`, `COMMIT_MODE=manual` |
| 확인하지 않음 | 실제 Kafka 에서의 수동 commit(`consumer.commit()`)과 위치 저장, 에이전트 호출(Qdrant, Gemini 필요), 처리 중 종료 후 재처리, 자동 commit 에서의 유실                                                                                                                           |
| 확인하지 않음 | 실제 `main.py` 에서 `agent_handler` 를 import 해 기동하는 것(작성 환경에는 에이전트 라이브러리가 없다)                                                                                                                                                                        |
| 확인하지 않음 | 에이전트 호출 중(LLM 대기 중)에 `Ctrl+C` 하면 종료가 즉시 되는지. 실험 ④는 이 문제를 피하려고 에이전트 호출 전의 대기(`AGENT_DEBUG_DELAY_SEC`) 구간에서 끈다                                                                                                                  |

## 9. 알려진 한계

| 항목           | 내용                                                                                                                                                                                    |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 중복 처리      | 처리 후 commit 이므로 같은 요청이 두 번 처리될 수 있다. 걸러내기는 4주차                                                                                                                |
| 실패한 요청    | 건너뛸 뿐 보관하지 않는다. 사용자에게 실패를 알릴 방법도 아직 없다. DLQ 는 Day 32                                                                                                       |
| 순차 처리      | 한 건이 120초까지 걸리면 그동안 뒤의 요청이 기다린다. 오래 걸리면 Kafka 가 이 워커를 죽은 것으로 보고 파티션을 다른 워커에 넘길 수 있다(`max_poll_interval_ms`, 기본값은 확인하지 않음) |
| 타임아웃       | 시간이 지나도 스레드 안의 LLM 호출은 계속된다(비용이 나갈 수 있음)                                                                                                                      |
| 결과 저장 없음 | 답은 로그에만 남는다                                                                                                                                                                    |
| 외부 한도      | Gemini 한도(429)에 걸리면 `failed` 로 센다. 재시도 정책은 아직 없다                                                                                                                     |
