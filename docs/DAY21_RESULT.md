# Day 21 결과 — 분산 락

> 구현과 실행 방법은 [DAY21_GUIDE.md](DAY21_GUIDE.md), 코드 흐름은 [DAY21_CODE_GUIDE.md](DAY21_CODE_GUIDE.md). 이 문서는 실행한 것과 확인한 결과를 담는다.
> 상태: 가이드 ① (`lock_check` 확인 스크립트)와 ② (`redis-cli` 로 락 키 보기)를 내 환경에서 실행해 기록함(2026-10-13). ③ (워커 2대 동시 요청)은 처음 실행은 응답만, 재실행은 서버 로그까지 받아 락이 동작한 것을 확인했다(3-3). ④ 는 내 환경에서 실행하지 않고 샌드박스 시뮬레이션 결과만 기록했다(3-4). ⑤ (락 끄고 ③ 다시)는 응답과 두 워커 서버 로그까지 받아 기록했다(3-5).
> 포트: **8080 = Spring WAS**, **8000 = FastAPI 워커**, **6379 = Redis**.

**전체 목적:** 같은 `sessionId` 로 요청이 동시에 오면 두 워커가 같은 대화를 읽고 서로의 턴을 덮어쓸 수 있다(Day 20). Redis 에 락을 걸어 같은 세션은 한 번에 한 요청만 처리되게 만들고, 락 함수와 `run_agent` 연결이 의도대로 동작하는지 확인한다. 락 있음/없음을 정식으로 비교하는 것은 Day 22 다.

### 3-2. 락이 Redis 에 걸린 모양 (내 환경, 실제 Gemini)

**목적:** 요청이 처리되는 동안 락 키가 실제로 보이고, 끝나면 사라지는지 본다.

요청: `POST localhost:8000/api/v1/agent/run`, 질문 "환불은 며칠 안에 신청해야 하나요?", `session_id` `d21-a`. 응답은 `{"answer":"환불은 상품 수령 후 7일 이내에 신청 가능합니다. 단, 상품 하자나 오배송의 경우 수령 후 30일 이내에 신청하실 수 있습니다.","provider":"gemini"}` 였다(실제 Gemini, 서버는 8000 하나).

| 시점                         | 명령 (`docker exec redis1 redis-cli ...`)    | 출력                                  | 읽는 법                                                                           |
| ---------------------------- | -------------------------------------------- | ------------------------------------- | --------------------------------------------------------------------------------- |
| 요청 처리 중                  | `--scan --pattern 'agent:lock:*'`            | `agent:lock:conversation:d21-a`       | 세션별 락 키가 일반 Redis 키로 생겼다                                              |
| 요청 처리 중                  | `GET agent:lock:conversation:d21-a`          | `527983e15946422e87d3eab7a90fd9b6`    | 값은 32자리 16진수 토큰(락마다 새로 만든 `uuid4().hex`)                             |
| 요청 처리 중                  | `TTL agent:lock:conversation:d21-a`          | `139`                                 | 만료를 150초로 걸었으므로 락을 잡은 지 약 11초 지난 시점으로 읽힌다(추정, 시각은 따로 재지 않음) |
| 요청이 끝난 뒤                | `GET agent:lock:conversation:d21-a`          | (빈 줄, 값 없음)                      | 키가 없다. 락이 풀렸다                                                             |
| 요청이 끝난 뒤                | `--scan --pattern 'agent:lock:*'`            | (출력 없음)                           | 락 키가 하나도 남지 않았다                                                         |

- 기대(가이드 ②)와 같다: 처리 중에는 키가 보이고 값은 32자리 토큰, TTL 은 150 부근, 끝난 뒤에는 없다.
- 중간에 `GET` 명령이 한 번 `zsh: command not found` 로 실패한 줄이 있는데, 입력 앞에 문자가 하나 더 붙은 것으로 보이는 오타이며 다시 입력해 정상으로 나왔다. 결과와 무관하다.
- 이 확인은 한 요청의 한 시점이다. 두 요청이 겹칠 때 뒤 요청이 기다리는 모습은 ③ 에서 본다.


### 3-3. 같은 세션 동시 요청, 워커 2대 (내 환경, 실제 Gemini, 락 있음)

**목적:** 워커 2대에 같은 세션을 동시에 보냈을 때 대화가 유실되지 않는지, 그리고 락 때문에 한쪽이 기다리는지 본다.

먼저 `DELETE .../sessions/d21-race` 를 보냈고 응답은 `{"sessionId":"d21-race","deleted":false}` 였다(지울 기록이 원래 없었다는 뜻). 이어서 두 요청을 동시에 보냈다.

| 요청                               | 워커       | 질문                | 답                                                                                                         | `time_total` |
| ---------------------------------- | ---------- | ------------------- | ---------------------------------------------------------------------------------------------------------- | ------------ |
| `[2]` (먼저 끝남)                   | 8001       | 교환 배송비는 누가? | 교환 배송비는 고객님께서 부담하셔야 합니다. 교환은 상품 수령 후 7일 이내에 1회에 한해 가능합니다.             | **11.90초**  |
| `[1]` (나중에 끝남)                 | 8000       | 환불은 며칠 안에?   | 환불 신청은 상품 수령 후 7일 이내(단순 변심) 또는 30일 이내(상품 하자/오배송)에 가능합니다. 환불 승인 후 ... | **81.03초**  |

끝난 뒤 `GET .../sessions/d21-race`: `turns` 2, `ttlSec` 3600, 메시지 4개가 **교환 질문 → 교환 답 → 환불 질문 → 환불 답** 순서였다.

| 가이드 ③ 에서 볼 것                           | 기대(락 있음)                          | 이번 결과                                                                                                  |
| --------------------------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `sessions/d21-race` 의 `turns`                | 2                                      | **2** (유실 없음)                                                                                          |
| 두 요청의 `time_total`                        | 늦게 끝난 쪽이 대략 두 요청 시간의 합  | 늦게 끝난 쪽 81.03초. 먼저 끝난 쪽 11.90초의 두 배 이상이어서 "합"보다 훨씬 길다(아래)                      |
| 두 워커의 `[timing] 이전 대화 N개 메시지`     | 한쪽 0개, 다른 쪽 2개                  | **미확인** (서버 로그를 받지 못함)                                                                         |

- 대화는 유실되지 않았다. 다만 이 결과만으로는 락이 동작했다고 말할 수 없다. 락이 없어도 `append_turn` 이 저장 직전에 다시 읽어서(Day 20 3-6) 두 턴이 모두 남을 수 있기 때문이다. 락이 동작했는지는 `[timing] 이전 대화 N개` 가 0개와 2개로 갈렸는지로 판단한다.
- 저장 순서가 교환(8001)이 먼저, 환불(8000)이 나중인 것은 8001 요청이 먼저 끝난 것과 맞는다. 8000 요청이 락을 기다렸다면 이 순서가 되지만, 락 없이 그냥 늦게 끝나도 같은 순서가 된다(구분 불가).
- 81.03초는 설명되지 않았다. 11.90초 요청이 먼저 끝났다면 락을 기다린 8000 요청의 시간은 대략 11.9초 + 자기 처리 시간이어야 하는데, 자기 처리 시간이 약 69초가 되는 셈이다. 가능한 원인은 Gemini 응답이 느렸거나 에이전트가 도구를 여러 번 돌았거나 하는 것인데, 로그가 없어 확인하지 못했다. 120초 제한(`AGENT_TIMEOUT_SEC`) 안에는 끝났다.


#### 3-3 재실행. 락 있음, 서버 로그 포함 (내 환경, 실제 Gemini)

두 워커를 `uvicorn main:app --port 8000` / `--port 8001` (`KAFKA_WORKER_ID` 는 `w1`, `w2`, 락 환경변수 없음 = 락 있음)로 띄우고 같은 요청 두 개를 동시에 보냈다. **이번에는 앞에 `DELETE` 를 하지 않았다.** 그래서 `d21-race` 에는 ⑤ 실행에서 남은 2턴(메시지 4개)이 이미 있었고, 가이드의 기대값(0개와 2개)에서 모두 4씩 늘어난 4개와 6개가 기대값이다.

| 요청                    | 워커 | 질문                | `time_total` | 서버 로그                                                                                              |
| ----------------------- | ---- | ------------------- | ------------ | ------------------------------------------------------------------------------------------------------ |
| `[2]` (먼저 끝남)        | 8001 | 교환 배송비는 누가? | **12.39초**  | `그래프 전체(run_agent)` 12.38초 (검색 0.51초, LLM 7.58초, 도구 요청 0개). **`이전 대화` 줄은 캡처에서 잘려 보지 못했다** |
| `[1]` (나중에 끝남)      | 8000 | 환불은 며칠 안에?   | **20.41초**  | **`이전 대화 6개 메시지`**, LLM 7.96초(도구 요청 0개), `그래프 전체(run_agent)` 8.01초                |

끝난 뒤 `sessions/d21-race`: `turns` **4**(메시지 8개). 앞 4개는 ⑤ 에서 남은 것이고, 뒤 4개가 이번 실행이다. 이번 실행의 순서는 **교환 질문 → 교환 답 → 환불 질문 → 환불 답**.

| 가이드 ③ 에서 볼 것                         | 기대(락 있음, `DELETE` 를 했다면 / 이번처럼 안 했을 때) | 이번 결과                                                                                   |
| ------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 뒤 요청의 `이전 대화 N개`                   | 2개 / **6개**                                            | **6개** (8000). 앞 4개 + 8001 이 방금 저장한 2개를 봤다                                      |
| 앞 요청의 `이전 대화 N개`                   | 0개 / 4개                                                | **미확인** (8001 로그의 해당 줄이 캡처에 없음)                                              |
| 늦게 끝난 요청의 `time_total`               | 두 요청 시간의 합                                        | 20.41초. 8001 의 12.39초 + 8000 의 처리 시간 8.01초 = 20.40초로 거의 같다                    |
| `turns`                                     | 4 / 2 + 앞 기록                                          | 4 (이번 2턴 모두 저장, 유실 없음)                                                           |

- **락이 동작했다고 볼 수 있다.** 8000 요청은 동시에 출발했는데(`&` 로 동시 실행, 총 20.41초) 처리 시간은 8.01초뿐이고, 앞 4개에 더해 8001 요청의 새 턴까지 6개를 읽었다. 8000 이 8001 의 저장이 끝나길 기다렸다가 읽었다는 뜻이고, 기다린 시간(약 12.4초)이 8001 의 처리 시간과 같다.
- 락이 없었다면(3-5) 8000 은 시작할 때 읽어 4개만 봤을 것이다. 이번에 6개를 본 것이 락 있음과 없음의 차이다.
- 8000 의 모델 호출은 이번에 도구 요청이 0개여서(검색 없음) 8초 만에 끝났다. 대화에 이미 같은 질문과 답이 있어서 모델이 검색 없이 답했을 가능성이 있으나, 로그로는 확인하지 못했다(추정).
- 처음 실행(위 3-3)의 81.03초와 이번 20.41초는 같은 조건이 아니다. 처음 실행은 서버 로그가 없어 원인을 모르는 채로 남아 있다.
- 서버 로그에는 `Heartbeat failed ... rebalancing`, `파티션 회수/배정` 줄도 섞여 있다. Kafka 그룹 재배정 로그이고 락과 무관하다.


### 3-4. 락 대기 시간 초과 (샌드박스 시뮬레이션, 내 환경에서 실행한 것이 아님)

**목적:** 락을 못 잡고 기다리다 `wait_sec` 이 지나면 HTTP 는 409, Kafka 경로는 `FAILED` 로 끝나는지 본다. 앞 요청 대신 락을 수동으로 걸어 둔다.

**이 항목의 숫자는 모두 코드를 만든 쪽 샌드박스(실제 `redis-server` 7.0.15, 가짜 모델 0.4초, 포트 8000 에 `uvicorn`)에서 나온 것이다.** 내 환경(`redis1`, Gemini)에서 실행한 결과가 아니다. 샌드박스의 `redis_lock.py`, `routers/agent.py`, `agent_graph.py`, `agent_handler.py` 는 내 환경 파일과 md5 가 같다(확인함).

가이드 ④ 의 순서대로 했다.

| 단계                                            | 명령 / 상황                                                                                   | 샌드박스에서 나온 결과                                                                                     |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 1) 워커를 3초로 재기동                          | `REDIS_LOCK_WAIT_SEC=3 uvicorn ... --port 8000`                                               | 기동됨                                                                                                     |
| 2) 락 수동으로 걸기                             | `SET agent:lock:conversation:d21-x manual NX EX 60`, `TTL`                                    | `OK`, `60`                                                                                                 |
| 3) 락이 걸린 상태에서 요청                      | `curl -i -w ... POST /api/v1/agent/run` (`session_id` `d21-x`)                                | `HTTP/1.1 409 Conflict`, `{"detail":"같은 세션의 앞 요청이 아직 처리 중이다: 3초 안에 락을 잡지 못함 name=conversation:d21-x"}`, `time_total` **3.12초** |
| 3) 직후 수동 락                                 | `GET agent:lock:conversation:d21-x`                                                           | `manual` (기다리다 실패한 요청이 남의 락을 건드리지 않음)                                                  |
| 4) 락 지우고 같은 요청                          | `DEL`, 같은 `curl`                                                                            | `DEL` 이 `1`, `HTTP/1.1 200 OK`, `time_total` 0.40초 (가짜 모델 시간)                                      |
| 요청 뒤                                         | `--scan --pattern 'agent:lock:*'`                                                             | 락 키 없음                                                                                                 |

**내 환경에서 200 이 나온 경우를 같은 방식으로 재현했다.** 워커를 3초 설정 없이 기본(대기 100초)으로 띄우고, 수동 락을 60초 대신 **5초**로 걸어(`EX 5`) 요청하니 `HTTP/1.1 200 OK`, `time_total` **5.39초**였다. 락이 만료되는 순간 요청이 들어간 것이다. 내 환경에서 60초 락으로 같은 일이 생기면 60초쯤 뒤 200 이 나온다는 추정과 같은 모양이다. 다만 내 환경의 `time_total` 은 받지 못해서 실제로 60초쯤이었는지는 확인하지 못했다.

**Kafka 경로(`agent_handler`)의 `FAILED` 기록**도 샌드박스에서 확인했다. `aiokafka`, `kafka_worker` 는 샌드박스에 없어 이름만 흉내 낸 가짜 모듈을 끼웠고, `result_store` 는 같은 인터페이스의 최소 복사본을 썼다. `REDIS_LOCK_WAIT_SEC=3`, 락 수동 보유 상태에서 `agent_handler` 에 메시지를 넣었다.

| 확인                                  | 결과                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------ |
| `agent_handler` 가 던진 예외          | `LockTimeout: 3초 안에 락을 잡지 못함 name=conversation:e3` (다시 던져짐) |
| 걸린 시간                             | 3.06초                                                                   |
| `store` 에 남은 상태                  | `FAILED`, 에러 `LockTimeout: 3초 안에 락을 잡지 못함 name=conversation:e3` |

- 이전에 "코드를 읽은 예상"이던 `LockTimeout` → `FAILED` 가 샌드박스에서 실행으로 확인됐다. 실제 Kafka, 내 환경의 `result_store` 와는 연결하지 않았다.
- 모델 단계에서 예외가 나도 락이 풀리는 것, `session_id` 가 없으면 락을 쓰지 않는 것도 같은 스크립트에서 확인했다(`락 남음? None`, 락 키 없음).


### 3-5. 락을 끄고 같은 세션 동시 요청 (내 환경, 실제 Gemini, 사용자 실행)

**목적:** ③ 과 같은 요청을 락 없이 했을 때 동작을 본다(가이드 ⑤). 사용자가 "이건 5번 내용"이라며 붙여 준 출력이다.

`DELETE .../sessions/d21-race` 응답은 `{"sessionId":"d21-race","deleted":true}` (③ 에서 남은 기록이 있어 지워졌다). 이어서 같은 두 요청을 동시에 보냈다.

| 요청                    | 워커  | 질문                | 답                                                                                    | `time_total` |
| ----------------------- | ----- | ------------------- | ------------------------------------------------------------------------------------- | ------------ |
| `[2]` (먼저 끝남)        | 8001  | 교환 배송비는 누가? | 교환 배송비는 고객님께서 부담하셔야 합니다. 사이즈나 색상 교환은 상품 수령 후 7일 이내 1회에 한해 가능합니다. | **6.93초**   |
| `[1]` (나중에 끝남)      | 8000  | 환불은 며칠 안에?   | 환불은 상품 수령 후 7일 이내에 신청하실 수 있습니다. 단, 상품에 하자가 있거나 오배송된 경우에는 수령 후 30일 이내에 가능합니다. | **16.01초**  |

끝난 뒤 `sessions/d21-race`: `turns` 2, 메시지 순서 **교환 질문 → 교환 답 → 환불 질문 → 환불 답**.

| 가이드 ⑤ 에서 볼 것                          | 기대(락 없음)                       | 이번 결과                                                                                  |
| -------------------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------ |
| `turns`                                      | 2 또는 1 (겹치면 1, 못 겹치면 2)    | **2** (유실 없음)                                                                          |
| 두 요청의 `time_total`                       | 둘 다 거의 한 건 시간               | 6.93초와 16.01초. 늦게 끝난 쪽이 2.3배이지만 Gemini 응답 시간이 매번 크게 달라 이것만으로는 판단 불가 |
| `[timing] 이전 대화 N개 메시지`              | 둘 다 0개                           | **둘 다 0개** (아래 서버 로그). 기대와 같다                                                 |

- 요청 명령은 ③ 과 같다. 락이 꺼져 있었는지는 요청 출력에는 나오지 않았고, 아래 서버 로그에서 두 워커를 `SESSION_LOCK_ENABLED=false uvicorn main:app --port 8000` / `--port 8001` 로 띄운 것이 확인된다.
- 대화는 유실되지 않았다. 락이 없어도 `append_turn` 이 저장 직전에 다시 읽어서 두 턴이 모두 남을 수 있다(Day 20 3-6). 그래서 이 결과도 3-3(락 있음)과 `turns` 로는 구분되지 않는다. 구분은 `이전 대화 N개` 로그(락 있음: 0과 2, 락 없음: 둘 다 0)와 두 요청 시간으로 해야 한다.
**두 워커의 서버 로그** (붙여 준 터미널 출력에서 해당 요청 부분)

| 워커 | `이전 대화` | 첫 LLM 호출(`agent_node`)  | 검색          | 두 번째 LLM 호출 | `그래프 전체(run_agent)` | 요청 출력의 `time_total` |
| ---- | ----------- | -------------------------- | ------------- | ---------------- | ------------------------ | ------------------------ |
| 8000 | **0개**     | 4.62초, 도구 요청 1개      | 0.51초        | **10.81초**, 도구 0개 | 16.00초              | 16.01초                  |
| 8001 | **0개**     | 3.12초, 도구 요청 1개      | 0.57초        | 3.18초, 도구 0개 | 6.92초                   | 6.93초                   |

- 락이 꺼진 두 워커 모두 앞 대화를 0개로 읽었다. 두 요청이 서로의 질문을 모른 채 시작한 것이다. 기대(락 없음: 둘 다 0개)와 같고, 락이 있을 때의 기대(0개와 2개)와 다르다.
- 8000 의 16.00초는 락 대기가 아니라 자기 처리 시간이다(4.62 + 0.51 + 10.81 ≈ 16초). 8001 과의 시간 차이는 두 번째 LLM 호출이 10.81초 대 3.18초로 달랐기 때문이다. 같은 질문 종류에서도 Gemini 호출 시간이 이만큼 달라진다.
- `turns` 가 2 로 남은 것은 락 때문이 아니다. 둘 다 앞 대화 0개로 시작했는데도 두 턴이 모두 저장됐으므로, 저장 직전에 다시 읽는 `append_turn` 덕분에 이번에는 유실이 없었다고 읽을 수 있다. 8001 이 6.92초에 끝나 저장한 뒤에 8000 이 16초에 저장하는 순서여서 저장 구간이 겹치지 않았다. 저장 시점이 거의 동시인 경우는 이번에 보지 못했다.
- 로그에는 `Heartbeat failed ... rebalancing`, `파티션 회수/배정` 줄이 많이 섞여 있다. 같은 Kafka 그룹(`agent-workers`)의 워커를 켜고 끌 때 나오는 파티션 재배정 로그이고, 락과는 무관하다. 8000 쪽 출력에는 앞선 서버 종료 로그와 `worker-16920` 줄도 섞여 있어 이번 실험의 근거로는 쓰지 않았다.

## 7. 참조 — LangGraph 와 "그래프"라는 말

락 자체와는 별개로, 문서와 대화에 나오는 "그래프"가 무엇인지 정리한다. 코드 위치는 `d2-ai-python/app/services/agent_graph.py` 다.


### 7-1. LangGraph 한 줄 요약

AI 에이전트의 작업 흐름을 **그래프(노드 + 화살표)로 정의하고 실행해 주는 파이썬 라이브러리**다. 각 단계(모델 호출, 도구 실행 등)를 노드로 만들고 다음에 갈 곳을 화살표로 잇는다. 조건에 따라 갈림길을 만들 수 있고 이전 단계로 되돌아가는 반복도 만들 수 있다. 단계들은 공용 상태를 주고받고, 끝 지점에 도착하면 최종 결과가 나온다. 우리 프로젝트에서는 "모델이 판단 → 도구 실행 → 다시 판단"을 반복하다가 답이 나오면 끝내는 에이전트 루프를 이 방식으로 만들었다.


### 7-2. 왜 "그래프"인가

수학과 알고리즘에서 말하는 그래프(점과 선으로 이루어진 구조)를 그대로 가져온 이름이다. 차트나 그림이 아니다. 지하철 노선도에서 역이 노드, 선로가 엣지인 것과 같다. 에이전트의 흐름은 일직선이 아니라 갈림길과 되돌아가기가 있어서 한 줄짜리 체인으로는 표현이 안 되고 그래프여야 한다.

| 알고리즘 용어         | LangGraph 에서                                   |
| --------------------- | ------------------------------------------------ |
| 정점(vertex)          | 노드(node)                                       |
| 간선(edge)            | 엣지(edge)                                       |
| 방향 그래프           | 엣지에 방향(화살표)이 있음                        |
| 사이클(순환)          | `agent → tools → agent` 반복                     |

쓰임새는 다르다. 알고리즘에서는 그래프를 BFS, DFS, 최단 경로 같은 탐색 대상으로 쓰지만, LangGraph 에서는 "다음에 실행할 단계"를 정하는 **실행 흐름도**로 쓴다. 정점은 데이터가 아니라 실행할 함수이고, 간선을 따라 움직이는 것은 상태다. 모양은 상태 머신(state machine)과 비슷하다.


### 7-3. 용어와 우리 코드

| 용어                                | 뜻                                                                         | 우리 코드                                                                                 |
| ----------------------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| State (상태)                        | 노드들이 같이 읽고 쓰는 공용 데이터. 한 번 실행하는 동안 노드에서 노드로 넘어감 | `AgentState`(TypedDict). 대화 메시지(`messages`) 등                                        |
| Node (노드)                         | 한 단계의 일을 하는 함수. 상태를 받아 바꿀 부분만 돌려줌                    | `agent_node`(모델 호출), `tool_node`(도구 실행), `give_up_node`(포기 답변)                  |
| Edge (엣지)                         | "이 노드 다음은 저 노드"로 고정한 화살표                                    | `add_edge("give_up", END)`                                                                |
| Conditional edge (조건부 엣지)      | 라우터 함수가 상태를 보고 다음 노드를 고르는 화살표                         | `should_continue` 가 도구 호출이 있으면 `tools`, 없으면 `END` 로 보냄                       |
| Entry point (시작점)                | 실행이 처음 들어가는 노드                                                  | `set_entry_point("agent")`                                                                |
| END                                 | 도착하면 실행이 끝나는 특수 지점                                           | `from langgraph.graph import END`                                                         |
| StateGraph                          | 위 부품을 조립하는 설계도 객체                                             | `StateGraph(AgentState)` 에 `add_node`, `add_edge` 를 붙임                                 |
| compile                             | 설계도를 실행 가능한 형태로 굳히는 단계                                    | `graph.compile()` → `AGENT_GRAPH`                                                         |
| invoke                              | 컴파일된 그래프를 초기 상태로 한 번 실행해 최종 상태를 받음                | `AGENT_GRAPH.invoke(initial_state)`                                                       |

우리 그래프의 흐름은 다음과 같다(코드의 `add_node`, `add_conditional_edges` 호출을 근거로 한 요약).

```
시작 → agent (모델이 판단)
        ├─ 도구 호출이 있으면 → tools (도구 실행) → 다시 agent   ← 에이전트 루프
        │                        └─ (조건에 따라) → give_up → END
        └─ 도구 호출이 없으면(최종 답) → END
```

- `agent ↔ tools` 반복 때문에 한 요청이 20~30초 걸린다(코드 주석의 "여기가 20~30초").
- 이 문서의 락은 그래프 **바깥**에서 걸린다. `run_agent` 가 락을 잡고, 안쪽 `_run_agent_turn` 에서 `AGENT_GRAPH.invoke` 를 실행한다. 그래프 안의 노드들은 락의 존재를 모른다.


### 7-4. 확인하지 않은 것

| 항목                                              | 내용                                                                                                              |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `give_up` 으로 가는 정확한 조건                    | `tools` 에서 갈라지는 조건부 엣지(310행 부근)가 있다는 것만 보았고, 라우터 함수의 조건(재시도 한도 등)은 읽지 않았다 |
| `messages` 가 "덮어쓰기"가 아니라 "이어 붙이기"인지  | `Annotated` 를 쓰는 것은 보았지만 `AgentState` 정의(69행 부근)를 자세히 읽고 확인하지 않았다                       |
| 최대 단계 수 제한(recursion limit)                 | 순환이 무한 루프가 되지 않게 LangGraph 에 이런 제한이 있다고 알고 있으나, 기본값과 우리 코드의 설정 여부는 확인하지 않았다 |
