# Day 41.1 — RAG 유무 정량 비교 가이드

> 상태: **실행 완료**(2026-10-21). 결과는 [DAY41_1_RESULT.md](DAY41_1_RESULT.md).
> 앞 문서: [DAY41_and_42_REPORT.md](DAY41_and_42_REPORT.md). 일부 비교는 [DAY10_GUIDE.md](DAY10_GUIDE.md)(질문 1개), 검색 방식 비교는 [DAY12_RESULT.md](DAY12_RESULT.md).

**전체 목적:** RAG(검색한 문서를 프롬프트에 붙이기)를 쓰면 답이 얼마나 정확해지고 시간이 얼마나 느는지 숫자로 비교한다. Day 10 에서는 질문 1개를 눈으로 봤고, 정확도는 재지 않았다. 모델은 Claude 만 쓴다(Gemini 무료는 너무 느려서). 질문을 임베딩하는 단계만 Gemini 임베딩 API 를 쓴다(이 프로젝트의 임베딩은 처음부터 Gemini 이고, 저장하는 문서와 질문이 같은 임베딩이어야 비교된다).

## 1. 무엇을 비교하나

| 방식  | 하는 일                                                                    | 알려 주는 것                                        |
| ----- | -------------------------------------------------------------------------- | --------------------------------------------------- |
| plain | 검색 없이 Claude 혼자 답한다                                               | RAG 가 없을 때의 기준선                             |
| rag   | 질문과 가까운 문단 3개를 Qdrant 에서 찾아 붙여 답한다                       | 이 프로젝트가 쓰는 방식                             |
| full  | 검색 없이 문서 4개 전체(약 15문단)를 붙여 답한다                            | "문서가 이 정도로 적으면 RAG 없이 다 붙이면 되지 않나"에 대한 기준 |

질문은 두 묶음이다.

| 묶음          | 개수 | 내용                                                                                       | 채점                                              |
| ------------- | ---- | ------------------------------------------------------------------------------------------ | ------------------------------------------------- |
| 문서 안 질문  | 12   | Day 12 의 `EVAL_QUESTIONS`. 이 가상 쇼핑몰 문서에만 있는 값을 묻는다(교환 배송비 5,000원, 재설정 링크 30분, 적립 1%와 1년 등) | 답에 정답 값이 모두 있으면 정답(글자 규칙)         |
| 문서 밖 질문  | 4    | 문서에 없는 내용(고객센터 전화번호, 반품 택배사, 해외 배송, 매장 수령)                      | "모른다/없다"고 답하면 지어내지 않은 것으로 센다    |

같은 질문을 3번 반복해(`--reps 3`) 한 번의 운이 결과를 정하지 않게 한다. 검색은 질문당 한 번만 하고 반복에서는 같은 문단을 쓴다.

## 2. 확인 전 예상

실행 전에 적어 둔다. 틀려도 숨기지 않고 결과 문서에 그대로 남긴다.

| 번호 | 예상                                                                                         |
| ---- | -------------------------------------------------------------------------------------------- |
| P1   | plain 은 문서 안 질문 36번 중 정답이 적다(대략 3분의 1 이하). 가상 쇼핑몰의 값은 모델이 알 수 없다. 단 화장품 환불 불가 같은 상식과 겹치는 질문은 맞힐 수 있다 |
| P2   | rag 는 정답이 대부분이다(대략 90% 이상). 틀리는 것은 검색이 정답 문단을 놓친 질문에 몰린다(Day 12 의 문단 청킹은 12/12 였다) |
| P3   | full 도 rag 와 비슷하게 맞는다. 문서가 적어서 전부 붙여도 맥락이 넘치지 않는다                 |
| P4   | 문서 밖 질문에서 rag 와 full 은 규칙(없으면 "없다")대로 모른다고 답하고, plain 은 일반적인 답을 하거나 모른다고 한다. plain 이 얼마나 지어내는지는 예상하지 않는다 |
| P5   | 시간은 plain < rag < full. rag 는 plain 보다 검색(질문 임베딩 포함 약 0.5초)만큼 더 걸린다       |

## 3. 실행

프로젝트 루트(`d2-ai-python`)에서 한다. 서버를 띄울 필요는 없고 Qdrant(6333)만 떠 있으면 된다.

| 순서 | 커맨드                                           | 목적                                        | 호출                                     |
| ---- | ------------------------------------------------ | ------------------------------------------- | ---------------------------------------- |
| 1    | `python -m app.experiments.rag_eval --selftest`     | 채점 규칙 확인                              | 없음                                     |
| 2    | `python -m app.experiments.rag_eval`                | 본 실행. 결과표와 전체 답변 파일 생성        | Claude 144번, 임베딩 약 31번             |

옵션: `--reps 3`(반복), `--k 3`(rag 가 가져올 문단 수), `--provider claude`, `--out rag_eval_result.json`.
시험용 컬렉션 `chunk-exp-rageval` 을 새로 만들고 `documents-12` 는 건드리지 않는다. Claude 는 한 번에 3~4초라 전체가 10분 안팎이다.

실행 뒤 두 가지를 알려 달라.

1. 터미널에 찍힌 결과표 전체.
2. `rag_eval_result.json` 이 만들어졌다는 것(내가 열어서 채점이 맞았는지 확인한다).

## 4. 결과표 읽는 법

| 항목                    | 뜻                                                                                         |
| ----------------------- | ------------------------------------------------------------------------------------------ |
| 검색 n/12               | 정답 근거 문단이 상위 3개 안에 들어왔는가. rag 가 틀릴 때 검색 탓인지 모델 탓인지 가른다       |
| 방식별 정답 a/36        | 문서 안 질문 12개 x 3번 중 정답 사실이 모두 들어간 답의 수                                    |
| 질문별 정답 횟수        | 질문마다 반복 3번 중 몇 번 맞았나. 3번 중 일부만 맞는 질문은 모델 답이 흔들린다는 뜻           |
| 문서 밖 모른다 비율     | 높을수록 지어내지 않았다                                                                    |
| 시간                    | 방식별 호출 1번의 평균, 중앙값, 최대. 검색 시간은 별도 줄                                       |

## 5. 한계 (미리 적어 둔다)

- 문서는 이 프로젝트가 만든 가상 쇼핑몰 4개(15문단)뿐이다. 문서가 수천 개로 늘면 full 은 불가능해지고 검색 실패도 늘어난다. 그 규모의 결과는 아니다.
- 채점은 글자 규칙이다. 표현이 달라 맞는 답을 틀리게 세거나, 값만 우연히 들어간 답을 맞게 셀 수 있다. 그래서 모든 답을 파일에 남기고 결과 문서에서 일부를 직접 확인한다.
- "모른다" 판정도 글자 규칙이다(`해당 내용이 없`, `알 수 없`, `모르` 등).
- 질문 16개, 모델 하나(Claude Haiku)의 결과다. 작은 차이는 해석하지 않는다.
- 검색 시간은 질문당 한 번 잰 값이고, 시간 비교는 Claude 호출 1회 기준이다. 에이전트가 도구로 검색하는 실제 흐름(모델 호출 2번)과는 다르다.
