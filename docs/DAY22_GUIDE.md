## 2. 개념

**동시 요청에서 생길 수 있는 문제는 둘이다.** 하나는 Day 20 에서 본 "유실"이고, 하나는 Day 21 ③·⑤ 에서 본 "앞 대화를 모르고 답함"이다. 이 둘은 발생 조건이 달라서 따로 센다.

| 문제           | 무슨 일                                                                                                  | 언제 생기나                                                                                             |
| -------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 유실           | `append_turn` 이 "읽기 → 붙이기 → 통째로 쓰기" 하는 사이에 다른 요청이 같은 키에 써서 한쪽 턴이 사라진다 | 두 요청의 **저장이 거의 같은 순간**일 때(읽기와 쓰기 사이는 밀리초 단위). 끝나는 시각이 흩어지면 드물다 |
| 앞 대화를 놓침 | 요청이 시작할 때 이전 대화를 읽는데, 그 사이 다른 요청의 턴이 저장되지 않아서 앞 질문을 모르고 답한다    | **시작이 겹치기만 해도** 생긴다. 모델 호출이 길수록(수 초) 겹칠 가능성이 크다                           |

락이 있으면 같은 세션 요청이 차례로 처리되므로 둘 다 사라진다. 대신 같은 세션은 차례로 기다리므로 시간이 늘어난다. 이 득실을 재는 것이 오늘의 일이다.

**보는 숫자**

| 숫자           | 뜻                                                                                                               | 락 있음 기대 / 락 없음              |
| -------------- | ---------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 저장된 턴      | N 개를 보냈을 때 대화에 남은 턴 수. N 보다 적으면 유실                                                           | N / N 이하 (겹치면 줄어듦)          |
| 유실 라운드    | 라운드 중 저장된 턴이 N 보다 적었던 라운드 수                                                                    | 0 / 시나리오에 따라 다름            |
| 앞 대화 반영률 | 각 요청이 모델에 넘긴 이전 대화 메시지 수의 합 ÷ N(N-1). 차례로 처리되면 이전 수가 0, 2, 4, ... 라서 합이 N(N-1) | 1.00 / 0에 가까움                   |
| 완벽한 라운드  | 이전 대화 수가 정확히 0, 2, 4, ... 로 나온 라운드 수                                                             | 전부 / 거의 없음                    |
| 라운드 시간    | 요청 N 개를 보내고 모두 끝날 때까지                                                                              | 같은 세션은 약 N 배 / 약 한 건 시간 |

**시나리오 (inproc, 가짜 모델)**

| 이름   | 조건                                                   | 왜 보나                                                                                     |
| ------ | ------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| fixed  | 같은 세션 N 개, 모델 대기 시간이 모두 같다(0.4초)      | 모두 같은 순간에 끝나 저장이 겹치기 가장 쉬운 경우. 유실을 크게 볼 수 있다                  |
| jitter | 같은 세션 N 개, 대기 시간이 요청마다 다르다(0.3~1.2초) | 실제 모델처럼 끝나는 시각이 흩어진 경우. 유실이 드문 대신 앞 대화를 놓치는 일은 남는지 본다 |
| diff   | 서로 다른 세션 N 개                                    | 락이 세션별이라 서로 기다리지 않아야 한다. 락이 다른 세션의 처리량을 깎지 않는지 본다       |

**inproc 과 http 의 차이**

| 방식   | 하는 일                                                                              | 장점 / 한계                                                                                                             |
| ------ | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| inproc | 한 프로세스 안에서 스레드로 `run_agent` 를 동시에 부른다. 모델은 가짜, Redis 는 진짜 | 빠르고 호출이 안 든다. 락을 코드에서 켜고 끌 수 있다. 이전 대화 수까지 잴 수 있다. 실제 Gemini, 실제 서버 경로는 아니다 |
| http   | 떠 있는 워커 2대에 HTTP 요청을 동시에 보낸다. 실제 Gemini                            | 실제 환경. 느리고 호출이 든다. 락을 켜고 끄는 것은 워커를 띄울 때의 환경변수로 한다. 이전 대화 수는 서버 로그로 본다    |

http 방식의 주의점: `POST /api/v1/agent/run` 은 `async def` 인데 안에서 동기 함수(`run_agent`)를 부른다. 그래서 워커 한 대는 한 번에 한 요청만 처리한다(이벤트 루프가 막힌다, Day 17~18 의 알려진 한계). 워커가 2대면 실제로 동시에 처리되는 것은 2건이다. 그래서 http 방식의 기본 N 은 워커 수(2)이고, N 을 더 크게 하면 같은 워커에 몰린 요청은 락이 없어도 차례로 처리되어 차이가 작아 보인다(샌드박스에서 N=4, 워커 2대, 락 없음: 한 라운드가 0.8초, 즉 워커마다 2건이 차례로 처리됨).

## 5. 실행과 확인

### ① 락 있음/없음 비교 (inproc, 기본)

**목적:** 같은 세션 4개 요청을 동시에 보내는 것을 10라운드씩 반복해서, 락 있음/없음의 저장된 턴, 앞 대화 반영률, 라운드 시간을 3개 시나리오(fixed, jitter, diff)에서 비교한다.

```bash
cd d2-ai-python
source venv/bin/activate
python -m app.experiments.race_test
```

기대(샌드박스에서 본 것, 내 환경 미실행): 마지막 줄이 `== 결과: PASS`. 표는 아래와 비슷한 모양이다. 락 없음의 숫자는 매번 다르다.

| 시나리오 | 락   | 저장된 턴(평균/최소, 기대 4) | 유실 라운드 | 앞 대화 반영률 | 완벽한 라운드 | 라운드 시간(평균/최대) |
| -------- | ---- | ---------------------------- | ----------- | -------------- | ------------- | ---------------------- |
| fixed    | 있음 | 4.00 / 4                     | 0/10        | 1.00           | 10/10         | 1.73초 / 1.86초        |
| fixed    | 없음 | 2.00 / 1                     | 10/10       | 0.00           | 0/10          | 0.41초 / 0.41초        |
| jitter   | 있음 | 4.00 / 4                     | 0/10        | 1.00           | 10/10         | 3.43초 / 4.26초        |
| jitter   | 없음 | 4.00 / 4                     | 0/10        | 0.00           | 0/10          | 1.03초 / 1.20초        |
| diff     | 있음 | 4.00 / 4                     | 0/10        | -              | -             | 0.41초 / 0.41초        |
| diff     | 없음 | 4.00 / 4                     | 0/10        | -              | -             | 0.41초 / 0.41초        |

읽는 법

| 보는 것               | 의미                                                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| fixed 락 있음 vs 없음 | 없음에서 턴이 2개만 남고(유실) 모두 앞 대화를 모른다(반영률 0.00). 있음에서는 4턴, 반영률 1.00, 시간은 약 4배            |
| jitter 락 없음        | 턴은 4개 모두 남았다(끝나는 시각이 흩어져 저장이 안 겹침). 그래도 반영률은 0.00 이다. **유실이 없어도 앞 대화는 모른다** |
| diff 락 있음 vs 없음  | 시간이 같다(한 건 시간). 락이 세션별이라 다른 세션 요청을 늦추지 않는다                                                  |

판정은 락 있음에만 한다(유실 0, 반영률 1.00, 완벽한 라운드 전부, diff 가 오래 걸리지 않음). 락 없음은 정보용이다.

### ② 동시 요청 수를 늘리면 (inproc)

**목적:** N 을 키우면 락 없음의 유실과 락 있음의 라운드 시간이 어떻게 변하는지 본다.

```bash
python -m app.experiments.race_test --n 6 --rounds 10
python -m app.experiments.race_test --n 8 --rounds 10 --scenarios fixed,jitter
```

확인할 것

| 보는 곳               | 기대(예상, 샌드박스에서 N=6 은 아직 보지 않았다)                                            |
| --------------------- | ------------------------------------------------------------------------------------------- |
| 락 있음의 라운드 시간 | 같은 세션 N 개가 차례로 처리되므로 약 N × 0.4초(fixed), 평균 N × 0.75초(jitter) 로 길어진다 |
| 락 있음의 저장된 턴   | 항상 N (판정)                                                                               |
| 락 없음의 저장된 턴   | fixed 에서는 N 보다 크게 줄어든다. jitter 에서는 N 근처                                     |

`--n` 은 2~10 이다. 대화는 최근 10턴만 저장하므로 그 이상은 턴 수를 해석할 수 없다.

### ③ 락 있음, 실제 서버와 Gemini (http)

**목적:** 실제 워커 2대와 실제 Gemini 에서 같은 세션 요청을 라운드마다 새 세션으로 반복해서, 락 있음의 라운드 시간과 유실을 본다.

터미널을 3개 쓴다(가상환경을 켠 상태, Kafka·Qdrant·Redis 컨테이너가 떠 있어야 한다). 워커는 락 환경변수 없이 띄운다(락 기본 켜짐).

```bash
# 터미널 1: 8000 = 워커 1
cd d2-ai-python
export KAFKA_WORKER_ID=w1
uvicorn app.main:app --port 8000

# 터미널 2: 8001 = 워커 2
cd d2-ai-python
export KAFKA_WORKER_ID=w2
uvicorn app.main:app --port 8001

# 터미널 3: 프로젝트 루트(ai-agent-serving-infra)에서 시작. 워커 둘이 뜬 것을 확인
curl -s localhost:8000/health
curl -s localhost:8001/health

# 테스트 실행
cd d2-ai-python
python -m app.experiments.race_test --mode http --rounds 3 --label lock-on

# Claude 로 돌릴 때는 락을 끈 워커 그대로 `--provider claude` 를 붙인다.
python -m app.experiments.race_test --mode http --rounds 3 --provider claude --label lock-on-claude
```

한 라운드마다 모델 호출 2번이 일어난다(5라운드 = 호출 10번). 서버를 2대가 아니라 다른 개수로 띄웠다면 `--urls` 를 바꾼다.

예상 시간: 한 라운드 약 15~40초, 5라운드 약 2~3분. 요청 한 건의 시간(7~20초) 두 개를 합친 값이다. 락이 있어서 같은 세션 두 요청이 차례로 처리되므로 두 건의 합이 한 라운드가 된다.

기대(샌드박스에서 가짜 모델로 본 것, 실제 Gemini 는 미실행): 요청별 시간이 `x, x+y` 모양(먼저 끝난 요청의 시간 x, 나중 요청은 기다린 x 에 자기 처리 시간 y 가 더해짐), 저장된 턴 2, 유실 0개. 두 워커 터미널의 로그에서 `이전 대화 0개` 와 `이전 대화 2개` 가 한 번씩 나온다.

### ④ 락 없음, 실제 서버와 Gemini (http)

**목적:** ③ 과 같은 조건에서 락만 끄고 같은 횟수를 돌려 비교한다.

③ 의 워커 두 대를 Ctrl+C 로 끄고, 이번에는 **락을 끄고** 다시 띄운다(두 워커 모두). 터미널 1, 2 에서 `export` 로 락 환경변수를 준 적이 있다면 먼저 `unset SESSION_LOCK_ENABLED` 한다.

```bash
# 터미널 1: 8000 = 워커 1 (락 끔)
cd d2-ai-python
export KAFKA_WORKER_ID=w1
SESSION_LOCK_ENABLED=false uvicorn app.main:app --port 8000

# 터미널 2: 8001 = 워커 2 (락 끔)
cd d2-ai-python
export KAFKA_WORKER_ID=w2
SESSION_LOCK_ENABLED=false uvicorn app.main:app --port 8001

curl -s localhost:8000/health
curl -s localhost:8001/health

# 같은 횟수로 테스트 실행
cd d2-ai-python
python -m app.experiments.race_test --mode http --rounds 3 --label lock-off

# Claude 로 돌릴 때는 락을 끈 워커 그대로 `--provider claude` 를 붙인다.

```

| 확인하지 않음                          | N≥6 의 결과, 서로 다른 세션의 http 동시 요청, Kafka 경로(Spring → Kafka → 워커)에서의 동시 요청                                                                                       |

## 7. 한계

| 항목                  | 내용                                                                                                                                                      |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 가짜 모델의 시간 분포 | fixed 는 모두 같은 시각에 끝나 유실이 과장되고, jitter 의 0.3~1.2초 균등분포는 실제 Gemini(4~80초까지 관찰됨)와 다르다. 두 시나리오는 양 끝을 보는 것이다 |
| 스레드 스케줄링       | inproc 의 동시 시작은 `Barrier` 로 맞추지만 실제 도착 순서는 매번 다르다. 락 없음의 숫자가 라운드마다, 실행마다 달라지는 이유다                           |
| http 의 실제 동시성   | 워커 한 대는 한 번에 한 요청만 처리하므로 실제 동시 처리 수는 워커 수다. N 을 워커 수보다 크게 하면 락 없음이어도 일부는 차례로 처리된다                  |
| Kafka 경로 아님       | http 방식은 FastAPI 의 직접 경로(`/api/v1/agent/run`)다. Spring → Kafka → 워커 경로에서는 파티션 배정, 한 워커의 메시지 순차 처리 때문에 동시성이 다르다  |
| 비용                  | http 방식은 라운드마다 실제 모델 호출 N 번이 든다                                                                                                         |
