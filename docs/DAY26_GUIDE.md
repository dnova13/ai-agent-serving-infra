# Day 26 가이드 — 동기 구조로 전환하고 장애(504, 에러율) 재현

> 상태: 코드와 k6 스크립트 작성 완료, **실험은 ①~⑥ 을 모두 실행했다**(DAY26_RESULT 3-1~3-6). ② 는 5건이 5초 간격이 아니라 묶음으로 끝나(1차: 25초에 5건, 2차: 11초 2건 + 26초 3건) 예상과 달랐다. 아래 기대값은 모두 "확인 전 예상"이다. Spring 코드는 이 환경에서 빌드하지 못했지만(gradle, maven 저장소에 접속 불가), 내 환경에서 기동되어 ① 이 통과했다. `ramping.js` 의 문법은 `node --check` 로만 확인했고 `k6 run` 으로는 돌려 보지 않았다.
> 포트: **8080 = Spring WAS**, **8000 = FastAPI 워커 1**, **8001 = FastAPI 워커 2**, **6379 = Redis(redis1 컨테이너)**, 9092 = Kafka, 6333 = Qdrant.
> 코드 흐름은 [DAY26_CODE_GUIDE.md](DAY26_CODE_GUIDE.md). 기준선(비동기)은 [DAY25_RESULT.md](DAY25_RESULT.md).

**전체 목적:** Day 25 에서 비동기 구조는 접수가 15ms 안팎으로 빠르다는 것을 확인했다. 오늘은 같은 부하를 "답이 나올 때까지 요청을 붙잡고 있는" 동기 구조로 보내서, 비동기로 바꾼 이유가 되는 장애(응답 지연, 504, 에러율 상승)를 직접 재현한다. 결과는 Day 27 에서 비동기를 되돌린 뒤 같은 조건으로 비교한다.

## 1. 오늘 목표

| 확인할 것                                                                                                                    | 실험 |
| ---------------------------------------------------------------------------------------------------------------------------- | ---- |
| 동기 경로(Spring → FastAPI) 한 건이 약 5초 뒤 200 으로 온다                                                                  | ①    |
| 동시에 5건을 보내면 한 건씩 차례로 끝난다 (FastAPI 가 동시에 한 건만 처리)                                                   | ②    |
| 처리 중인 동안 `/health` 도 응답이 밀린다                                                                                    | ③    |
| VU 20 으로 올리면 일부가 30초를 넘겨 504 가 된다                                                                             | ④    |
| Spring 을 빼고 FastAPI 를 직접 부르면 504 는 없고 k6 시간 초과만 나온다 (원인이 Spring 이 아니라 FastAPI 처리 방식임을 확인) | ⑤    |
| 시험이 끝난 뒤에도 FastAPI 가 포기된 요청을 계속 처리한다                                                                    | ⑥    |

## 2. 개념

| 항목               | 내용                                                                                                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 동기 구조          | `POST /api/v1/agent/run`(FastAPI)은 `async def` 안에서 막히는 함수 `run_agent` 를 그대로 호출한다. 실행 중에는 이벤트 루프가 멈춰서 같은 워커가 다른 요청을 받지 못한다(`/health` 포함). 한 번에 한 건씩만 처리된다 |
| 504                | 오늘 추가한 `POST /api/agent/sync`(Spring)가 FastAPI 를 호출해 `app.sync.timeout-ms`(기본 30000)를 넘기면 포기하고 504 를 돌려준다. 접속 자체가 안 되면 502                                                         |
| 포기와 처리의 분리 | Spring 이 504 를 주고 연결을 끊어도 FastAPI 가 이미 돌고 있는 `run_agent` 는 멈추지 않는다. 그래서 클라이언트는 실패인데 서버는 계속 일하는 낭비가 생긴다 (⑥ 에서 본다)                                             |
| k6 시간 제한       | 동기 모드의 k6 요청 시간 제한은 `POLL_MAX_SEC`(기본 60초)다. Spring 의 30초보다 길어야 k6 가 Spring 의 504 를 받는다                                                                                                |
| 처리량 계산        | 가짜 LLM 5초(±20%)로 한 건씩이면 FastAPI 처리량은 초당 약 0.2건. VU 20 이고 쉬는 시간 1초면 요청이 초당 20건 가까이 들어오려 하지만, 실제로는 대부분 기다린다                                                       |

## 3. 바뀐 것

| 파일                                                       | 바뀐 것                                                                                                                |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `d3-was-spring/.../was/sync/SyncAgentClient.java`          | 새 파일. FastAPI `/api/v1/agent/run` 을 호출하고 시간 초과는 504, 접속 실패는 502 로 바꾼다                            |
| `d3-was-spring/.../was/sync/SyncAgentController.java`      | 새 파일. `POST /api/agent/sync`. 본문은 기존 접수 API 와 같은 `{question, provider}`                                   |
| `d3-was-spring/.../was/messaging/AgentRequestMessage.java` | `quote` 를 public 으로 열었다 (JSON 문자열 만들기 재사용). 기존 코드는 `[OLD]` 주석으로 남겼다                         |
| `d3-was-spring/src/main/resources/application.properties`  | `app.sync.fastapi-url`, `app.sync.timeout-ms`, `app.sync.connect-timeout-ms` 추가                                      |
| `scripts/k6/ramping.js`                                    | `MODE=sync`(Spring 경유), `MODE=sync-direct`(FastAPI 직접) 추가. 응답 코드별 카운터 `sync_200/504/502/other_5xx/other` |

기존 비동기 경로(`POST /api/agent/requests`)는 그대로 있다.

## 4. 준비

| 순서 | 할 일                                                                                                                                                                          |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1    | Kafka 에 쌓인 요청이 없어야 한다. 워커를 끈 상태에서 `kafka-consumer-groups --describe` 로 LAG 0 확인 (Day 25 README 참고). 쌓였으면 먼저 비운다                               |
| 2    | 워커는 **8000 하나만** 띄운다. 이 워커는 Kafka 를 읽지 않게 하고 가짜 LLM 을 켠다: `KAFKA_CONSUMER_ENABLED=false FAKE_LLM_ENABLED=true FAKE_LLM_DELAY_SEC=5` (`--reload` 없이) |
| 3    | 8001 워커는 띄우지 않는다                                                                                                                                                      |
| 4    | Spring(8080)을 다시 빌드해 띄운다 (`./gradlew bootRun`). 새 클래스가 컴파일되는지가 첫 확인이다                                                                                |

2번(워커)을 한 번에 띄우는 명령. 프로젝트 루트에서 실행한다(venv 가 필요하면 먼저 활성화). 설정 3개를 같이 주고 `--reload` 는 붙이지 않는다.

```bash
KAFKA_CONSUMER_ENABLED=false FAKE_LLM_ENABLED=true FAKE_LLM_DELAY_SEC=5 uvicorn app.main:app --port 8000
```

요청 처리 시각을 로그에 붙여 보려면(선택) 끝에 파이프를 붙인다. 이때 `PYTHONUNBUFFERED=1` 이 있어야 줄이 바로 나온다.

```bash
KAFKA_CONSUMER_ENABLED=false FAKE_LLM_ENABLED=true FAKE_LLM_DELAY_SEC=5 PYTHONUNBUFFERED=1 \
  uvicorn app.main:app --port 8000 2>&1 | while IFS= read -r l; do echo "$(date +%T.%N | cut -c1-12) $l"; done
```

## 5. 실행과 확인

각 실험은 앞 실험의 요청이 모두 끝난 뒤(약 30초 기다린 뒤) 시작한다. 이전 요청이 FastAPI 에 남아 있으면 숫자가 섞인다.

### ① 동기 경로 한 건

**목적:** Spring 의 `/api/agent/sync` 가 FastAPI 답을 그대로 돌려주는지 본다.

```bash
curl -s -o /dev/null -w "status=%{http_code} time=%{time_total}s\n" -X POST http://localhost:8080/api/agent/sync \
  -H 'Content-Type: application/json' -d '{"question":"환불은 며칠 안에?","provider":"fake"}'
```

| 항목   | 기대값 (확인 전 예상) |
| ------ | --------------------- |
| status | 200                   |
| time   | 약 4~6초              |

### ② 동시 5건

**목적:** FastAPI 가 동시에 한 건씩만 처리하는지 본다.

```bash
for i in 1 2 3 4 5; do
  curl -s -o /dev/null -w "$i: status=%{http_code} time=%{time_total}s\n" -X POST http://localhost:8080/api/agent/sync \
    -H 'Content-Type: application/json' -d '{"question":"환불은 며칠 안에?","provider":"fake"}' &
done; wait
```

| 항목   | 기대값 (확인 전 예상)                                            |
| ------ | ---------------------------------------------------------------- |
| status | 모두 200                                                         |
| time   | 약 5, 10, 15, 20, 25초로 벌어진다 (순서는 요청마다 다를 수 있음) |

### ③ 처리 중 `/health`

**목적:** 이벤트 루프가 막히는지 본다.

동기 요청을 백그라운드로 보내고, 1초 뒤 `/health` 를 호출한다. 한 터미널에서 한 번에 실행한다(터미널 두 개로 타이밍을 맞추면 요청이 이미 끝난 뒤에 보내는 실수가 생긴다).

```bash
curl -s -o /dev/null -w "sync status=%{http_code} time=%{time_total}s\n" -X POST http://localhost:8080/api/agent/sync \
  -H 'Content-Type: application/json' -d '{"question":"환불은 며칠 안에?","provider":"fake"}' &
sleep 1
curl -s -o /dev/null -w "health status=%{http_code} time=%{time_total}s\n" http://localhost:8000/health
wait
```

| 항목 | 기대값 (확인 전 예상)                                        |
| ---- | ------------------------------------------------------------ |
| health time | 처리가 끝날 때까지 기다렸다가 답하므로 수 초(남은 처리 시간, 약 3~5초). sync 응답과 거의 같은 시각에 나온다 |

### ④ k6 VU 20, 동기 (Spring 경유)

**목적:** 요청이 몰렸을 때 504 와 에러율이 나오는지 본다.

```bash
k6 run -e MODE=sync -e MAX_VUS=20 scripts/k6/ramping.js
```

| 항목                            | 기대값 (확인 전 예상)                             |
| ------------------------------- | ------------------------------------------------- |
| `sync_200`                      | 전체 70초 동안 처리량 한계(약 0.2건/초)로 십여 건 |
| `sync_504`                      | 다수. 30초 넘게 기다린 요청은 모두 504            |
| `sync_502`, `sync_other_5xx`    | 0                                                 |
| `accepted`                      | 50% 미만 (임계값 `rate>0.99` 실패 표시)           |
| `http_req_duration` (POST sync) | p95 가 30초 부근 (504 가 30초에 끊기므로)         |
| `http_req_failed`               | 504 비율만큼 높음                                 |

### ⑤ k6 VU 20, 동기 (FastAPI 직접)

**목적:** 같은 부하를 Spring 없이 보내 병목이 FastAPI 처리 방식에 있음을 확인한다. 시작 전 ④ 의 포기된 요청이 끝나도록 충분히(약 2분) 기다린다.

```bash
k6 run -e MODE=sync-direct -e MAX_VUS=20 scripts/k6/ramping.js
```

| 항목       | 기대값 (확인 전 예상)                                                                                  |
| ---------- | ------------------------------------------------------------------------------------------------------ |
| `sync_504` | 0 (Spring 이 없으므로)                                                                                 |
| 응답 지연  | 요청이 FastAPI 에 줄을 서므로 ④ 보다 오래 걸린다. 60초 안에 못 끝난 요청은 k6 시간 초과로 `sync_other` |
| 처리 건수  | ④ 와 비슷(처리량은 같은 한계)                                                                          |

### ⑥ 시험 뒤 남은 처리

**목적:** 클라이언트가 포기한 요청을 서버가 계속 처리하는지 본다. ④ 직후 바로 확인한다.

```bash
curl -s -o /dev/null -w "health time=%{time_total}s\n" http://localhost:8000/health
```

| 항목 | 기대값 (확인 전 예상)                                                                                           |
| ---- | --------------------------------------------------------------------------------------------------------------- |
| time | k6 가 끝난 직후에도 수 초 이상 걸린다 (포기된 요청이 FastAPI 에 남아 있으므로). 시간이 지나면 0.0x초로 돌아온다 |
