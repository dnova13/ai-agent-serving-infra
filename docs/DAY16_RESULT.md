# Day 16 결과 — Consumer 와 에이전트 연결, commit 시점

> 구현과 실행 방법은 [DAY16_GUIDE.md](DAY16_GUIDE.md). 이 문서는 실행 결과와 해석을 담고, 실행하며 나온 의문에 대한 설명은 해당 실험 안에 풀어 적었다.
> 상태: 완료(2026-10-12). 선택 실험 중 ⑧, ⑨ 는 하지 않았고, 확인하지 않은 항목은 6번에 적었다.

**목적:** Day 15 에서 로그만 남기던 Kafka 워커(FastAPI 8000)에 에이전트(`run_agent`)를 연결하고, Day 13 부터 미뤄 둔 결정인 "언제 commit 할 것인가"를 실험으로 확인한다. 에이전트 처리는 7초 정도 걸려서 처리 도중 서버가 죽을 수 있고, 그때 요청이 유실되는지 중복되는지는 commit 시점이 정한다. 그래서 수동 commit(처리 후)과 자동 commit 을 같은 상황에서 비교해 어느 쪽을 쓸지 근거를 남긴다.

```
[Spring WAS :8080] -> [Kafka agent.requests] -> [FastAPI :8000 의 워커] -> run_agent() -> (답) 로그
                                                  └ 처리가 끝난 뒤에 commit
```

결과(답)는 아직 저장하지 않고 로그로만 남긴다. 저장과 조회는 Redis 를 붙이는 4주차다.

## 3. 확인된 결과

### 3-1. 요청 접수와 에이전트 연결

**목적:** Spring(8080)이 요청을 접수해 Kafka 에 넣으면, FastAPI(8000)의 워커가 그 메시지를 받아 실제 에이전트(`run_agent`)를 호출해 답을 만드는 전체 연결이 되는지 확인한다.

Postman 으로 Spring(8080)에 두 요청을 보냈고 둘 다 접수됐다.

| 요청                     | 응답                 | requestId      |
| ------------------------ | -------------------- | -------------- |
| 정상 질문, `gemini`      | `202 Accepted`, 68ms | `2e30f45a-...` |
| `실패 테스트`, `invalid` | `202 Accepted`, 44ms | `bc887ea3-...` |

`invalid` 요청도 202 인 것은 정상이다. Spring 은 `provider` 값을 검증하지 않고 Kafka 에 넣기만 하므로, 지원하지 않는 값이라는 오류는 Kafka 를 거쳐 FastAPI(8000)가 에이전트를 부를 때 난다.

정상 요청이 에이전트까지 간 것은 3-3 의 로그에서 확인된다. `requestId=b124747b-...` 가 `[agent] 시작` 이후 약 7.6초 만에 답을 냈다. 이 처리 시간(7.6초)이 Spring 의 202 응답(수십 ms)과 분리되어 있다는 점이 이 프로젝트의 비동기 구조의 핵심이다. 한 번 잰 값이다.

### 3-2. 에이전트가 실패했을 때

**목적:** 에이전트 호출이 실패해도 워커가 죽지 않고 다음 요청을 계속 처리하는지, 실패가 `/health` 의 `failed` 로 세어지는지 확인한다. 실패한 메시지 한 건이 뒤의 요청을 막는 문제(poison message)를 피하려는 설계를 검증하는 것이다.

`provider=invalid` 요청에 대해 FastAPI(8000) 로그는 다음과 같았다.

```
[agent] 시작 requestId=bc887ea3-... partition=0 offset=46 provider=invalid
처리 실패, 건너뜀 requestId=bc887ea3-... partition=0 offset=46
...
ValueError: 지원하지 않는 provider입니다: invalid
```

에이전트의 `get_model()` 이 던진 예외를 워커가 잡고 이 메시지를 건너뛰었다. 긴 트레이스백이 나오는 것은 원인을 남기려고 `logger.exception` 을 쓰기 때문이다. 트레이스백에 `asyncio/threads.py`, `concurrent/futures/thread.py` 가 보이는데, 에이전트(`run_agent`)가 이벤트 루프가 아니라 별도 스레드에서 실행됐다는 흔적이다.

이어서 확인한 `/health`(FastAPI 8000, Spring 8080 에는 `/health` 가 없다):

```
{"status":"ok","kafka_consumer":{"state":"running","topic":"agent.requests","group":"agent-workers","received":2,"skipped":0,"failed":1,"committed":3,"commit_mode":"manual","current_request_id":null,"last_error":null}}
```

| 필드                 | 값        | 의미                                                                                                                  |
| -------------------- | --------- | --------------------------------------------------------------------------------------------------------------------- |
| `status`             | `ok`      | 서버 자체가 살아 있으면 항상 `ok`. Kafka 가 꺼져 있어도 `ok` 이므로, Kafka 상태는 `kafka_consumer.state` 로 봐야 한다 |
| `state`              | `running` | 실패 뒤에도 워커가 계속 동작 (`connecting`, `running`, `error`, `stopped` 중 하나)                                    |
| `received`           | 2         | 에이전트까지 성공한 요청. 서버를 다시 켜면 0 부터 다시 센다                                                           |
| `skipped`            | 0         | 메시지 모양이 잘못돼 건너뛴 건수                                                                                      |
| `failed`             | 1         | 에이전트가 실패해 건너뛴 요청(`invalid`)                                                                              |
| `committed`          | 3         | 수동 commit 횟수. 성공 2 + 실패 1 과 같다. **실패한 메시지도 commit 하고 넘어갔다**                                   |
| `commit_mode`        | `manual`  | 처리 후 commit 모드                                                                                                   |
| `current_request_id` | `null`    | 지금 처리 중인 요청의 id. 처리 중이 아니면 `null`                                                                     |
| `last_error`         | `null`    | 마지막 Kafka 접속 오류 사유                                                                                           |

실패한 메시지도 commit 하는 것은 의도한 설계다. commit 하지 않고 계속 재시도하면 그 메시지 하나가 풀리지 않을 때 뒤의 요청이 모두 막힌다. 대신 실패한 요청은 지금은 `failed` 숫자와 로그로만 남는다(DLQ 는 Day 32).

`received` 2건 중 하나가 `2e30f45a-...` 일 것으로 보이지만, 그 요청의 `[agent] 완료` 로그는 받지 못해 확인하지 못했고 나머지 한 건이 어떤 요청인지도 모른다.

### 3-3. commit 시점: 처리 중에 서버를 끄면

**목적:** 이 실험은 "에이전트 처리가 끝난 뒤에 commit 한다"는 결정이 실제로 요청 유실을 막는지 보려는 것이다. commit 이 무엇인지는 [DAY16_GUIDE.md](DAY16_GUIDE.md) 의 "commit 은 git 커밋이 아니다" 항목에 적었다.

**수동 commit 으로 하려는 것**

에이전트 처리는 오래 걸려서(이번 7.6초) 처리 도중에 서버가 죽을 수 있다. 책갈피(commit)를 언제 꽂느냐에 따라 그때의 결과가 갈린다.

|                         | 자동 commit                                                                | 수동 commit (채택)                                                                            |
| ----------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 누가                    | Kafka 라이브러리가 알아서                                                  | 우리 코드가 직접 `consumer.commit()` 호출                                                     |
| 언제                    | 메시지를 읽은 뒤 주기적으로, 그리고 종료할 때(3-4)                         | 에이전트 처리가 끝난 직후                                                                     |
| 비유                    | 책을 펴자마자 "읽었다"고 표시                                              | 다 읽은 뒤에 "읽었다"고 표시                                                                  |
| 처리 중에 서버가 죽으면 | 읽음으로 기록돼 다시 켜도 그 요청은 오지 않는다 → 요청 유실(3-4 에서 확인) | 기록이 없어서 다시 켜면 같은 요청을 처음부터 다시 처리한다                                    |
| 대가                    | 사용자가 답을 영영 못 받을 수 있다                                         | 같은 요청이 두 번 처리될 수 있다(LLM 호출이 두 번 나갈 수 있다). 중복 걸러내기는 4주차(Redis) |

유실보다 중복이 낫다고 보고 수동 commit 을 택했다.

**실험 방법과 `AGENT_DEBUG_DELAY_SEC`**

`AGENT_DEBUG_DELAY_SEC` 는 `agent_handler.py` 에서 에이전트를 부르기 **전에** 지정한 초만큼 기다리게 하는 실험용 환경변수(기본 0)다. 에이전트 처리가 7초 정도로 짧아서 그 사이에 정확히 `Ctrl+C` 를 누르기 어려워, "처리 중, commit 전" 상태를 30초 동안 유지하려고 넣었다. 실험이 끝나면 `unset` 해야 한다(지우지 않으면 모든 요청이 30초씩 늦어진다). 대기가 에이전트 호출 **전**이라서, 이 실험은 LLM 응답을 기다리는 도중에 서버를 끄는 경우는 보여 주지 않는다(6번).

**결과 로그**

| 순서 | 로그                                                                                                                                              | 의미                                                       |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 1    | `[agent] 시작 requestId=b124747b-5143-43ce-8189-2b882980335d partition=0 offset=47 provider=gemini`                                               | 요청을 받고 처리 시작 (30초 대기 중)                       |
| 2    | `^C` → `워커 종료 received=0 skipped=0`                                                                                                           | 처리가 끝나기 전에 서버를 끔. 이 요청은 commit 되지 않았다 |
| 3    | (지연 없이 다시 기동) `[agent] 시작 requestId=b124747b-... offset=47`                                                                             | **같은 requestId, 같은 offset 47 을 다시 받음**            |
| 4    | `[agent] 완료 requestId=b124747b-... elapsed_ms=7612 answer_len=40 answer=단순 변심으로 인한 환불 시 왕복 배송비는 고객님께서 부담하셔야 합니다.` | 이번에는 끝까지 처리                                       |

처리 후 commit 이라 끝나기 전에 죽은 요청이 유실되지 않고 다시 처리됐다. 같은 요청이 두 번 시작됐지만, 이번에는 첫 번째가 대기 구간에서 끊겨 에이전트 호출은 한 번뿐이었다. 로그의 `>>> [DEBUG] after_tools_router 호출됨: ...` 는 기존 에이전트 코드에 있던 디버그 출력이다.

**순서를 그림으로**

```
정상:     ① 47 을 읽음 → ② run_agent() 처리 (약 7.6초) → ③ 답 → ④ commit (책갈피 48)

처리 중   1차: ① 47 읽음 → ② 처리 시작 → ✖ Ctrl+C (commit 못 함, 책갈피는 47 앞 그대로)
에 죽음   2차: ① 47 을 다시 읽음 → ② 처리 → ③ 답 → ④ commit (책갈피 48)
          → 유실 없음, 처리 시작은 두 번
```

자동 commit 이었다면(3-4 에서 확인):

```
① 읽음 → ② 처리 중 ✖ Ctrl+C → 종료할 때 전달된 것까지 commit (책갈피가 다음으로)
다시 켜면: 책갈피가 이미 넘어가 있음 → 그 요청은 다시 오지 않음 → 답을 못 받은 채 사라짐
```

**다시 켰을 때 어떻게 47 을 처리하게 되나**

워커가 메시지를 "감지"하는 것이 아니라, 다시 켤 때 Kafka 에 "내 그룹은 어디까지 처리했지?"를 묻고 **저장된 책갈피 위치부터** 읽는 것이다.

```
서버를 다시 켠다
  → 워커가 Kafka 에 접속하면서 그룹 agent-workers 로 가입
  → Kafka: "이 그룹의 저장된 책갈피는 47 앞이다"
  → 워커가 47 부터 읽는다 → 47 이 그대로 남아 있으므로 다시 받는다
  → 에이전트 처리 → 끝나면 commit (책갈피 48)
```

두 가지가 받쳐 준다. 첫째, 메시지는 읽어도 지워지지 않는다(Day 13). 서버가 꺼져 있는 동안에도 47번은 토픽에 남아 있다. 둘째, 책갈피는 Kafka 가 보관하고 commit 하기 전에는 옮겨지지 않는다. 서버가 꺼진 동안 새 요청(48, 49번)이 들어와도 같은 방식으로 처리될 것으로 보이지만, 이번에는 확인하지 않았다(6번).

**이 동작을 하는 코드**

`app/services/kafka_worker.py` 의 `_run()` 안이다.

```python
consumer = AIOKafkaConsumer(
    TOPIC,                                      # 구독할 토픽 (agent.requests)
    bootstrap_servers=BOOTSTRAP,                # Kafka 주소 (localhost:9092)
    group_id=GROUP,                             # 그룹 agent-workers → 이 그룹의 책갈피를 Kafka 가 기억
    auto_offset_reset=OFFSET_RESET,             # 책갈피가 없을 때만 쓰는 시작 위치 (latest)
    enable_auto_commit=(COMMIT_MODE == "auto"), # manual 이면 False → 자동으로 책갈피를 꽂지 않음
)
await consumer.start()                          # ① 접속 + 그룹 가입. 이때 Kafka 가 저장된 책갈피 위치를 알려 준다
logger.info("Kafka 접속 완료, 수신 대기")

async for record in consumer:                   # ② 책갈피 위치부터 메시지를 한 건씩 받는다. 새 메시지가 없으면 여기서 기다린다
    await self._handle(record)                  # ③ JSON 해석 → agent_handler → run_agent() (끝날 때까지 기다림)
    if COMMIT_MODE == "manual":
        await consumer.commit()                 # ④ 처리가 끝난 뒤에만 책갈피를 저장
        self.committed += 1
```

"감지"에 해당하는 것은 `async for record in consumer:` 한 줄이다. 서버를 다시 켜면 `consumer.start()` 때 Kafka 가 알려 준 책갈피 위치부터 이 루프가 시작되므로, 꺼져 있던 동안 쌓인 메시지와 처리하다 만 메시지가 먼저 나온다. `_handle()` 은 받은 값을 JSON 으로 해석해 `AgentRequestMessage` 로 만들고 `agent_handler` 를 호출하며, 실패하면 `failed` 로 세고 넘어간다. 워커를 서버와 함께 켜고 끄는 부분은 Day 15 에서 만든 `main.py` 의 `lifespan` 이다.

**commit 이 끝나기 전에는 다음 offset 으로 가지 않나**

"다음으로 가지 않는다"는 두 가지로 나뉜다.

| 구분                    | 설명                                           | 우리 코드                                                             |
| ----------------------- | ---------------------------------------------- | --------------------------------------------------------------------- |
| 저장된 책갈피           | `commit()` 을 해야만 옮겨진다                  | 처리 전에는 안 옮겨진다. 서버가 죽으면 다음에 이 위치부터 다시 읽는다 |
| 워커가 다음에 읽을 위치 | commit 과 상관없이 메시지를 읽으면 앞으로 간다 | 한 건 처리가 끝나기 전에는 다음 메시지를 읽으러 가지 않는다           |

두 번째가 그렇게 되는 것은 commit 때문이 아니라 코드가 한 건씩 순서대로 처리하게 짜여 있기 때문이다(위 코드에서 `await self._handle(record)` 가 끝나야 commit 하고 루프가 다음 메시지를 받는다). 그래서 우리 워커에서는 "47번 처리와 commit 이 끝나야 48번으로 간다"가 사실상 맞다. 여러 건을 동시에 처리하게 바꾸면(Day 18 이후) 다음 메시지를 먼저 읽을 수 있고, 그때는 어떤 위치까지 commit 해도 안전한지를 따로 따져야 한다.

### 3-4. 자동 commit 이면: 같은 상황에서 요청이 사라진다

**목적:** 3-3 에서 채택한 수동 commit 이 실제로 필요한 이유를 보여 주기 위해, 같은 상황을 자동 commit 으로 시험해 요청이 유실되는지 비교한다. `Ctrl+C`(정상 종료)와 `kill -9`(강제 종료) 두 방식에서 모두 보려는 것이다.

3-3 과 같은 상황을 `KAFKA_COMMIT_MODE=auto`, `AGENT_DEBUG_DELAY_SEC=30` 으로 세 번 시험했다. 1, 2 는 `Ctrl+C` (정상 종료), 3 은 `kill -9` (강제 종료)로 FastAPI(8000)를 껐다가 다시 켰다.

| 실험 | 순서                                                                                                                                                                                                                                                  | 결과                                                                                                                                 |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 1    | offset 48 (`1a985791-1914-4639-8676-1a23d1409925`) `[agent] 시작` → **바로** `Ctrl+C` (`워커 종료 received=0 skipped=0`) → 다시 기동                                                                                                                  | 다시 켠 뒤 처음 처리된 것은 offset 49 (`93e5189d-3d77-4061-b9ba-619f2fcb1e47`). **48 은 다시 오지 않았고 `완료` 로그도 없다 = 유실** |
| 2    | offset 55 (`cb7b6707-eca6-4a7e-957a-7fe6cebdba97`) `[agent] 시작` → Spring(8080)에 보낸 **직후** 바로 종료 (`워커 종료 received=1 skipped=0`) → 다시 기동                                                                                             | 새 요청은 offset 56 (`bf06f228-1711-4799-a47c-b384e9664aec`) 부터 시작. **55 는 다시 오지 않았다 = 유실**                            |
| 3    | offset 61 (`091cdb9f-db15-45c7-9a20-586239dc2005`) `[agent] 시작` → 사용자 말로 5초 전에 `kill -9 <부모PID> <자식PID>` (`--reload` 로 띄워서 PID 가 둘, `lsof -i :8000` 으로 확인). **`워커 종료` 로그가 찍히지 않음** → `source run.sh` 로 다시 기동 | 다시 켠 뒤 처음 시작된 것은 offset 62 (`e8d27aed-6675-4a56-b594-63b835998c08`). **61 은 다시 오지 않았다 = 유실**                    |

수동 commit(3-3)에서는 같은 상황에서 offset 47 이 다시 와서 끝까지 처리됐다. 자동 commit 에서는 48, 55, 61 이 모두 사라졌다. 3 은 `stop()` 을 거치지 않는 강제 종료였는데도 유실됐다.

**왜 사라지나: 종료 때의 commit 과 주기 commit**

자동 commit 이 읽음으로 기록하는 경로가 두 개 있고, 실험 3 이 그중 하나만으로도 유실이 난다는 것을 보여 준다. 아래 소스 내용은 작성 환경에 설치된 aiokafka 0.12.0 을 읽은 것이며 사용자 환경의 버전은 확인하지 않았다.

| 경로       | 동작                                                                                                                                                                                                 | 어떤 실험에서 보이나                                                |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 종료할 때  | `consumer.stop()` 을 하면 마지막 자동 commit(`_maybe_do_last_autocommit`)을 한 번 더 하고, **앱에 이미 전달한 메시지(`all_consumed_offsets()`)까지** 전부 commit 한다. 처리가 끝났는지는 보지 않는다 | 실험 1, 2 (`Ctrl+C` 로 `stop()` 이 실행됨, `워커 종료` 로그가 찍힘) |
| 주기적으로 | 별도 루틴이 5초(`auto_commit_interval_ms` 기본값) 간격으로 `_maybe_do_autocommit` 을 호출한다. 이 5초는 **consumer 를 시작한 때부터 흐르는 타이머**라서, 메시지를 받은 시점부터 센 5초가 아니다      | 실험 3 (`kill -9` 라 `stop()` 이 없었다)                            |

처음에는 "자동 commit 은 약 5초 간격이라서 메시지를 받고 5초가 지난 뒤에 꺼야 유실된다"고 설명했는데, 타이머가 메시지와 무관하게 흐르므로 이는 틀렸다. 메시지를 받은 뒤 1초 만에도 타이머가 울릴 수 있다. 그래서 "5초 전에 껐다"는 것만으로는 주기 commit 이 없었다고 말할 수 없다.

실험 3 은 `워커 종료` 로그가 찍히지 않았으므로 종료 때의 commit 이 아니다. 그러면 61 을 읽음으로 저장한 것은 죽기 전에 이미 한 번 울린 주기 commit 이다(소스에서 읽은 동작에 맞춘 해석이며, 실제로 commit 이 언제 일어났는지는 로그로 보지 못했다). 실험 1, 2 는 `Ctrl+C` 라서 두 경로 중 어느 쪽이 작용했는지 로그로 구분할 수 없고, 둘 다 가능하다. 어느 경로든 결과는 같다. 처리 중이던 메시지가 "읽었다"고 저장된 채 서버가 꺼진다.

죽이는 시점이 타이머의 어느 위치인지에 따라 주기 commit 이 먼저 일어날 수도, 아닐 수도 있다. 그래서 `kill -9` 에서는 유실될 때도 있고 다시 올 때도 있을 것으로 보이며, 이번에는 한 번 시험해 유실로 나왔다. 여러 번 반복해 확률을 본 것은 아니다.

| 구분           | 자동 commit                                                                   | 수동 commit (채택)                     |
| -------------- | ----------------------------------------------------------------------------- | -------------------------------------- |
| commit 되는 것 | 앱에 **전달된 것**까지 (주기적으로, 종료할 때도)                              | 처리가 **끝난 뒤** 우리가 부른 것만    |
| 종료할 때      | `stop()` 이 처리 중인 메시지도 commit 하고 끈다 (`kill -9` 는 이 단계가 없다) | 추가 commit 없음                       |
| 다시 켜면      | 책갈피가 이미 넘어가 있어 그 메시지를 읽지 않는다                             | 책갈피가 그대로라 같은 메시지를 읽는다 |

그래서 "수동은 다시 받아 처리하고, 자동은 메시지를 다시 받지 않고 offset 만 넘긴다"고 정리된다. 자동 commit 에서도 48 번 메시지 자체는 토픽에 그대로 남아 있다. 다만 `agent-workers` 그룹의 책갈피가 49 로 넘어가 있어서 이 그룹이 다시 읽지 않을 뿐이다(kafka-ui 로 다른 그룹을 만들거나 offset 을 되돌리면 읽을 수는 있지만, 이번에는 해 보지 않았다).

**자동 commit 과 관련된 코드**

`app/services/kafka_worker.py` 에서 자동 commit 과 이어지는 곳은 네 군데다.

| 위치      | 코드                                                     | 역할                                                                          |
| --------- | -------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 45행      | `COMMIT_MODE = os.getenv("KAFKA_COMMIT_MODE", "manual")` | 환경변수로 모드를 고른다. 실험 때 `export KAFKA_COMMIT_MODE=auto`             |
| 117행     | `enable_auto_commit=(COMMIT_MODE == "auto")`             | auto 이면 `True`. aiokafka 가 주기적으로, 그리고 종료할 때 알아서 commit 한다 |
| 129~130행 | `if COMMIT_MODE == "manual": await consumer.commit()`    | auto 에서는 조건이 거짓이라 **우리 코드는 commit 을 부르지 않는다**           |
| 147행     | `await consumer.stop()`                                  | 종료할 때 호출된다. auto 이면 이 안에서 aiokafka 가 마지막 commit 을 한다     |

115행에는 예전 코드 `enable_auto_commit=True` 가 `[OLD]` 주석으로 남아 있다. 유실을 일으키는 동작(`_maybe_do_last_autocommit`)은 우리 코드가 아니라 `stop()` 안의 aiokafka 라이브러리에 있다.

**실무에서의 차이**

| 구분            | 자동 commit                                | 수동 commit (처리 후)                                    |
| --------------- | ------------------------------------------ | -------------------------------------------------------- |
| 전달 보장       | at-most-once (최대 한 번, 유실될 수 있음)  | at-least-once (최소 한 번, 중복될 수 있음)               |
| 실패했을 때     | 사용자가 답을 못 받고 아무도 모른다        | 같은 요청을 다시 처리한다(LLM 호출이 두 번 나갈 수 있다) |
| 어울리는 곳     | 일부 유실돼도 되는 로그, 지표, 클릭 이벤트 | 유실되면 안 되는 주문, 결제, 에이전트 요청               |
| 이 프로젝트에서 | 사용자 질문이 사라지므로 부적합            | 채택. 중복은 requestId 로 걸러내는 쪽으로 푼다           |

수동 commit 을 쓴다고 문제가 끝나는 것은 아니다. 뒤에 숙제가 남는다.

| 숙제                       | 내용                                                                                                   | 다룰 곳       |
| -------------------------- | ------------------------------------------------------------------------------------------------------ | ------------- |
| 멱등성                     | 같은 requestId 가 두 번 와도 결과가 한 번만 반영되게 한다                                              | 4주차 (Redis) |
| 실패 정책                  | 지금은 실패한 요청도 commit 하고 건너뛴다(한 건이 파티션을 막지 않게). 보관과 재시도는 DLQ 로          | Day 32        |
| commit 비용                | 한 건마다 commit 하면 호출이 늘어난다. 처리 시간이 7초대라 지금은 무시할 수준이지만 부하 시험에서 본다 | Day 25~       |
| 리밸런싱 중 중복           | 워커가 여러 개가 되면 그룹이 재배정될 때 같은 메시지가 다시 올 수 있다                                 | Day 18 이후   |
| 수동 commit ≠ exactly-once | 정확히 한 번을 보장해 주지 않는다. 멱등성으로 같은 효과를 만든다                                       | 4주차         |

이 프로젝트가 수동 commit 을 택한 이유는 사용자의 질문이 사라지는 것보다 같은 질문이 두 번 처리되는 쪽이 고칠 수 있는 문제이기 때문이다.

### 3-5. 배선만 보기: `KAFKA_HANDLER=log`

**목적:** Spring(8080) → Kafka → FastAPI(8000) 구간이 에이전트(LLM, Qdrant) 없이도 동작하는지 확인한다. 문제가 생겼을 때 Kafka 구간의 문제인지 에이전트의 문제인지 나눠 볼 수 있고, LLM 호출 비용도 들지 않는다.

에이전트를 부르지 않고 Kafka 구간만 확인하는 모드다. `export KAFKA_HANDLER=log` 로 FastAPI(8000)를 기동하고 Spring(8080)으로 요청 1건을 보냈다.

| 확인한 것           | 값                                                                                                                                                                                           |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FastAPI(8000) 로그  | `[recv] partition=0 offset=64 requestId=4340c7d3-100d-43b5-8d9c-8c7e6b81358e provider=gemini createdAt=2026-10-12T01:38:59.899530+00:00 question=단순 변심으로 환불하면 배송비는 누가 내요?` |
| `[agent] 시작` 로그 | 없음. 에이전트가 호출되지 않았다                                                                                                                                                             |
| `/health`           | `state running`, `received 1`, `skipped 0`, `failed 0`, `committed 0`, `commit_mode auto`, `current_request_id null`, `last_error null`                                                      |

요청의 requestId, provider, question 이 FastAPI 에서 그대로 해석되어 Spring → Kafka → FastAPI 구간이 에이전트 없이 동작함을 확인했다. `createdAt` 은 UTC 표기이고 한국시간으로 10:38:59 이다.

이 실행에서는 3-4 실험의 `KAFKA_COMMIT_MODE=auto` 가 풀리지 않은 채였다(`/health` 의 `commit_mode auto`). 그래서 `committed 0` 은 자동 commit 에서는 우리 코드가 commit 을 세지 않기 때문이다. 수동 모드에서 `log` 핸들러일 때 `committed` 가 오르는지는 확인하지 않았다(6번).

### 3-6. 처리 중에 `/health` 가 응답하는가

**목적:** 에이전트를 별도 스레드(`asyncio.to_thread`)로 돌린 설계가 실제로 FastAPI(8000)의 이벤트 루프를 막지 않는지 확인한다. 막힌다면 처리하는 약 7초 동안 `/health` 응답이 끊긴다.

기본 모드(`commit_mode manual`)로 서버를 새로 켜고, Spring(8080)에 정상 요청을 보낸 직후 `for i in $(seq 1 8); do curl -s localhost:8000/health; echo; sleep 1; done` 을 실행했다.

| 확인한 것                             | 값                                                                    |
| ------------------------------------- | --------------------------------------------------------------------- |
| 응답 횟수                             | 8번 모두 응답 (`status ok`, `state running`). 끊기거나 멈춘 줄 없음   |
| `current_request_id`                  | 8번 모두 `99c21aee-edb1-4b06-ae82-c4f46c7f0d3c` (처리 중인 요청의 id) |
| `received`, `committed`               | 8번 모두 `0`, `0` (처리가 끝나기 전의 값)                             |
| `commit_mode`, `failed`, `last_error` | `manual`, `0`, `null`                                                 |

에이전트가 처리하는 동안에도 FastAPI(8000)가 `/health` 에 응답했고 `current_request_id` 에 처리 중인 요청이 보였다. 에이전트를 별도 스레드로 돌린 구조가 이벤트 루프를 막지 않는다는 근거다.

이 캡처는 8초 동안 처리가 계속된 구간까지만 담고 있다. 처리가 끝난 뒤 `current_request_id` 가 `null` 로 돌아가고 `received`, `committed` 가 1 오르는지는 이 출력에서 확인하지 못했다(6번).

## 5. 해석

| 확인한 것                                                                    | 의미                                                                                                                         |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 처리 중에 끈 요청이 재시작 후 같은 offset 으로 다시 옴                       | 처리 후 수동 commit 으로 요청 유실을 막는다. 대가로 같은 요청이 두 번 시작될 수 있다                                         |
| 실패한 요청도 commit 하고 넘어감(`committed 3 = received 2 + failed 1`)      | 실패 한 건이 뒤의 요청을 막지 않는다. 대신 실패한 요청은 지금은 로그에만 남는다                                              |

| 정상 요청의 에이전트 처리 시간 7.6초                                         | Spring 의 202 응답(수십 ms)과 분리되어 있다. 부하 시험(Day 25~)의 기준이 될 값이다. 한 번 잰 값이고, Day 17 에서 같은 서버로 다시 재니 22~29초였다(DAY17_RESULT 3번)                               |

## 6. 확인하지 않은 것

아래는 모두 선택 항목이라 하지 않아도 Day 16 은 완료다. 방법은 가이드의 ⑥~⑩ 단계에 있다. 이번에는 ⑧, ⑨ 를 하지 않고 끝냈다(⑤ 와 ⑩ 의 자동 commit 부분은 3-4, ⑥ 은 3-5, ⑦ 은 3-6 에서 했다).

| 항목                                                        | 내용                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 자동 commit 실험 (가이드 ⑤, ⑩)                              | `kill -9` 는 1번만 시험했고(유실) 몇 초 뒤에 죽였는지는 사용자 말("5초 전")뿐이다. 수동 commit 에서의 `kill -9` 는 시험하지 않았다. 93e5189d, bf06f228, e8d27aed 가 재시작 뒤에 새로 보낸 요청인지(그렇게 보임), 실험 2 의 `received=1` 이 어느 요청인지는 기록하지 못했다. aiokafka 소스는 작성 환경의 0.12.0 을 읽은 것이다 |
| `KAFKA_HANDLER=log` 모드 (가이드 ⑥)                         | 3-5 에서 했다. 다만 `KAFKA_COMMIT_MODE=auto` 가 남은 상태였고, 수동 모드에서 `committed` 가 오르는지는 확인하지 않았다                                                                                                                                                                                                        |
| 처리 중 `/health` 응답 (가이드 ⑦)                           | 3-6 에서 처리 중 응답과 `current_request_id` 는 확인했다. 처리가 끝난 뒤 `null` 복귀와 `received`, `committed` 증가는 확인하지 않았다                                                                                                                                                                                         |
| 에이전트 호출 도중에 서버를 끄는 경우 (가이드 ⑧, 하지 않음) | 이번 실험은 호출 전 대기 구간에서 끈 것이다. LLM 응답을 기다리는 중에 `Ctrl+C` 하면 종료가 바로 되는지 확인하지 않았다                                                                                                                                                                                                        |
| 서버가 꺼진 동안 쌓인 요청 (가이드 ⑨, 하지 않음)            | 순서대로 처리되는지 확인하지 않았다                                                                                                                                                                                                                                                                                           |
| 재시작 후 `/health` 의 `committed`                          | 재시작 후 commit 이 실제로 한 번 일어났는지를 숫자로 보지 못했다                                                                                                                                                                                                                                                              |
| 정상 요청 `2e30f45a-...` 의 결과                            | `[agent] 완료` 로그를 받지 못했다                                                                                                                                                                                                                                                                                             |
| `/health` 의 `received` 2건                                 | 어떤 요청인지 확인하지 못했다                                                                                                                                                                                                                                                                                                 |
| kafka-ui(8090)의 그룹 Lag                                   | 서버가 꺼진 동안 Lag 이 1 이었는지 확인하지 않았다                                                                                                                                                                                                                                                                            |
