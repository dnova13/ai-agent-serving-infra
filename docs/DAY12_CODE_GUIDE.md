> 파일 경로는 프로젝트 루트(`ai-agent-serving-infra/`) 기준이다. 코드가 길어서 줄 번호는 적지 않았다. 함수 이름으로 찾는다.
> 포트: **6333 = Qdrant**. 서버(8000, 8080)는 쓰지 않고 `python -m app.experiments.chunk_experiment` 로 직접 실행한다. Gemini 임베딩 API 를 호출한다.
> 상태: 나중에 코드를 읽고 정리한 문서다. 이 문서를 쓰면서 코드를 실행해 확인한 것은 없다. 설명한 코드는 Day 12 커밋(`7a3f7a1`) 시점의 것이다.

**전체 목적:** 문서를 자르는 방식만 바꾸고 나머지(문서, 질문, 임베딩 모델, Qdrant 설정)는 고정한 채 top-1 / top-3 적중을 재는 실험이 코드에서 어떻게 만들어지는지, 그리고 무료 임베딩 한도(분당 100건)를 어떻게 피하는지 따라간다.


## 1. 전체 흐름

```
main()
 ① build_chunks(args)      전략 4개로 같은 문서 4개를 자름 → {전략: [(문서ID, 청크번호, 텍스트)]}
 ② ingest(client, 전략, 청크)  전략마다 별도 컬렉션 chunk-exp-<전략> 을 새로 만들어 청크를 임베딩해 upsert
 ③ 질문 12개를 한 번씩만 임베딩 (모든 전략이 같은 질문 벡터를 쓴다)
 ④ search_chunks(...)      컬렉션마다 top-3 검색
 ⑤ hit_rank(hits, must)    must 문자열이 모두 든 청크가 몇 등인지 → 1, 2, 3 또는 None
 ⑥ 전략별 요약 표 + 질문별 순위 표 출력, 끝나면 컬렉션 삭제(--keep 이면 남김)
```

## 2. 주요 코드

### 2-1. 통제 실험이 되는 장치

| 고정한 것                  | 코드에서 보장하는 방법                                                                                                           |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 같은 문서                  | `build_chunks` 가 모든 전략에 같은 `LONG_DOCS` 를 쓴다                                                                            |
| 같은 질문 벡터             | 질문을 한 번만 임베딩해 모든 컬렉션 검색에 재사용한다(`_query_cache` 도 있다)                                                      |
| 서로 섞이지 않음           | 전략마다 컬렉션 이름이 다르다(`PREFIX = "chunk-exp-"` + 전략). 기존 `documents-12` 와도 안 섞인다                                    |
| 같은 Qdrant 설정           | 컬렉션을 만들 때 차원 768, COSINE 으로 동일하게 만든다(Day 7 의 `qdrant_setup` 와 같은 설정)                                      |

바뀌는 값은 청킹 전략 하나이고 옵션(`--size`, `--overlap`, `--max-chars`, `--sem-max`, `--k`)은 그 전략의 세부값이다.

### 2-2. 네 가지 자르기

| 함수                                     | 입력         | 핵심 동작                                                                                         |
| ---------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------- |
| `chunk_fixed(text, size=150, overlap=30)`| 문서 1개     | 글자 수로 자르고 다음 조각은 앞 조각과 30자 겹친다                                                |
| `chunk_sentence(text, max_chars=150)`    | 문서 1개     | `split_sentences` 로 나눈 문장을 이어 붙이다가 150자를 넘기면 새 청크                              |
| `chunk_paragraph(text)`                  | 문서 1개     | 빈 줄(`\n\n`)로 나눔                                                                              |
| `chunk_semantic(texts, max_chars=300, k=0.5)` | **문서 리스트 전체** | 문장을 임베딩하고, 인접 문장의 코사인 유사도(`_cosine`)가 떨어지는 곳에서 자름. 결과는 `{문서 번호: [청크]}` |

`semantic` 만 입력이 문서 리스트인 이유는 문장 임베딩 호출을 묶으려는 것이다(코드 주석). 이 전략만 청킹 단계에서 API 를 부른다.

### 2-3. 판정 (`hit_rank`)

```python
for rank, h in enumerate(hits, 1):
    if all(m in h["text"] for m in must):
        return rank
return None
```

정답 근거 문자열(`must`)이 **모두 한 청크 안에** 있어야 성공이다. 근거 두 개가 청크 경계에서 갈라지면 실패로 센다. 경계 문제를 드러내려는 평가 방식이라고 코드 주석에 적혀 있다. 순위가 1이면 top-1 성공, 3 이하이면 top-3 성공이므로 항상 top-3 ≥ top-1 이다.

### 2-4. 임베딩 한도 보호

| 장치                    | 설명                                                                                                                                     |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 슬라이딩 윈도우 `_sent` | 텍스트를 1건 보낼 때마다 시각을 쌓고 60초 지난 것은 지운다. `len(_sent)` 가 최근 60초 동안 보낸 건수다                                    |
| `QUOTA_PER_MIN = 90`    | 무료 한도 100 에서 여유를 둔 값. 가까워지면 `_wait_for_quota` 가 기다린다                                                                  |
| `BATCH = 20`            | 한 번에 20건씩 보낸다                                                                                                                    |
| `_call_with_retry`      | 그래도 429 가 나오면 안내된 시간만큼 쉬고 다시 시도한다                                                                                    |
| 캐시                    | 같은 텍스트는 API 를 다시 부르지 않는다. 문서용과 질문용은 `task_type` 이 달라 벡터가 달라서 캐시를 둘(`_doc_cache`, `_query_cache`)로 나눴다 |

이 장치는 실험 첫 실행에서 합계 약 130건을 한꺼번에 보내 429(RESOURCE_EXHAUSTED)가 난 뒤에 넣은 것이라고 코드 주석에 적혀 있다.

### 2-5. 실행 옵션 (`main`)

| 옵션                         | 용도                                                       |
| ---------------------------- | ---------------------------------------------------------- |
| `--size`, `--overlap`        | fixed 의 청크 크기와 겹침                                  |
| `--max-chars`                | sentence 의 청크 최대 글자 수                              |
| `--sem-max`, `--k`           | semantic 의 최대 글자 수와 분할 민감도(작을수록 많이 자름) |
| `--keep`                     | 실험 컬렉션을 지우지 않음                                  |
| `--show`                     | 잘린 청크를 출력하고 실험은 계속                           |
| `--chunks-only`              | 청크만 출력하고 종료(Qdrant 저장과 검색 없음)              |


## 3. 결과를 읽는 순서

1. 전략별 요약 표에서 청크 수, 평균 길이, top-1 / top-3 을 본다.
2. 질문별 순위 표에서 `X`(top-3 안에 없음)가 어느 질문, 어느 전략에 나왔는지 본다.
3. `--chunks-only` 또는 `--show` 로 실제 경계를 보고, 근거가 두 청크로 갈라졌는지 확인한다.
4. 정확도가 같으면 "성공 시 top-1 길이"를 본다. 짧을수록 모델에 넘기는 문맥이 적다.

기록된 숫자는 DAY12_RESULT 에 있다(기본 옵션: fixed 9/10, sentence 11/11, paragraph 12/12, semantic 12/12 의 top-1/top-3).
