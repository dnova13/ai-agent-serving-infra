# Day 28 코드 설명 — breakpoint.js, run-breakpoint.sh, resource-sampler.sh

> 이 문서는 Day 28 에서 새로 만든 스크립트가 하는 일을 설명한다. 기존 서버 코드와 `ramping.js` 는 바꾸지 않았다.
> 포트: **8080 = Spring WAS**, **8000 = FastAPI 워커 1**, 9092 = Kafka.

**전체 목적:** 부하를 계단식으로 올리며 계단별 접수 응답 시간과 성공 비율을 따로 재고, 자원 사용량을 함께 기록해 Breakpoint 와 그 원인 후보를 찾는다.


## 1. 한눈에 보기

| 파일                             | 하는 일                                                                                       |
| -------------------------------- | --------------------------------------------------------------------------------------------- |
| `scripts/k6/breakpoint.js`       | VU 를 계단식으로 올리며 `POST /api/agent/requests`(8080)를 보내고, 계단별 지표와 기준을 만든다 |
| `scripts/k6/run-breakpoint.sh`   | 파일 한도 올리기 → 샘플러 실행 → k6 실행 → 샘플러 종료, 결과를 `scripts/k6/out/` 에 저장      |
| `scripts/k6/resource-sampler.sh` | 5초마다 Spring, FastAPI, k6, kafka 의 CPU 와 메모리를 한 줄씩 출력                              |


## 2. breakpoint.js

| 부분                         | 내용                                                                                                                                                                         |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 환경변수                     | `STEPS`(계단의 VU 수), `STEP_RAMP_SEC`, `STEP_HOLD_SEC`, `RAMP_DOWN_SEC`, `THINK_SEC`, `P95_MS`, `MIN_OK_RATE`, `ABORT`, `PROVIDER`, `SPRING`. 기본값은 파일 맨 위 주석에 있다      |
| `stages`                     | `STEPS` 의 계단마다 "올리기"와 "머물기" 두 구간을 만들고 마지막에 0 으로 내리는 구간을 붙인다. `ramping-vus` 실행기가 이 목록대로 VU 수를 바꾼다                               |
| `currentStep()`              | 시험 시작 뒤 지난 시간(`exec.scenario.startTime` 기준)으로 지금이 어느 계단의 어느 구간인지 계산한다. 머무는 구간은 계단의 VU 수, 올리는 구간은 `ramp`, 끝난 뒤는 `down` 을 돌려준다 |
| 이름표(`step`)               | 요청과 사용자 정의 지표(`accepted`, `status_*`)에 붙인다. 요약에서 계단별로 나눠 볼 수 있다                                                                                    |
| 계단별 임계값                | 계단마다 `http_req_duration{…,step:N}` 의 p(95)와 `accepted{step:N}` 에 기준을 건다. 처음 FAIL 이 나온 계단이 Breakpoint 다. 나머지 `count>=0` 임계값은 요약에 계단별 값을 보이게 하는 표시용이다 |
| `ABORT=1`                    | 기준을 처음 넘는 계단에서 시험을 멈춘다(`abortOnFail`). 기본은 끝까지 돌려 전체 곡선을 본다                                                                                  |
| 요청 시간 제한               | 요청마다 `timeout: '10s'`. 10초 넘게 응답이 없으면 실패로 보고 `status_0` 으로 센다                                                                                          |
| 응답 코드별 개수             | `status_202`(성공), `status_503`(Kafka 전송 실패), `status_other_5xx`, `status_0`(응답 없음), `status_other`                                                                  |


## 3. run-breakpoint.sh 와 resource-sampler.sh

| 파일                  | 내용                                                                                                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `run-breakpoint.sh`   | `ulimit -n 10240` 으로 열 수 있는 파일 한도를 올린다(그 터미널에서만 적용). 첫 인자는 결과 파일 이름이고 나머지는 k6 옵션이다. 끝나면 자원 기록을 화면에 다시 출력한다 |
| `resource-sampler.sh` | 포트 8080, 8000 을 듣는 프로세스와 k6 프로세스의 `ps` 값, kafka 컨테이너의 `docker stats` 값을 INTERVAL(기본 5초)마다 찍는다. 프로세스가 없으면 `(없음)` 을 찍는다 |


## 4. 확인하지 않은 것

| 항목                                          | 상태                                                                        |
| --------------------------------------------- | --------------------------------------------------------------------------- |
| `breakpoint.js` 와 두 셸 스크립트의 실행      | 문법만 확인했다(`node --check`, `bash -n`). k6 와 Spring 이 없어 실행하지 못했다 |
| 계단별 이름표가 요약에 계단별로 나오는지      | 실행 전. k6 의 하위 지표(tag 별) 표시를 기대한 것이다                        |
| `ps`, `lsof`, `docker stats` 출력 형식        | macOS 기준으로 썼고 직접 돌려 보지 않았다                                   |
