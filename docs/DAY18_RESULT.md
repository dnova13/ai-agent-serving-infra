# Day 18 결과 — Consumer Group 과 멀티 컨슈머 (파티션 3개, 워커 1~4개)

> 구현과 실행 방법은 [DAY18_GUIDE.md](DAY18_GUIDE.md). 이 문서는 재측정한 결과와 해석을 담는다.
> 상태: 핵심(워커 1개, 2개, 3개 비교)을 재측정해 기록함(2026-10-12). 선택 실험 중 워커 4개(가이드 ④)도 한 번 돌려 3-4 에 기록했다. 워커 종료, `kill -9`, 다른 그룹(⑤~⑦)은 하지 않았고 6번에 적었다.
> 포트: **8080 = Spring WAS**, **8000 = FastAPI 워커 1(`w1`)**, **8001 = 워커 2(`w2`)**, **8002 = 워커 3(`w3`)**, **8003 = 워커 4(`w4`, 3-4 에서만)**.

**전체 목적:** 지금까지는 워커 하나가 요청을 한 건씩 차례로 처리해서(Day 17: 3건에 75초) 요청이 몰리면 뒤의 요청이 기다렸다. 같은 그룹(`agent-workers`)에 워커를 늘리면 파티션을 나눠 맡아 병렬로 처리하는지, 그리고 시간이 얼마나 줄어드는지를 파티션 3개짜리 토픽에서 워커 1개, 2개, 3개로 비교한다.

## 3. 확인된 결과

### 3-1. 파티션 3개, 워커 1개 (기준값)

**목적:** 파티션이 3개여도 워커가 하나면 한 건씩 차례로 처리해서 시간이 줄지 않는다는 기준값을 잰다.

| 확인한 것              | 값                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| 파티션 배정            | `localhost:8000:[0,1,2]`. 한 워커가 셋을 모두 맡음                                       |
| Spring(8080)의 응답    | 3건 모두 `202` (0.041초, 0.019초, 0.015초)                                               |
| 요청의 파티션 분포     | 파티션 2 에 2건, 파티션 1 에 1건, 파티션 0 에 0건                                        |
| 건당 처리 시간(서버)   | 30383 ms, 23058 ms, 22318 ms (합 75.8초)                                                 |
| 처리 완료까지          | 77초. 3건 모두 `DONE`, 실패 0건                                                          |
| 동시 처리 배율         | 스크립트 출력 `처리 시간 합계 75초 / 완료 시간 77초 = 0.9배`                             |

처리 중인 워커 수는 처음부터 끝까지 `1/1` 이었다. 건당 처리 시간의 합(75.8초)과 완료 시간(77초)이 거의 같아, 한 건씩 차례로 처리됐다. 배율이 1.0 보다 작게 나온 것은 완료 시간 쪽에 약 1초가 더 들어갔기 때문이다(요청이 메시지를 받기까지의 시간과 `/health` 를 1초 간격으로 확인하는 오차로 보이나, 구분해서 확인하지는 않았다).

이 실행의 시작 전 `/health` 는 `received 6`, `committed 6` 이었다. 워커 1을 새로 켠 상태가 아니라 이전 측정의 누적 값이 남아 있었던 것으로 보인다. 스크립트가 시작 대비 증가량으로 판정하므로 이 결과에는 영향이 없다.


### 3-2. 워커 2개

**목적:** 워커를 2개로 늘리면 파티션이 어떻게 나뉘고, 처리 시간이 줄어드는지 본다.

| 확인한 것              | 값                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------- |
| 파티션 배정            | `w1(8000)` = `[1]`, `w2(8001)` = `[0,2]`. 한 워커가 2개, 한 워커가 1개                            |
| Spring(8080)의 응답    | 3건 모두 `202` (0.038초, 0.012초, 0.015초)                                                        |
| 요청의 파티션 분포     | 파티션 1 에 2건, 파티션 0 에 1건, 파티션 2 에 0건                                                 |
| 워커별 처리 건수       | `w1` 2건(14751 ms, 23354 ms), `w2` 1건(25550 ms)                                                  |
| 건당 처리 시간(서버)   | 합 63.7초                                                                                         |
| 처리 완료까지          | 38초. 3건 모두 `DONE`, 실패 0건                                                                   |
| 동시 처리 배율         | 스크립트 출력 `처리 시간 합계 63초 / 완료 시간 38초 = 1.6배`                                      |

처리 중인 워커 수는 처음 24초 동안 `2/2` 이었다가 `w2` 가 끝난 25초부터 `1/2` 로 줄어 38초에 `0/2` 가 됐다. 처음 15초에 `w1` 의 첫 요청이, 25초에 `w2` 의 요청이, 38초에 `w1` 의 두 번째 요청이 끝난 순서와 맞는다. 두 워커가 동시에 일해서 워커 1개일 때(77초)보다 짧았다.

완료 시간(38초)은 더 많이 받은 `w1` 의 처리 시간 합(14.8 + 23.4 = 38.1초)과 같다. 이번에도 가장 바쁜 워커가 끝나야 전체가 끝났다.

이 실행의 시작 전 `/health` 는 `received 9`, `committed 9` 였다(이전 측정의 누적 값. 증가량으로 판정하므로 영향이 없다).


### 3-3. 워커 3개

**목적:** 워커 3개가 파티션을 하나씩 맡을 때 처리 시간이 줄어드는지, 요청 분배가 고른지 본다.

| 확인한 것              | 값                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| 파티션 배정            | `w1(8000)` = `[2]`, `w2(8001)` = `[1]`, `w3(8002)` = `[0]`. 한 워커가 하나씩                                 |
| Spring(8080)의 응답    | 3건 모두 `202` (0.039초, 0.014초, 0.012초)                                                                   |
| 요청의 파티션 분포     | 파티션 0, 1, 2 에 1건씩                                                                                      |
| 워커별 처리 건수       | `w3` 1건(21184 ms), `w2` 1건(45656 ms), `w1` 1건(26397 ms)                                                   |
| 건당 처리 시간(서버)   | 합 93.2초                                                                                                    |
| 처리 완료까지          | 46초. 3건 모두 `DONE`, 실패 0건                                                                              |
| 동시 처리 배율         | 스크립트 출력 `처리 시간 합계 93초 / 완료 시간 46초 = 2.0배`                                                 |

처리 중인 워커 수는 처음 21초 동안 `3/3` 이었고, `w3` 이 끝난 22초부터 `2/3`, `w1` 이 끝난 27초부터 `1/3`, 마지막 `w2` 가 끝난 46초에 `0/3` 이 됐다(서버가 잰 처리 시간 21.2초, 26.4초, 45.7초와 맞는다). 처음으로 요청이 세 파티션에 1건씩 나뉘어 세 워커가 모두 동시에 일했다.

완료 시간(46초)은 가장 오래 걸린 요청(`w2` 의 45.7초)과 같다. 세 워커가 모두 일했지만 한 요청이 나머지보다 두 배쯤 걸려서, 먼저 끝난 두 워커가 그만큼 놀았다. 그래서 배율이 이론상 상한인 3.0 이 아니라 2.0 이다.

이 실행의 시작 전 `/health` 는 `received 12`, `committed 12` 였다(이전 측정의 누적 값. 증가량으로 판정하므로 영향이 없다).


### 3-4. 워커 4개 (파티션 3개보다 많음)

**목적:** 워커가 파티션 수보다 많을 때 남는 워커가 놀고, 워커를 더 늘려도 처리가 빨라지지 않는지 본다.

| 확인한 것              | 값                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 파티션 배정            | `w1(8000)` = `[]`, `w2(8001)` = `[2]`, `w3(8002)` = `[1]`, `w4(8003)` = `[0]`. 파티션 3개를 세 워커가 하나씩, 한 워커는 못 받음 |
| Spring(8080)의 응답    | 3건 모두 `202` (0.038초, 0.012초, 0.013초)                                                                               |
| 요청의 파티션 분포     | 파티션 0 에 2건, 파티션 2 에 1건. 파티션 1 에는 0건                                                                      |
| 워커별 처리 건수       | `w4` 2건(25297 ms, 22269 ms), `w2` 1건(21990 ms). `w1`, `w3` 은 0건                                                      |
| 건당 처리 시간(서버)   | 합 69.6초                                                                                                                |
| 처리 완료까지          | 49초. 3건 모두 `DONE`, 실패 0건                                                                                          |
| 동시 처리 배율         | 스크립트 출력 `처리 시간 합계 69초 / 완료 시간 49초 = 1.4배`                                                             |

배정이 비어 있는 워커는 `w1`(8000)이었다. 나중에 켠 `w4` 가 아니라 처음부터 있던 워커가 `[]` 가 됐다. 워커가 들어올 때마다 파티션을 전부 다시 나누므로(4번) 어느 워커가 빈손이 될지는 정할 수 없다. 이 실행에서 일한 워커는 파티션을 가진 `w2`, `w4` 둘뿐이었다(파티션 1 을 가진 `w3` 은 요청이 없어 놀았다).

처리 중인 워커 수는 처음 22초 동안 `2/4`, `w2` 가 끝난 23초부터 `1/4`, `w4` 의 두 번째 요청이 끝난 49초에 `0/4` 였다. 처음부터 끝까지 4개 중 2개만 일했다. 완료 시간(49초)은 가장 바쁜 `w4` 의 두 요청 합(47.6초)과 같았다(3-5 비교와 같은 결과).

파티션보다 워커가 많으면 남는 워커는 일을 받지 못한다는 것은 `w1` 의 `[]` 와 0건으로 확인했다. 다만 이 실행은 3건뿐이고, 워커 3개일 때와 같은 조건으로 비교한 것이 아니다(요청의 파티션 분포가 달랐다). 그래서 "워커 4개가 3개보다 느리다/빠르다" 같은 비교는 하지 않는다.

이 실행의 시작 전 `/health` 는 `received 15`, `committed 15` 였다(이전 측정의 누적 값. 증가량으로 판정하므로 영향이 없다).


### 3-5. 워커 1~4개 비교

**목적:** 워커 수에 따라 시간과 병렬 정도가 어떻게 달라졌는지, 그리고 전체 시간을 정하는 것이 무엇인지 한 표로 본다.

| 워커 | 파티션 배정                        | 요청의 파티션(3건) | 워커별 처리 건수              | 완료 시간 | 건당 시간의 합 | 동시 처리 배율(스크립트 출력) |
| ---- | ---------------------------------- | ------------------ | ----------------------------- | --------- | -------------- | ----------------------------- |
| 1개  | `w1` `[0,1,2]`                     | 2, 1, 2            | `w1` 3                        | 77초      | 75.8초         | 0.9                           |
| 2개  | `w1` `[1]`, `w2` `[0,2]`           | 1, 1, 0            | `w1` 2, `w2` 1                | 38초      | 63.7초         | 1.6                           |
| 3개  | `w1` `[2]`, `w2` `[1]`, `w3` `[0]` | 0, 1, 2            | `w1` 1, `w2` 1, `w3` 1        | 46초      | 93.2초         | 2.0                           |
| 4개  | `w1` `[]`, `w2` `[2]`, `w3` `[1]`, `w4` `[0]` | 0, 0, 2 | `w2` 1, `w4` 2 (`w1`, `w3` 은 0) | 49초 | 69.6초         | 1.4                           |

스크립트의 배율은 소수점 첫째 자리에서 버림한 값이다(2개일 때 63.7÷38 = 1.67 이 1.6, 3개일 때 93.2÷46 = 2.03 이 2.0, 4개일 때 69.6÷49 = 1.42 가 1.4 로 출력됨).

**전체 완료 시간은 가장 바쁜 워커의 처리 시간 합과 같았다.** 워커 1개 `w1` 75.8초 → 77초, 2개 `w1` 38.1초(14.8 + 23.4) → 38초, 3개 `w2` 45.7초 → 46초, 4개 `w4` 47.6초(25.3 + 22.3) → 49초. 네 번 모두 맞았다. 요청이 한 워커에 몰리면 그 워커가 끝날 때까지 전체가 끝나지 않는다.

워커 4개는 파티션(3개)보다 워커가 많은 경우라 앞의 셋과 성격이 다르다. 4개의 49초와 1.4배는 요청이 파티션 0 에 2건 몰린 분포 때문이고, 워커가 하나 늘어서 느려졌다는 뜻이 아니다. 요청 분포가 실행마다 달라서 워커 수끼리의 우열은 이 표로 말할 수 없다(5번).


### 3-6. 이론값과 측정값의 차이

**목적:** 요청이 이상적으로 나뉘고 건당 시간이 같다고 했을 때의 값(이론)과 실제 측정값이 얼마나 다른지, 그 차이가 왜 생겼는지 본다.

이론값은 측정한 12건(3-1~3-4)의 건당 처리 시간 평균 약 25.2초를 모든 요청에 똑같이 쓰고, 요청이 파티션에 가장 고르게 나뉜다고 놓고 계산한 값이다. 3건은 2개 워커에 똑같이 나눌 수 없어서 2개일 때는 한 워커가 2건을 맡는다. 이 계산은 측정이 아니라 가정이다.

| 워커 | 이론상 완료 시간                 | 측정 완료 시간 | 이론상 배율 | 측정 배율 | 차이의 원인                                                                                         |
| ---- | -------------------------------- | -------------- | ----------- | --------- | --------------------------------------------------------------------------------------------------- |
| 1개  | 약 76초 (3건을 차례로)           | 77초           | 1.0         | 0.9       | 거의 같다. 1초 안팎은 측정 오차 수준                                                                |
| 2개  | 약 50초 (한 워커가 2건)          | 38초           | 1.5         | 1.6       | 요청 하나가 14.8초로 짧아서 이론보다 빨랐다. 워커 구조 때문이 아니라 건당 처리 시간이 짧았던 것(3-7)     |
| 3개  | 약 25초 (워커마다 1건)           | 46초           | 3.0         | 2.0       | 분배는 이상적(1/1/1)이었지만 한 요청이 45.7초 걸려, 가장 느린 요청이 전체 시간을 정했다             |
| 4개  | 약 25초 (3개와 같음, 파티션이 3개) | 49초         | 3.0         | 1.4       | 요청 2건이 파티션 0 에 몰려 한 워커(`w4`)가 차례로 처리(25.3 + 22.3초). 워커를 늘려도 몰린 파티션은 못 나눔 |

차이를 만든 것은 세 가지다.

| 원인                         | 설명                                                                                                                      |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 요청이 파티션에 고르게 안 나뉨 | key 를 해시해 파티션을 정하므로 3건으로는 치우치기 쉽다. 3건이 서로 다른 파티션에 갈 확률은 약 22% 다(3개 측정에서만 그랬다)   |
| 건당 시간이 흔들림           | 같은 질문 종류인데 14~46초로 달랐다. 병렬로 처리해도 가장 느린 요청이 끝나야 전체가 끝난다                                |
| 실행마다 조건이 다름         | 워커 수를 바꿀 때마다 요청의 파티션 분포와 건당 시간이 함께 바뀌어서, 워커 수의 효과만 따로 떼어 볼 수 없다               |

이 표로 말할 수 있는 것은 "워커를 늘릴수록 병렬 처리 정도가 커지는 경향이 있고, 완료 시간은 가장 바쁜 워커가 정한다"까지다. "워커 N개면 N배 빨라진다"는 이 데이터로 말할 수 없다. 이론에 가까운 값을 보려면 요청을 더 늘려(예: 12건 이상) 분포를 평균에 가깝게 하고 같은 조건을 반복해야 하며, 이번에는 하지 않았다(6번).


### 3-7. 건당 처리 시간이 길었던 이유

**목적:** 요청 3건(스크립트 기본값)을 처리하는 데 워커 1개로 77초나 걸린 것이 정상인지, 시간이 어디서 쓰였는지 본다.

3-1~3-4 에서 건당 처리 시간(서버가 잰 `elapsedMs`)은 14~46초였고, 12건의 평균은 약 25.2초였다. 처음에는 이 시간이 Kafka 나 Spring 쪽 때문인지, 에이전트 안에서 쓰이는지 알 수 없었다.

| 단계                              | 확인한 것                                                                                                     | 확인 방법              |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------- | ---------------------- |
| Spring(8080) 의 접수              | `202` 응답이 0.01~0.05초                                                                                      | 스크립트 출력(2번 단계) |
| 건당 처리 시간(`run_agent` 전체)  | 14~46초, 평균 약 25.2초. `elapsedMs` 는 `run_agent` 호출 하나를 감싼 시간이라 느린 구간은 이 안이다           | 3-1~3-4 의 결과 조회   |
| 에이전트 구조                     | 그래프가 `agent`(LLM 호출) → `tools` → `agent` 로 돈다. 도구를 한 번 쓰면 LLM 을 최소 2번 호출한다           | `agent_graph.py` 코드 |

처음에는 이 시간을 "Gemini 응답이 느려서"라고 말하려 했지만, 그 시점에는 단계별로 시간을 재지 않았으므로 확인된 말이 아니었다. 그래서 `agent_graph.py` 의 `agent_node`, `tool_node`, `search_vector_db`, `run_agent` 에 시간 로그(`[timing]`)를 넣고 1건(`bash scripts/day17_e2e.sh 1`, 워커 1개)을 다시 돌렸다.

| 단계                                   | 걸린 시간 | 전체(28.94초) 중 비율 |
| -------------------------------------- | --------- | --------------------- |
| LLM 호출 1 (도구를 부를지 판단, 도구 요청 1개) | 13.84초   | 약 48%                |
| 임베딩 + Qdrant 검색 (도구 실행)       | 0.51초    | 약 2%                 |
| LLM 호출 2 (검색 결과로 답 작성, 도구 요청 0개) | 14.54초   | 약 50%                |
| 합계                                   | 28.89초   | 그래프 전체 28.94초, 나머지 0.05초 |

서버 로그의 `elapsed_ms=28945` 도 그래프 전체 시간 28.94초와 같다. 최종 답은 40자짜리 짧은 문장인데도 LLM 호출 2 가 14.5초 걸렸으므로, 답이 길어서 느린 것이 아니라 호출 하나가 원래 14초쯤 걸린 것이다.

| 구분         | 내용                                                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| 확인된 것    | 이 요청에서는 시간의 약 98% 가 LLM(Gemini) 호출 2번이었다. 임베딩과 Qdrant 검색(0.5초), Kafka 전달, 커밋, 결과 저장은 병목이 아니었다 |
| 결론         | 건당 약 25초는 LLM 호출 2번(호출당 약 14초)이 대부분이다. 워커를 늘렸을 때 줄어든 시간은 이 느린 호출을 여러 워커가 겹쳐서 처리한 효과다 |
| 확인 못한 것 | LLM 호출 하나가 왜 14초인지(모델 응답 지연, 무료 티어 제한, 네트워크 등 구분 못 함). 1건만 쟀고, 14~46초로 흔들리는 폭의 원인도 모름. Day 16 에서 한 번 7.6초였던 차이도 풀리지 않음 |

이 구조는 비동기로 처리하는 이유와 이어진다. 요청 하나가 25초쯤 걸리면 동기 API 는 그동안 연결을 잡고 있어야 하지만, Kafka 를 거치면 Spring(8080)은 0.04초 만에 `202` 를 돌려준다.


## 4. 리밸런싱 로그: 워커를 추가하고 껐다 켤 때

**목적:** 같은 그룹에 워커가 들어오거나 나갈 때 기존 워커(`w1`, 8000)에게 어떤 일이 일어나는지 로그로 확인한다.

워커 3개로 늘리는 과정에서 `w1` 이 파티션 `[1]` 을 받자, 사용자가 `[2]` 를 받을 때까지 다른 워커를 껐다 켰다. 그때 `w1`(8000) 터미널에 찍힌 로그는 다음과 같다.

```
Heartbeat failed for group agent-workers because it is rebalancing
[w1] 파티션 회수 [1]
[w1] 파티션 배정 [1] (리밸런싱 7번째)
Heartbeat failed for group agent-workers because it is rebalancing
[w1] 파티션 회수 [1]
[w1] 파티션 배정 [1] (리밸런싱 8번째)
Heartbeat failed for group agent-workers because it is rebalancing
[w1] 파티션 회수 [1]
[w1] 파티션 배정 [2] (리밸런싱 9번째)
GET /health 200 OK
[agent] 시작 worker=w1 requestId=52b2a386-b5fc-4aea-a38d-eff50b6ea8c4 partition=2 offset=6 provider=gemini
```

| 로그                                                         | 의미                                                                                                                                    |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| `Heartbeat failed ... because it is rebalancing`             | 워커가 들어오거나 나가면 그룹이 재배정을 시작하고, 이미 가입한 워커의 생존 신호(heartbeat)가 "재배정 중이니 다시 가입하라"는 응답을 받는다는 aiokafka 의 알림이다. 오류가 아니라 재배정이 시작될 때마다 나온다 |
| `파티션 회수 [1]`                                            | 재배정이 시작되어 `w1` 이 맡던 파티션을 모두 내놓았다                                                                                   |
| `파티션 배정 [1]` 또는 `[2]`                                 | 재배정 결과 받은 파티션. 받은 파티션이 같아도(`[1]` → `[1]`) 한 번은 모두 내놓고 다시 받는다                                            |
| `리밸런싱 7번째 → 8번째 → 9번째`                             | `w1` 이 켜진 뒤 파티션을 새로 배정받은 횟수(처음 가입 포함). 워커를 껐다 켤 때마다 올라갔고, 이 로그에서는 마지막에 `[2]` 를 받았다      |

같은 로그 위쪽에 `... 404 Not Found` 가 한 줄 보이는데(화면 위쪽에 일부만 보임), 스크립트가 요청을 처리하지 않은 워커 주소로 결과를 먼저 물어봐서 나오는 정상 응답이다. 스크립트는 워커 주소를 차례로 물어 200 이 오는 곳에서 읽는다.

**파티션 번호는 정할 수 없다.** 어느 워커가 어느 파티션을 받는지는 그룹에 들어온 순서와 워커마다 임의로 붙는 멤버 ID 로 정해져서 사용자가 고를 수 없다. 이전 측정에서의 배정과 같을 필요도 없다. 측정에서 중요한 것은 워커 3개가 파티션을 하나씩 나눠 가졌는지다. 워커를 껐다 켤 때마다 재배정이 일어나므로, 반복하면 처리가 멈추는 구간이 늘어난다.

마지막 `[agent] 시작` 줄의 `52b2a386-b5fc-4aea-a38d-eff50b6ea8c4` 는 3-3 의 세 번째 요청이다. 3-3 의 결과 조회에서도 이 요청이 `worker=w1`, `partition=2` 로 나와 로그와 스크립트 출력이 일치한다.

이 로그로 확인된 것은 실제 Kafka 에서 회수와 배정이 로그로 남고 횟수가 세어진다는 점이다. 재배정이 처리 중인 요청과 겹쳤을 때 `commit 거절` 이 나는지, 재배정 동안 처리가 몇 초 멈췄는지는 이 로그로는 알 수 없다.


## 5. 해석

| 확인한 것                                                    | 의미                                                                                                                                                                        |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 같은 그룹의 워커가 파티션을 나눠 맡음                        | 워커 1개 `[0,1,2]`, 2개 `[1]`/`[0,2]`, 3개 `[2]`/`[1]`/`[0]` 으로 나뉘었다. 한 파티션은 한 워커만 읽는다                                                                       |
| 동시 처리 배율이 0.9 → 1.6 → 2.0 으로 커짐                   | 워커를 늘리고 요청이 나뉠수록 병렬로 처리되는 정도가 커졌다. 단, 워커 수마다 한 번씩만 측정했고 요청의 파티션 분포가 실행마다 달랐다(3개일 때만 1/1/1). 3개의 균등한 분포는 운이 따른 면이 있다 |
| 완료 시간 = 가장 바쁜 워커의 처리 시간 합                    | 네 번 모두 맞았다. 병목은 가장 많은 요청을 받은 파티션의 워커다. 요청 key 가 매번 다른 UUID 여도 건수가 적으면 치우칠 수 있다                                                 |
| 워커 3개(46초)가 워커 2개(38초)보다 오래 걸림                | 3개일 때는 요청이 고르게 나뉘었지만 한 요청이 45.7초로 오래 걸려 그 요청이 전체 시간을 정했다. 건당 시간이 22~46초로 흔들려서 완료 시간만으로는 워커 수의 효과를 비교하기 어렵다. 그래서 동시 처리 배율과 분포로 본다 |
| 워커 3개에서 배율이 3.0 이 아니라 2.0                        | 세 요청의 처리 시간이 21.2초, 26.4초, 45.7초로 달라서, 먼저 끝난 워커가 나머지를 기다리며 놀았다(처리 중인 워커가 3 → 2 → 1 로 줄어든 구간). 병렬 처리는 가장 느린 요청이 끝날 때까지 이어진다 |
| 워커 4개일 때 `w1` 이 `[]` 이고 0건 처리 (3-4)               | 파티션 수(3)보다 많은 워커는 일을 받지 못한다. 어느 워커가 빈손이 될지는 정할 수 없고 처음부터 있던 워커도 될 수 있다. 처리량을 늘리려면 파티션도 함께 늘려야 한다(파티션 증가는 되돌릴 수 없음) |
| 측정 배율이 이론(1.0 / 1.5 / 3.0 / 3.0)과 다름 (3-6)       | 2개는 이론보다 빨랐고 3개, 4개는 느렸다. 원인은 요청의 파티션 쏠림과 건당 시간의 흔들림이다. 이론은 가정으로 계산한 값이고 측정이 아니다 |
| 건당 25초는 LLM 호출 2번이 대부분 (3-7)                     | 1건을 단계별로 재서 확인했다. 호출당 약 14초이고 그 이유는 모른다. 시간 비교 결과가 크게 흔들린 이유와 이어진다                                                       |
| 리밸런싱은 워커가 들어오거나 나갈 때마다 일어남              | 워커를 추가하고 껐다 켤 때마다 파티션을 모두 내놓고 다시 받았다(4번). 반복할수록 처리가 멈추는 구간이 늘 수 있다                                                              |


## 6. 확인하지 않은 것

아래는 선택 항목이거나 이번 실행으로 보지 못한 것이다. 방법은 가이드 6번(실행과 확인)에 있다.

| 항목                                      | 내용                                                                                                                                  |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 워커가 파티션보다 많을 때 (가이드 ④)       | 3-4 에서 한 번 확인했다. kafka-ui 의 멤버 4개/배정 3개 화면과, 워커 3개와 같은 분포로 맞춘 시간 비교는 하지 않았다                    |
| 워커 종료 (가이드 ⑤)                       | 정상 종료 때의 재배정, 처리 중이던 요청을 다른 워커가 다시 처리하는지(중복) 확인하지 않았다                                           |
| `kill -9` (가이드 ⑥)                       | 이어받기까지 걸리는 시간(세션 타임아웃, 기본 10초 예상)을 재지 않았다                                                                 |
| 다른 그룹 (가이드 ⑦)                       | 그룹이 다르면 같은 요청을 둘 다 받는지 확인하지 않았다                                                                                |
| 6건 이상에서의 분포와 단축                 | 3건으로만 시험했다. 건수가 늘면 분포가 고르게 되고 배율이 커지는지는 보지 않았다                                                      |
| 같은 조건의 반복                           | 워커 수마다 한 번씩만 돌렸다. 요청 분포와 건당 시간이 매번 달라서 이번 수치로 평균적인 단축률을 말할 수 없다                          |
| 재배정 중 처리 멈춤과 `commit 거절`        | 재배정 동안 처리가 몇 초 멈췄는지, 처리 중인 요청과 겹쳐 `commit 거절` 로그가 났는지 확인하지 않았다                                  |
| kafka-ui(8090)의 그룹 화면                 | 멤버 수, 배정, 파티션별 Lag 을 화면으로 확인하지 않았다                                                                               |
| 건당 시간이 흔들리는 이유 (3-7)            | 단계별 시간은 1건만 쟀다. 14~46초로 달라지는 원인(LLM 호출 시간 차이인지, 호출 횟수 차이인지)과 LLM 호출 하나가 14초인 이유는 확인하지 않았다 |
| 요청별 로그와 스크립트의 대조              | 세 번째 요청 한 건(`52b2a386-...`)만 로그와 스크립트 출력이 일치하는 것을 확인했고, 나머지 요청은 대조하지 않았다                     |
| 파티션 수를 늘린 방법                      | `application.properties` 수정과 Spring(8080) 재시작으로 3개가 된 것은 `/health` 의 `[0,1,2]` 로 확인했다. 가이드의 `docker exec` 명령은 쓰지 않았다 |
