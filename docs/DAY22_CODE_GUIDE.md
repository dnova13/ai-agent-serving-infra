# Day 22 코드 가이드 — race_test.py

> 대상 파일: `d2-ai-python/app/experiments/race_test.py` (새 파일). 기존 코드는 바꾸지 않았다.
> 사용법과 기대 숫자는 [DAY22_GUIDE.md](DAY22_GUIDE.md).
> 포트: **8080 = Spring WAS**, **8000 = FastAPI 워커(1번)**, **8001 = FastAPI 워커(2번)**, **6379 = Redis**.

**전체 목적:** 같은 세션 동시 요청 테스트가 어떤 순서로 돌고, 숫자가 어떻게 만들어지며, 무엇을 판정하고 무엇을 정보로만 남기는지 코드 위치별로 설명한다.


## 1. 전체 흐름

```
main()  ── 인자 읽기, N 범위 확인(2~10), Redis 연결 확인
   │
   ├─ --mode inproc ─▶ _run_inproc()
   │      · run_agent 의 모델 자리에 FakeGraph(대기만 하는 가짜)를 끼운다
   │      · 시나리오(fixed / jitter / diff) × 락(있음 / 없음) 마다 라운드를 반복
   │      · one_round(): 스레드 N 개가 Barrier 에서 동시에 출발 → run_agent 호출 → 결과를 Redis 에서 읽어 집계
   │      · _report_inproc(): 표 출력, 락 있음만 판정(PASS/FAIL)
   │
   └─ --mode http ───▶ _run_http()
          · 라운드마다 새 세션 → 서버들에 POST 를 동시에(Barrier) → GET 으로 저장된 턴 확인 → DELETE
          · 요청별 시간, 라운드 시간, 유실 라운드 수를 출력(판정 없음)
```

| 구분             | inproc                                                  | http                                                     |
| ---------------- | ------------------------------------------------------- | -------------------------------------------------------- |
| 모델             | 가짜(`time.sleep`)                                      | 실제 Gemini                                              |
| Redis            | 진짜(`localhost:6379`)                                  | 서버가 쓰는 Redis                                        |
| 락 켜고 끄기     | 코드에서 `ag.SESSION_LOCK_ENABLED` 를 바꿈               | 서버를 띄울 때의 환경변수. 스크립트가 못 바꿈            |
| 이전 대화 수     | 가짜 모델이 직접 기록해서 숫자로 집계                   | 서버 로그의 `[timing] 이전 대화 N개` 로만 본다           |
| 판정             | 락 있음에만 PASS/FAIL                                   | 없음(정보 출력)                                          |


## 2. 주요 코드

### 2-1. 가짜 모델과 이전 대화 수 기록 (`_run_inproc` 안의 FakeGraph)

```python
_tls = threading.local()   # 요청 스레드가 자기 세션 이름을 모델 쪽에 알리는 용도

class FakeGraph:
    def invoke(self, state):
        msgs = state["messages"]
        with seen_lock:
            seen.setdefault(_tls.session, []).append(len(msgs) - 1)   # 모델이 받은 "이전 대화" 메시지 수
            delay = latency_of[current["scenario"]]()
        time.sleep(delay)                                             # 모델이 답하는 시간 대신
        return {"messages": msgs + [AIMessage(content="답:" + msgs[-1].content)]}

ag.AGENT_GRAPH = FakeGraph()
```

| 부분                              | 설명                                                                                                                                                 |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ag.AGENT_GRAPH = FakeGraph()`    | `agent_graph.run_agent` 가 부르는 그래프를 가짜로 바꾼다. 락, 대화 읽기, 저장은 진짜 코드가 그대로 돈다. 바뀌는 것은 모델 호출뿐이다                  |
| `len(msgs) - 1`                   | `state["messages"]` 는 "이전 대화 + 이번 질문"이다. 이번 질문 1개를 빼면 이전 대화 메시지 수다. 서버 로그의 `이전 대화 N개` 와 같은 값이다           |
| `_tls.session`                    | `invoke` 는 세션 이름을 받지 않는다. 요청 스레드가 시작할 때 `_tls.session` 에 자기 세션을 적고, 같은 스레드에서 `invoke` 가 불리므로 그 값을 읽는다   |
| `latency_of`                      | 시나리오별 대기 시간. fixed/diff 는 `--latency`(0.4초), jitter 는 `random.uniform(0.3, 1.2)`                                                         |
| `"답:" + 질문`                    | 답을 질문에서 만들어서, 나중에 저장된 (질문, 답) 쌍이 서로 짝이 맞는지(`pair_ok`) 확인할 수 있다                                                     |

### 2-2. 한 라운드 (`one_round`)

```python
barrier = threading.Barrier(n)

def worker(i):
    _tls.session = names[i]
    barrier.wait()                      # 모두 같은 순간에 출발
    ag.run_agent(f"Q{i}", "gemini", names[i])
```

| 단계                  | 설명                                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 세션 이름             | 같은 세션 시나리오(fixed, jitter)는 N 개 요청이 이름 하나를 공유한다. diff 는 요청마다 다른 이름이다. 라운드, 락 여부마다 새 이름이다 |
| `Barrier`             | 스레드를 먼저 다 만들고 `wait()` 에서 모아서 한꺼번에 풀어, 시작 시점을 최대한 맞춘다(도착 순서는 그래도 매번 다르다)                    |
| 라운드가 끝나면       | Redis 에서 대화를 읽어 저장된 턴 수(`len(history)//2`), 모델이 본 이전 대화 수(정렬), 걸린 시간, 짝 맞음 여부를 `_Round` 에 담는다   |
| 정렬된 이전 대화 수   | 차례로 처리됐다면 `[0, 2, 4, ..., 2(N-1)]` 이다. 이 값과 같은지가 "완벽한 라운드", 합을 `N(N-1)` 로 나눈 것이 "반영률"이다           |

### 2-3. 락 켜고 끄기 (inproc)

```python
ag.SESSION_LOCK_ENABLED = lock_on     # 라운드마다 바꾼다 (agent_graph.run_agent 가 이 값을 매번 읽는다)
...
finally:
    ag.SESSION_LOCK_ENABLED = lock_saved   # 끝나면 원래 값으로
```

`run_agent` 는 호출될 때마다 모듈 변수 `SESSION_LOCK_ENABLED` 를 읽으므로(Day 21 의 `if not session_id or not SESSION_LOCK_ENABLED:`), 환경변수 없이도 같은 프로세스 안에서 켜고 끌 수 있다. 각 (시나리오, 락) 조합을 모두 돌린 뒤 정리(`cs.clear`)한다.

### 2-4. 집계와 판정 (`_report_inproc`)

| 열                 | 계산                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------- |
| 저장된 턴(평균/최소) | 라운드별 저장된 턴의 평균과 최솟값. 기대는 N                                                  |
| 유실 라운드        | 저장된 턴 < N 인 라운드 수                                                                     |
| 앞 대화 반영률     | 라운드마다 `sum(priors) / (N(N-1))`, 그 평균                                                  |
| 완벽한 라운드      | `priors == [0, 2, ..., 2(N-1)]` 인 라운드 수                                                  |
| 라운드 시간        | 평균과 최대                                                                                    |

판정(`failures`)은 **락 있음에만** 한다.

| 판정 조건                                      | 이유                                                                            |
| ---------------------------------------------- | ------------------------------------------------------------------------------- |
| 락 있음에서 유실 라운드가 0 이어야 함          | 락의 존재 이유                                                                   |
| 락 있음(같은 세션)에서 모든 라운드가 완벽해야 함 | 뒤 요청이 앞 요청의 저장 뒤에 읽어야 한다                                       |
| 락 있음에서 저장된 질문-답 쌍이 짝이 맞아야 함 | 락 때문에 저장이 꼬이면 안 됨                                                   |
| diff 락 있음의 라운드 시간 ≤ 모델 시간 × 2.5   | 다른 세션 요청을 락이 늦추면 안 됨(느슨한 한도)                                 |

락 없음은 스레드 스케줄링에 따라 매번 다르므로 판정하지 않고 숫자만 보여 준다.

### 2-5. http 방식 (`_http`, `_run_http`)

```python
status, hist, _ = _http("GET", f"{urls[0]}/api/v1/agent/sessions/{session}")
turns = hist.get("turns") ...
loss = 라운드 중 (turns is None or turns < 200 응답 수) 인 라운드 수
```

| 부분                     | 설명                                                                                                                                    |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| `_http`                  | 표준 라이브러리(`urllib`)로 요청. 상태코드, JSON 본문, 걸린 시간을 돌려준다. 오류는 상태코드 0 으로 돌려 예외로 중단되지 않게 한다      |
| 요청 분배                | 요청 `i` 는 `urls[i % 서버 수]` 로 간다. 서버 2대에 번갈아 보낸다                                                                       |
| 질문                     | `QUESTIONS` 를 돌려 써서 같은 세션 안의 질문이 서로 다르게 한다                                                                         |
| 유실 판정                | 저장된 턴이 "200 응답을 받은 요청 수"보다 적으면 유실. 409(락 시간 초과)나 오류 응답은 저장되지 않는 것이 정상이라 세지 않는다            |
| 공급자(`--provider`)     | 요청 본문에 `"provider"`(gemini 또는 claude, 기본 gemini)를 실어 보낸다. 서버가 요청마다 그 값으로 모델을 고른다. 도구 검색의 임베딩은 어느 쪽이든 Gemini 다 |
| 실패한 요청 표시         | 200 이 아니면 `└ 상태 코드: 본문 앞부분` 을 출력하고, 응답이 하나도 없는 라운드를 유실로 세지 않도록 `(turns or 0) < 200 응답 수` 로 판정한다. 요약 줄에 실패한 라운드 수를 함께 낸다 |
| 이전 대화 수             | HTTP 응답에는 없다. 서버 로그를 본다                                                                                                    |
| 서버 수보다 큰 N         | `async def` 가 막혀 한 워커가 한 번에 한 요청만 처리하므로, 경고를 출력한다                                                             |


## 3. 결과를 읽는 순서

| 순서 | 보는 것                                   | 이유                                                                                          |
| ---- | ----------------------------------------- | --------------------------------------------------------------------------------------------- |
| 1    | 마지막 줄 `== 결과: PASS/FAIL`            | 락 있음이 약속(유실 0, 앞 대화 반영, 다른 세션 안 기다림)을 지키는가                          |
| 2    | fixed 락 없음의 유실 라운드, 반영률        | 락이 막아 주는 최악의 경우(겹침)의 크기                                                       |
| 3    | jitter 락 없음의 유실 라운드, 반영률       | 실제처럼 흩어질 때: 유실은 드물어도 앞 대화를 놓치는 일은 남는가                              |
| 4    | 락 있음의 라운드 시간                      | 락의 비용(같은 세션은 약 N 배)                                                                 |
| 5    | diff 의 락 있음 vs 없음 시간               | 락이 다른 세션의 처리량을 깎지 않는가                                                         |
