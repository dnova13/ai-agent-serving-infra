## 2. 개념

### 2-1. 락이 하는 일

`run_agent` 는 같은 `sessionId` 의 요청을 `redis_lock.lock("conversation:<sessionId>")` 안에서 실행한다(Day 21). 락은 Redis 에 `SET <키> <토큰> NX PX <만료ms>` 로 잡는다. 못 잡으면 `RETRY_INTERVAL_SEC`(0.1초)의 0.5~1.5배를 쉬었다가 다시 시도하고, `LOCK_WAIT_SEC`(100초)가 지나면 `LockTimeout` 이 된다(서버에서는 HTTP 409). 락 만료 `LOCK_TTL_SEC` 는 150초다.

### 2-2. 이 방식에서 N 이 커지면 생기는 일 (확인 전 예상)

- 요청은 한 번에 하나씩 처리되므로 전체 시간은 대략 N × (한 건 처리 시간)이다.
- 기다리는 요청은 모두 0.1초마다 `SET NX` 를 시도한다(폴링). 기다리는 요청이 N 에 비례하고 기다리는 시간도 N 에 비례하므로, 전체 시도 횟수는 N 의 제곱에 가깝게 늘 것으로 예상한다(⑤ 에서 확인).
- 폴링 방식이라 먼저 온 요청이 먼저 잡는다는 보장이 없다(선착순이 아니다). 요청마다 대기 시간 편차가 생긴다.
- Redis 클라이언트는 연결 풀을 쓴다. redis-py 8.1.0(이 프로젝트의 고정 버전)의 기본 풀 최대 연결 수는 100개다. 동시에 Redis 를 부르는 스레드가 100개를 넘으면 `MaxConnectionsError` 가 날 수 있다.
- `agent_graph.run_agent` 는 `fail_open=True` 로 락을 잡는다. Redis 오류로 락을 못 잡으면 락 없이 계속 실행한다(`redis_lock` 의 설계, Day 21). 연결 풀이 모자란 것도 Redis 오류로 취급되면 락이 우회된다 → ⑥ 에서 확인한다.

### 2-3. 이 시험의 구조

- 이 프로세스 안에서 스레드 N개가 `Barrier` 로 같은 순간에 출발해 `run_agent` 를 부른다. 모델은 가짜(0.05초 대기)이고 Redis 는 진짜다.
- 가짜 모델 안에서 "지금 모델 호출 구간에 몇 개가 들어와 있나"를 센다. 락이 제대로 동작하면 최댓값이 1 이다.
- 대화 기록은 최근 10턴만 보관(`CONVERSATION_MAX_TURNS`)하므로 N 이 10 을 넘으면 저장된 턴 수로는 유실을 알 수 없다. 대신 요청이 모델에 넘긴 "이전 대화 메시지 수"가 0, 2, 4, ... 20(상한)으로 차례로 쌓였는지, 동시 실행 최대, 저장 순서로 판단한다.

## 6. 알려진 한계

- 모델은 0.05초 대기하는 가짜다. 실제 모델은 건당 수 초~수십 초가 걸린다. 건당 20초라면 기다림 한도 100초 안에 끝나는 요청은 5개 안팎이라, 같은 세션 100개를 동시에 보내면 대부분 시간 초과(409)가 되는 것으로 계산된다. 이것은 계산이고 실제 모델로 확인하지 않았다.
- Spring → Kafka → 워커를 거치는 경로로는 보내지 않았다. 이 프로세스 안의 스레드로 `run_agent` 를 직접 부른다. 실제 워커는 `asyncio.to_thread` 를 쓰므로 한 프로세스의 동시 스레드 수가 이 시험의 100~200개보다 훨씬 적다(기본 스레드 풀 크기는 CPU 수 + 4, 최대 32). 그래서 ⑥ 의 연결 풀 부족이 실제 워커에서 같은 조건으로 생긴다는 뜻은 아니다. 다만 여러 워커 프로세스는 각자 연결 풀을 가지므로 Redis 쪽 연결 수는 합쳐서 늘어난다.
- 워커 프로세스를 여러 개 띄워 락을 경쟁시키는 시험은 Day 22 의 http 방식(N=2)에서만 했다. 오늘은 한 프로세스 안의 스레드 경쟁이다. 락은 Redis 에 있어서 프로세스가 달라도 같은 원리지만, 이번에 프로세스 간 경쟁을 N=100 으로 확인한 것은 아니다.
- 락 만료를 연장하는 기능은 없다(Day 21 의 알려진 한계). ④ 는 그 한계를 보여 주는 것이고 고치지 않았다.
- `fail_open=True` 로 Redis 오류 때 락 없이 계속하는 동작도 Day 21 에서 의도한 설계다. ⑥ 은 그 동작이 연결 풀 부족에서도 발동하는지 보는 것이며, 코드는 바꾸지 않았다. 바꾼다면 연결 풀 크기를 환경변수로 받거나, 풀 부족일 때는 락을 우회하지 않고 대기·재시도하게 하는 방법이 있다(아직 만들지 않았다).
- 대화는 최근 10턴만 보관하므로 저장된 턴 수로는 N>10 의 유실을 볼 수 없다. 그래서 동시 실행 최대와 "이전 대화 메시지 수"의 순서로 본다.
- 락 시도 횟수와 대기 시간은 이 PC, 이 Redis 의 값이다. 비율(N 에 따른 증가)을 보는 용도다.
