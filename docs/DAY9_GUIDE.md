# Day 9 가이드 — 검색 함수 작성 + 정확도 확인

> 상태: 완료. 단일 검색 동작 확인, top-1 정확도 11/12. (`score_threshold` 는 아직 미정 — 아래 "다음에 할 것" 참고)

## 1. 오늘 목표

Day 8 에서 채운 컬렉션(`documents-12`, 24건)에서 **질문과 의미가 가까운 문서를 찾는 함수**를 만든다.

```
질문 → 임베딩(RETRIEVAL_QUERY, 768차원) → Qdrant 에서 가장 가까운 top-k → 원문 반환
```

핵심 확인: **문서에 없는 표현으로 물어도** 의미가 같은 문서가 나오는가. ("돈 돌려받고 싶어요" → 환불 규정)

## 2. 만든 파일

| 파일 | 역할 |
|---|---|
| `app/services/qdrant_search.py` | `search(query, limit, category, score_threshold)` — Day 10 에서 에이전트 도구가 그대로 호출 |
| `app/experiments/search_eval.py` | 질문 12개 × 정답 카테고리로 top-1 / top-3 정확도 측정 |

## 3. 검색이 동작하는 방식

1. 질문을 Day 8 과 **같은 모델, 같은 768차원**으로 임베딩한다. (차원이 다르면 검색 자체가 에러)
2. 이때 `task_type` 은 문서용(`RETRIEVAL_DOCUMENT`)이 아니라 **질문용(`RETRIEVAL_QUERY`)** 을 쓴다.
3. Qdrant 가 컬렉션의 모든 벡터와 코사인 유사도를 계산해 가장 높은 top-k 를 돌려준다.
4. payload(원문, 카테고리)를 같이 받아서 바로 사용한다.

## 4. 설계 결정과 이유

### 4-1. `client.search()` 가 아니라 `query_points()`
- 설치된 qdrant-client 1.19.1 에는 `search()` 가 없다. 계획서의 `client.search()` 는 옛 API 이고, 지금은 `query_points()` 를 쓴다.
- 반환도 리스트가 아니라 `.points` 를 가진 객체다.

### 4-2. 컬렉션 이름은 `qdrant_setup.COLLECTION_NAME` 에서만 가져옴
- Day 8 에서 문서에 적은 이름과 코드의 이름이 달라 0건으로 보였던 문제의 재발 방지.

### 4-3. 카테고리 필터 (`category` 인자)
- 지정하면 해당 카테고리 문서 안에서만 검색한다. (예: 환불 문서만)
- Qdrant 는 **필터를 적용한 뒤 그 안에서 가까운 것**을 찾는다. 가까운 걸 먼저 뽑고 거르는 게 아니라서 결과 개수가 줄어들지 않는다.
- 이후 Redis/Kafka 단계에서 "사용자별/주제별 검색" 같은 확장의 기반이 된다.

### 4-4. `score_threshold`
- 유사도가 이 값 미만인 결과는 버린다. 관련 없는 질문에 억지로 문서를 끼워 주는 것을 막는 장치.
- 값은 **데이터를 보고 정해야** 한다. 아래 실행 결과의 점수 분포를 보고 Day 10 에서 정한다. 지금은 기본값 `None`(끄기).

### 4-5. `format_for_llm()`
- 검색 결과를 LLM 에 줄 문자열로 바꾼다. Day 10 에서 `search_vector_db` 도구가 이걸 반환한다.

## 5. 정확도 측정 방법과 한계

`search_eval.py` 가 질문 12개를 던져 정답 카테고리가 1위 / 3위 안에 나오는지 센다.
- `O`: 1위가 정답 / `△`: 3위 안에 정답 / `X`: 3위 안에도 없음
- **한계**: 문서 24건, 질문 12개로는 통계적으로 의미 있는 정확도가 아니다. "방향이 맞는지" 보는 용도다.
- 문서가 24건뿐이라 아무 질문에도 뭔가 걸리기 쉬워 정확도가 좋아 보이는 착시가 있다.
- 질문이 두 카테고리에 걸치면(예: 사이즈 교환 ↔ 사이즈 후기) 둘 다 정답으로 허용했다.

## 개념 정리 (Day 9 중 나온 질문)

> 별도 문서로도 정리해 두었다: `CONCEPTS_RAG.md`

### 검색의 원리: 질문을 벡터로 바꿔서 가까운 것을 찾는다

```
저장(Day 8) : 문서 24건 → [임베딩 모델] → 벡터 24개 → Qdrant 에 저장
검색(Day 9) : 질문     → [같은 임베딩 모델] → 벡터 1개 → Qdrant 가 가장 가까운 문서 top-k 반환
```

- 임베딩 모델은 "비슷한 맥락에서 쓰이는 말은 가까운 좌표, 다른 맥락의 말은 먼 좌표"가 되도록 학습되어 있다.
- 그래서 글자가 달라도 의미가 비슷하면 가깝다. `LIKE '%비밀번호%'` 는 글자가 같아야 찾는다.
- 거리는 **코사인 유사도**(두 벡터의 각도)로 잰다. 1 에 가까울수록 같은 의미. 이 계산은 수학이고 Qdrant 가 한다.
- **저장할 때와 검색할 때 같은 모델, 같은 차원(768)** 을 써야 한다. 좌표계가 다르면 거리가 의미 없다.
- 이 방식은 "의미가 비슷하다고 판단한 순서"일 뿐 정답을 아는 게 아니다. 어휘가 겹치는 다른 문서가 걸릴 수 있다. (예: "택배 언제 와요?" → 배송 규정이 아니라 배송 후기가 1위)

### 예시: `python -m app.services.qdrant_search "비번 까먹음"`

| 순위 | 점수 | 문서 |
|---|---|---|
| 1 | 0.7560 | member-001 (비밀번호 찾기) ← 정답 |
| 2 | 0.6181 | refund-001 (환불) ← 무관 |
| 3 | 0.6142 | member-002 (회원 탈퇴) |

- "비번"="비밀번호" 줄임말, "까먹음"="잊었다". 글자는 거의 안 겹치지만 같은 상황(로그인/재설정)에서 쓰이는 말이라 가깝다.
- 정답과 2위의 점수 차이가 0.14 로 뚜렷했다. (비교: "돈 돌려받고 싶다" 는 1~3위 차이가 0.01)
- **무관한 문서도 0.6 안팎은 나온다.** 이 값이 점수의 "바닥"일 가능성이 있고, 정답 점수(0.71~0.82)와의 사이에 임계값을 둘 수 있을지는 **무관한 질문의 점수를 재서 확인해야** 한다. (아직 미확인)

### 누가 벡터로 바꾸나

```
내 코드(embedding.py) → HTTP 로 질문 전송(API 키 포함)
  → Google 서버의 gemini-embedding-001 이 768개 숫자로 변환
  → 내 코드가 받은 숫자를 Qdrant 에 넘겨 검색
```

| 누가 | 역할 |
|---|---|
| Google 서버의 임베딩 모델 | 텍스트 → 벡터 변환 (실제 AI) |
| 내 코드 | API 호출, 결과 전달 |
| Qdrant | 벡터 저장, 거리 계산, 가까운 문서 반환 (AI 아님) |

- 검색할 때마다 질문 1개당 Google API 를 1번 호출한다 → API 키/한도(429)가 필요하다.
- **검색 시간의 대부분은 이 외부 호출(네트워크)** 이고 Qdrant 검색은 수 ms 다. k6 부하 테스트 때 병목 후보.
- 질문 텍스트가 Google 로 전송된다. (민감 정보가 있는 서비스라면 고려)
- 대안: `sentence-transformers` 같은 오픈소스 모델을 직접 돌리면 한도/네트워크 지연이 없다. 대신 모델 다운로드, 연산 자원, 한국어 성능 확인이 필요하다. 한도가 문제 되면 k6 단계에서 검토.

### AI 는 어디서 몇 번 쓰이나

| 단계 | AI 사용 | 비고 |
|---|---|---|
| 질문 → 벡터 | 사용 (임베딩 모델) | Day 9 까지 여기만 사용 |
| 가까운 문서 찾기 | 미사용 | Qdrant 의 수학 계산 |
| 찾은 문서로 답변 문장 생성 | **Day 10 부터** (채팅 모델) | 지금까지 출력한 건 AI 답변이 아니라 저장된 문서 원문 |

전체 구조(RAG):
```
질문 → [AI: 임베딩] → [Qdrant: 검색] → 찾은 문서 → [AI: 채팅 모델] 문서를 근거로 답변 생성 → 응답
```
- 검색만으로 끝내지 않고 채팅 모델을 한 번 더 쓰는 이유: 검색 결과는 질문에 직접 답하는 문장이 아니라 문서 원문이다. 질문과 관련된 부분만 골라 합치고, "문서에 없으면 모른다고 답하기" 같은 규칙도 이 단계에서 지킨다.
- 검색이 엉뚱한 문서를 가져오면 모델은 그 문서를 근거로 답한다. 그래서 검색 품질을 먼저 챙긴다.

### 토큰 절약과 캐싱은 다른 개념

**토큰**
- 검색 단계에서 채팅 모델 토큰은 안 쓰지만, 질문 임베딩에는 임베딩 모델 토큰을 쓴다. (싸고 한도가 채팅 모델과 따로)
- RAG 가 절약하는 건 **채팅 모델에 보내는 입력**이다. 문서 전체를 매번 프롬프트에 넣는 대신 질문과 가까운 상위 k 건만 보내므로 문서 수가 늘어도 입력이 일정하다.
- 단, 문서를 붙이지 않고 모델 지식만으로 답하는 경우보다는 토큰이 더 든다. 절약은 "전부 넣는 방식" 대비다.

**캐싱은 아니다**
- 캐싱 = 같은 요청의 결과를 저장해 뒀다가 재사용. 벡터 DB 는 지식을 찾아 주는 색인이라 같은 질문이 와도 임베딩 호출과 채팅 모델 호출은 그대로 일어난다.
- 비슷한 점: 문서 임베딩은 Day 8 에 한 번만 계산해 저장하고 검색 때 재계산하지 않는다. 다만 이것은 질문에 대한 답을 재사용하는 캐시가 아니다.

**진짜 캐싱 후보 (이 프로젝트에서)**
- 답변 캐시(Redis): 같은 질문의 답변을 저장해 채팅 모델 호출 자체를 없앤다. → 4주차 Redis 도입 때 실험 후보.
- 시맨틱 캐시: 이전 질문을 벡터 DB 에 저장해 두고, 의미가 거의 같은 질문이 오면 이전 답변을 재사용. 벡터 DB 의 응용 사례.
- 프롬프트 캐싱: 모델 쪽에서 프롬프트 앞부분이 같을 때 처리 결과를 재사용해 비용을 줄이는 기능.
