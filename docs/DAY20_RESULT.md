# Day 20 결과 — 에이전트 대화 상태를 Redis 에 저장하고 이어가기

> 구현과 실행 방법은 [DAY20_GUIDE.md](DAY20_GUIDE.md), 코드 흐름은 [DAY20_CODE_GUIDE.md](DAY20_CODE_GUIDE.md). 이 문서는 실행한 것과 확인한 결과를 담는다.
> 상태: 가이드 ② 의 질문 쌍(같은 세션 두 번, 세션 없이 한 번)과 ③ 세션 분리(`sessions` 조회 포함), ④ Spring → Kafka → FastAPI 경로, ⑧ 워커 두 대로 같은 세션에 동시 요청을 내 환경에서 실행해 기록함(2026-10-13). Spring 단위 테스트도 통과. ⑤~⑦ 은 직접 실행했다고 하나 출력을 남기지 않아 결과는 기록하지 않았다(6번).
> 포트: **8080 = Spring WAS**, **8000 = FastAPI 워커**, **6379 = Redis(`redis1`)**.

**전체 목적:** 지금까지 에이전트는 요청마다 새 대화로 시작해서 "그럼 그 기간이 지나면요?"처럼 앞 질문을 가리키는 질문에 답할 수 없었다. 같은 `sessionId` 로 온 요청이면 앞의 질문과 답을 Redis 에서 불러와 이어서 답하는지 확인한다.

## 1. 실행 환경

| --------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 호출 경로 | FastAPI(8000)의 `POST /api/v1/agent/run` 을 직접 호출 (Spring, Kafka 를 거치지 않음)                                                         |
| 세션 이름 | `d20-a`(3-1, 3-3), `d20-b`(3-3)                                                                                                              |
| 에이전트  | `provider=gemini`, 대화 저장은 Redis(`redis1`), 이전 대화 최대 10턴, 만료 3600초(기본값)                                                     |
| 실행 위치 | 내 환경(`d2-ai-python`, 가상환경 켠 상태). `redis-cli` 와 서버 터미널 로그는 이번 기록에 없다. 저장된 값은 3-3 에서 `sessions` API 로만 봤다 |

## 3. 확인된 결과

### 3-1. 같은 세션이면 앞 대화를 이어간다

**목적:** 두 번째 질문의 "그 기간"이 첫 질문의 환불 신청 기간을 가리킨다는 것을 모델이 아는지 본다.

| 순서 | 질문                                 | `session_id` | 답                                                                                                                                          |
| ---- | ------------------------------------ | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 환불은 며칠 안에 신청해야 하나요?    | `d20-a`      | 상품 수령 후 7일 이내에 신청 가능. 상품 하자나 오배송은 수령 후 30일 이내이고 무료. 단순 변심의 왕복 배송비는 고객 부담                     |
| 2    | 그럼 그 기간이 지나면 어떻게 되나요? | `d20-a`      | "환불 신청 가능 기간이 지난 경우에는 시스템상 환불 처리가 어렵습니다. 추가적인 도움이 필요하시다면 고객센터로 직접 문의해 주시기 바랍니다." |

두 번째 답은 "그 기간"을 환불 신청 가능 기간으로 이해하고 답했다. 두 번째 질문만으로는 어떤 기간인지 알 수 없는 문장이다.

### 3-2. 세션이 없으면 앞 대화를 모른다

**목적:** 같은 두 번째 질문을 `session_id` 없이 보냈을 때와 비교해, 3-1 의 이해가 세션(저장된 대화) 덕분인지 본다.

| 질문                                 | `session_id` | 답                                                                                                                                        |
| ------------------------------------ | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 그럼 그 기간이 지나면 어떻게 되나요? | 없음         | "어떤 기간에 대해 문의하시는 것인지 확인이 어려워 정확한 답변을 드리기 어렵습니다. 교환, 환불, 배송 등 구체적인 상황을 말씀해 주시면 ..." |

같은 질문인데 `session_id` 가 있으면 기간을 이해하고, 없으면 어떤 기간인지 되묻는다. 두 호출의 차이는 `session_id` 하나뿐이다.

### 3-3. 다른 세션은 섞이지 않는다

**목적:** 한 세션의 대화가 다른 세션으로 새지 않는지, 그리고 Redis 에 대화가 어떤 모양으로 저장되는지 본다.

| 순서 | 호출                                            | 결과                                                                                                                               |
| ---- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 4    | `d20-b` 로 "방금 내가 뭐라고 물었지?"           | "이전 대화 내용을 다시 확인해 보니, 방금은 저에게 질문을 하지 않으셨습니다. 혹시 쇼핑몰 이용과 관련하여 궁금하신 점이 있으신가요?" |
| 5    | `GET /api/v1/agent/sessions/d20-b`              | `turns` 1, `ttlSec` 3595, `messages` 2개(방금 한 질문, 위의 답)                                                                    |
| 6    | `d20-a` 로 같은 질문 "방금 내가 뭐라고 물었지?" | "환불 신청 가능 기간이 지난 경우 어떻게 되는지에 대해 물으셨습니다."                                                               |

- 같은 질문인데 `d20-b` 는 앞의 질문을 모르고, `d20-a` 는 직전 질문(3-1 의 두 번째 질문)을 정확히 말했다. 세션마다 대화가 따로 보관된다.
- `d20-b` 의 `turns` 가 1 이다. `d20-a` 의 대화(2턴 이상)가 섞였다면 이 값이 더 컸을 것이다. 저장된 `messages` 에도 `d20-a` 의 질문은 없다.
- `ttlSec` 3595 는 기본 만료 3600초에서 몇 초 지난 값이다. 저장할 때 TTL 이 걸린다는 뜻이다.
- `d20-b` 의 답은 "이전 대화 내용을 다시 확인해 보니"라고 말하지만, 실제로는 이전 대화가 없던 세션이었다. 모델이 이전 대화가 있는 것처럼 말한 표현이며 저장된 내용과는 맞지 않는다. 또 이번 질문 자체("방금 내가 뭐라고 물었지?")는 질문으로 세지 않았다.
- `d20-a` 의 `sessions` 조회(턴 수, 남은 시간)는 이번 기록에 없다.

### 3-4. Spring → Kafka → FastAPI 경로로도 이어간다

**목적:** 지금까지는 FastAPI(8000)를 직접 호출했다. Spring(8080)이 받은 `sessionId` 가 Kafka 메시지에 실려 FastAPI 워커까지 전달되고, 그 결과가 Redis 에 저장되는지 본다. 앞 질문이 `DONE` 이 된 뒤 다음 질문을 보냈다.

| 순서 | 호출                                                              | 결과                                                                                                                                                                 |
| ---- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 7    | Spring 에 "교환 시 배송비는 누가 부담하나요?" (`sessionId=d20-c`) | `ACCEPTED`. 결과 `DONE`, 워커 `w1`, partition 2, offset 8, `elapsedMs` 5307. 답: 교환 배송비는 고객님 부담, 사이즈나 색상 교환은 수령 후 7일 이내 1회 가능           |
| 8    | 같은 `d20-c` 로 "그럼 반품할 때는요?"                             | `ACCEPTED`. 결과 `DONE`, 워커 `w1`, partition 0, offset 81, `elapsedMs` 4039. 답: 단순 변심은 왕복 배송비 고객 부담, 하자나 오배송은 판매자 부담, 7일 이내 신청 가능 |
| 9    | `GET /api/v1/agent/sessions/d20-c`                                | `turns` 2, `ttlSec` 3588, `messages` 4개(질문1, 답1, 질문2, 답2 순서)                                                                                                |

- 9번에서 Spring 경로로 보낸 두 질문과 두 답이 `d20-c` 키에 순서대로 들어 있다. `sessionId` 가 Spring 컨트롤러, Kafka 메시지, FastAPI 워커를 거쳐 `run_agent` 까지 전달되어 저장에 쓰인 것이다. 컨트롤러가 `sessionId` 를 메시지에 담는 부분과 `AgentRequestMessage` 의 `sessionId` 해석이 이 실행에서 확인됐다.
- 두 요청은 서로 다른 partition(2, 0)에서 처리됐지만 같은 워커 `w1` 이었다. 워커가 하나라 모든 파티션을 `w1` 이 맡고 있어서다. 같은 세션의 요청이 다른 파티션으로 가도 대화는 Redis 한 키에 모인다는 것은 이 실행에서 보였다(워커가 둘일 때의 동작은 ⑧ 에서 본다).
- 8번 답이 앞 대화를 이용했는지는 이 답만으로 알 수 없다. "반품할 때는요?"는 앞 질문 없이도 반품 안내로 답할 수 있는 문장이고, 세션 없이 보낸 비교를 하지 않았다. 이어가기를 확인한 직접 증거는 9번의 저장된 대화이고, 답이 앞 대화를 이용한다는 확인은 3-1, 3-2 의 비교가 한다.
- `elapsedMs` 가 5.3초, 4.0초다. Day 18 에서 잰 건당 약 25~29초보다 훨씬 짧다. 왜 달라졌는지는 확인하지 않았다(이번 기록에는 `[timing]` 로그도 없다). 같은 환경인지, 모델 응답 시간이 변한 것인지 알 수 없다.
- 서버 로그의 `[timing] 이전 대화 N개 메시지` 는 확인하지 않았다.

### 3-5. 3-4 결과로 정리한 요청 흐름과 장애 시 동작

**목적:** 3-4 는 정상 상태에서 `sessionId` 가 전달되는지만 봤다. 이 결과를 실제 사용자가 쓰는 흐름에 놓고, 중간에 서버가 죽거나 화면을 새로고침하면 무엇이 남는지, 그리고 이 비동기 구조가 동기 호출과 무엇이 다른지를 코드와 이미 확인한 실험(Day 16, 17, 18)을 근거로 정리한다. 아래는 이번에 새로 실행한 결과가 아니라 **코드를 읽고 정리한 설명**이며, 확인하지 않은 부분은 따로 표시했다.

**실제 사용자 흐름**

| 순서 | 사용자(화면)                                                     | 시스템                                                                                                                               |
| ---- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 1    | 채팅창을 열면 화면이 `sessionId` 를 정한다(예: UUID)             | 서버는 `sessionId` 를 발급하지 않고 받은 값을 Redis(6379) 키로만 쓴다                                                                |
| 2    | 질문을 입력하면 Spring(8080)에 `{question, sessionId}` 를 보낸다 | Spring 이 `requestId` 를 만들어 Kafka 에 넣고 바로 `requestId` 와 `ACCEPTED` 를 돌려준다                                             |
| 3    | 로딩 표시, `requestId` 로 결과를 반복 조회(폴링)                 | FastAPI(8000) 워커가 Kafka 에서 꺼내 Redis 의 이전 대화를 읽고, 모델을 호출하고, 새 대화를 저장하고, 결과를 `requestId` 에 묶어 기록 |
| 4    | `DONE` 이 되면 답을 보여 준다                                    | -                                                                                                                                    |
| 5    | 다음 질문은 **같은 `sessionId`** 로 보낸다                       | 워커가 Redis 에서 앞 대화를 읽어 이어서 답한다                                                                                       |

- 사용자(화면)가 아는 서버는 Spring 하나이고 FastAPI 는 뒤쪽 워커다. FastAPI 의 `POST /api/v1/agent/run` 은 Kafka 없이 에이전트만 시험하려는 개발용 직접 경로이고, 3-1~3-3 의 실험이 이 경로였다.
- 3-4 에서 결과 조회를 FastAPI(8000)에 직접 한 것은 확인용이다. Spring 에는 결과 조회 API 가 아직 없어서 **지금 상태로는 실제 사용자가 답을 받아 볼 경로가 없다.**
- 폴링은 서버가 아니라 **프론트가 타이머로 돈다.** 서버는 조회 요청이 올 때마다 한 번 읽어 `PROCESSING`/`DONE`/`FAILED` 를 답할 뿐이다. `scripts/day17_e2e.sh` 가 하던 "1초마다 조회"가 화면이 하는 역할이다.
- 제한은 양쪽에 둔다. 서버는 에이전트 한 건에 최대 120초(`AGENT_TIMEOUT_SEC`)를 기다리고 넘으면 `FAILED` 로 기록한다. 프론트는 최대 대기 시간(또는 횟수)을 두고 넘으면 에러 메시지를 보이는 것이 보통이다. 프론트 제한이 서버보다 짧으면 화면은 에러인데 워커는 계속 처리해서 답이 나중에 저장될 수 있으니 두 값을 같이 정해야 한다. 이 값들은 아직 정하지 않았고 프론트도 만들지 않았다.

**중간에 죽거나 새로고침하면 무엇이 남는가**

| 상황                                                             | 결과 (코드 기준 예상)                                                                                                                                                      |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Kafka 에 들어간 뒤 Spring 이나 프론트가 죽음                     | 메시지는 Kafka 에 있으니 워커가 끝까지 처리한다. 대화는 Redis 에, 요청 결과는 워커 메모리에 기록된다                                                                       |
| 새로고침 후 `requestId` 로 결과 조회                             | 답이 보인다. 단 프론트가 `requestId` 를 보관해야 하고, Spring 의 결과 조회 API 가 있어야 하고(없음), 워커가 재시작되지 않아야 한다                                         |
| 새로고침 후 `sessionId` 로 대화 조회(`GET sessions/{sessionId}`) | 질문과 답이 순서대로 보인다. 단 프론트가 `sessionId` 를 보관해야 하고, 마지막 대화 후 1시간 이내, 최근 10턴 이내여야 한다                                                  |
| **처리 중에** 새로고침                                           | 대화 조회에는 그 질문이 아직 안 보인다. 대화는 답이 나온 뒤 한꺼번에 저장되기 때문이다(`run_agent` 의 ⑤)                                                                   |
| Spring 이 Kafka 에 넣기 **전에** 죽음                            | 질문 자체가 없던 일이 된다. 사용자는 `ACCEPTED` 를 받지 못했으므로 프론트가 재시도해야 한다                                                                                |
| 워커가 처리 도중 죽음                                            | 그 메시지는 commit 되지 않아 워커가 다시 뜨면 같은 메시지를 다시 받아 처음부터 처리한다(Day 16 에서 확인한 동작). 그 `requestId` 의 결과 기록은 사라졌다가 다시 만들어진다 |

정리하면 워커가 끝까지 살아 있으면 프론트나 Spring 이 죽어도 답은 사라지지 않는다. 다만 이것은 위 표의 조건을 갖췄을 때의 이야기다.

**지금 구조의 빈 곳**

| 항목                    | 내용                                                                                                                                                                                                         |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Spring 의 결과 조회 API | 없다. 결과 조회는 FastAPI 의 Day 17 임시 API 다                                                                                                                                                              |
| 요청 결과의 저장 위치   | 워커 메모리(`result_store`)다. 워커 재시작 시 사라지고, 개수 제한(`MAX_ENTRIES`)을 넘으면 오래된 것부터 밀리고, 워커가 여럿이면 처리한 워커에만 있다(Day 18). 대화(Redis)와 달리 아직 Redis 로 옮기지 않았다 |
| Redis 의 지속성         | compose 가 `docker-data/redis` 에 덤프를 남기게 되어 있지만 저장 주기와 재시작 후 복구는 확인하지 않았다(DAY19_RESULT 7번). "Redis 에 있으니 안전하다"고 말할 수 없다                                        |
| 영구 보관               | 오래 확실히 남기려면 질문과 답을 RDB 같은 영구 DB 에 따로 저장하고 Redis 는 빠른 조회와 임시 상태로 두는 구성이 보통이다. 이 프로젝트의 계획 범위인지는 확인하지 않았다                                      |
| 대화 길이와 만료        | 최근 10턴, 마지막 대화 후 3600초는 임시 정책이다(Day 24, CONVERSATION_CONTEXT_NOTES.md)                                                                                                                      |

**동기 호출과 비동기 구조**

| 방식                                  | 흐름                                                                                                                                       | 맞는 경우                                                     |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| 동기                                  | 화면 → 서버 → LLM 호출을 기다림 → 같은 연결로 응답. Kafka, `requestId`, 폴링이 없다. 이 프로젝트의 `POST /api/v1/agent/run` 이 이 방식이다 | 사용자가 적은 소규모 서비스. 구현이 단순하고 장애 지점이 적다 |
| 비동기 (Spring → Kafka → 워커 → 폴링) | 3-5 의 사용자 흐름                                                                                                                         | 사용자가 많거나 처리 시간이 긴 서비스                         |

- 동기 방식은 요청 하나가 20~30초 동안 서버의 스레드나 연결을 붙잡는다. 동시에 처리할 수 있는 수가 정해져 있어서 사용자가 그보다 많으면 줄을 서고, 그 대기 시간이 응답 시간에 더해진다. 로드밸런서나 게이트웨이에 응답 제한 시간이 있으면 에러로 보일 수 있다. 연결이 끊기면 결과 기록도 남지 않는다. 계산 예: 동시 처리 슬롯 10개, 건당 20초이면 초당 0.5건이다. 이 숫자는 이해를 돕는 계산이고 측정값이 아니다.
- 비동기로 바꿔도 **LLM 한 건이 빨라지지는 않는다.** 달라지는 것은 사용자 연결을 붙잡지 않는 것, 몰린 요청을 Kafka 에 쌓아 두었다가 워커가 감당하는 속도로 처리하는 것(에러 대신 느려짐)이다. 처리량 자체는 워커 수로 정해진다. 실측 근거는 Day 18 의 12건 처리다. 워커 1개 77초, 2개 38초, 3개 46초, 4개 49초이며, 3개 이후는 파티션 분배가 고르지 않아 이론값만큼 줄지 않았다(DAY18_RESULT 3번).
- 어느 사용자 수부터 동기와 비동기가 어떻게 갈리는지는 **측정하지 않았다.** 계획서의 k6 비교 실험이 이 숫자를 얻는 단계다. 그 전의 위 설명은 일반 원리로만 읽는다.

### 3-6. 같은 세션에 두 워커로 동시 요청 (선택 ⑧)

**목적:** 락이 없는 지금 구조에서, 같은 `sessionId` 로 두 워커가 동시에 대화를 저장할 때 한쪽 턴이 사라지는지 본다. 워커 두 대(포트 8000, 8001)에 `POST /api/v1/agent/run` 을 동시에 보냈다(`&` 와 `wait`). 8000 한 대에서는 이벤트 루프가 막혀 순서대로 처리되므로 경합이 생기지 않는다.

| 순서 | 호출                                       | 결과                                                                                                           |
| ---- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| 10-1 | 8000 에 "환불은 며칠 안에?" (`d20-race`)   | 답: 수령 후 7일 이내, 하자나 오배송은 30일 이내                                                                |
| 10-2 | 8001 에 "교환 배송비는 누가?" (`d20-race`) | 답: 교환 배송비는 고객 부담, 수령 후 7일 이내 1회 가능                                                         |
| 11   | `GET sessions/d20-race`                    | `turns` 2, `ttlSec` 3600, 메시지 4개: 환불 질문, 환불 답, 교환 질문, 교환 답 (두 답이 10-1, 10-2 와 같은 문장) |

- 이 실행에서는 **두 턴이 모두 저장됐다.** 유실은 보이지 않았다.
- 저장 순서는 환불, 교환이다. 어느 요청이 먼저 끝났는지는 이 출력으로 알 수 없다.
- 이 한 번의 결과로 "락이 필요 없다"고 말할 수 없다. 유실은 두 워커의 `append_turn` 읽기와 쓰기가 몇 밀리초 안에 겹쳐야 생기는데, 두 요청의 완료 시각은 보통 수 초 차이가 나서 한쪽이 쓴 뒤 다른 쪽이 읽는 경우가 더 흔하다(DAY20_CODE_GUIDE 4-1). 이번에 못 본 것이지 생기지 않는다는 증거가 아니다.
- 두 질문이 서로 무관해서, 한쪽이 상대 질문을 모르는 채 답했더라도 답에서 티가 나지 않는다. 시작 때 두 워커가 모두 빈 대화를 읽었는지는 `[timing] 이전 대화 N개 메시지` 로그를 보지 않아 확인하지 못했다.
- 실행 전에 `d20-race` 를 지웠는지 이 기록에는 출력이 없다. 결과가 이번 요청 두 개만 담고 있어서 깨끗한 상태에서 실행된 것으로 본다.

**겹치면 어떻게 되는가 (설명, 이번에 재현하지 못함)**

`append_turn` 은 "읽기 → 붙이기 → 통째로 쓰기"라서, 두 워커의 읽기와 쓰기가 몇 밀리초 안에 겹치면 나중에 쓴 쪽이 먼저 쓴 쪽의 턴을 덮어쓴다.

| 시각 | 워커 A (환불)             | 워커 B (교환)             | Redis 의 `d20-race`                          |
| ---- | ------------------------- | ------------------------- | -------------------------------------------- |
| t1   | `append_turn` 읽기 → `[]` | `append_turn` 읽기 → `[]` | `[]`                                         |
| t2   | `[환불Q, 환불A]` 쓰기     | `[교환Q, 교환A]` 쓰기     | 먼저 도착한 쪽이 저장                        |
| t3   |                           |                           | 나중에 도착한 쪽이 덮어씀 → 한쪽 턴이 사라짐 |

| 항목               | 내용                                                                                                                                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 결과               | `turns` 가 2 가 아니라 1. 한쪽 질문과 답이 통째로 없다. 에러가 나지 않고 조용히 사라진다                                                                                                                    |
| 사용자에게         | 그 시점의 두 답은 둘 다 정상으로 받는다. 그 뒤 사라진 턴을 가리키는 질문("아까 환불 말고…")에서 모델이 모르거나, 모르는 채 그럴듯하게 답할 수 있다                                                          |
| 어느 쪽이 사라지나 | 나중에 쓰는 쪽이 이기므로 매번 다를 수 있다                                                                                                                                                                 |
| 생기기 쉬운 경우   | 질문을 연달아 빠르게 보냄, 같은 대화를 두 탭에서 사용, 재시도가 겹침 (일반적인 예이고 이번에 확인한 것이 아니다)                                                                                            |
| 막는 방법          | 같은 세션을 저장하는 동안 한 번에 한 워커만 들어오게 하는 락. 예: Redis 의 `SET key value NX EX` 로 락 키를 잡은 워커만 읽고 쓰고, 못 잡은 쪽은 기다린다. Day 21 에서 만들고 Day 22 에서 락 유무를 비교한다 |

이 유실은 이번 실행에서 직접 본 적이 없다. 위는 코드 흐름(`append_turn`)에서 읽은 설명이다.

**트러블슈팅: 같은 세션 이름으로 다시 실행했더니 요청 수보다 많은 턴이 쌓여 있다**

**증상:** 요청 두 개를 보냈는데 `GET sessions/d20-race` 가 `turns` 4, 메시지 8개였다. 요청 수와 맞지 않아 그 결과로는 유실 여부를 판단할 수 없었다.

| 순서 | 질문                | 답의 끝부분                                                | 그 실행의 출력과              |
| ---- | ------------------- | ---------------------------------------------------------- | ----------------------------- |
| 1    | 교환 배송비는 누가? | "…수령 후 7일 이내에 신청해 주세요."                       | 일치하는 출력 없음            |
| 2    | 환불은 며칠 안에?   | "…단순 변심에 의한 환불 시 왕복 배송비는 고객 부담입니다." | 그 실행의 환불 답과 같은 문장 |
| 3    | 환불은 며칠 안에?   | 2번과 질문, 답이 완전히 같음                               | 그 실행의 환불 답과 같은 문장 |
| 4    | 교환 배송비는 누가? | "…교환이 가능합니다." (1회에 한해)                         | 그 실행의 교환 답과 같음      |

**원인 (추정):** 앞서 실행이 에러로 끝난 시도(Redis 가 꺼진 상태에서 한 실행 등)를 반복하면서, 같은 `session_id` (`d20-race`)를 지우지 않고 다시 보냈다. 이 키는 마지막 저장 후 3600초 동안 Redis 에 남으므로, 앞 실행들에서 저장된 턴이 새 실행의 결과에 섞여 보였다. 목록에서 그 실행의 두 턴(환불, 교환)은 출력과 맞았고 나머지 두 턴은 맞지 않았다. 다만 2번과 3번이 질문도 답도 같은 문장인 이유는 설명하지 못했다. 같은 요청이 두 번 저장된 것인지, 같은 답이 우연히 나온 것인지 알 수 없다.

**대처:** 이 실험은 "이번 실행의 요청 수 = 저장된 턴 수"인지를 보는 것이므로 시작 상태가 깨끗해야 한다.

| 순서 | 할 일                                                                                                                       | 이유                                                                                                      |
| ---- | --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 1    | `curl -s localhost:8000/health` 의 `redis.connected` 가 `true` 인지 확인 (두 워커 모두. Redis 가 켜져 있어야 함)            | 꺼진 채로 보내면 두 요청 모두 읽기와 저장에 실패하고 답만 정상으로 와서, 실험이 아무것도 보여 주지 못한다 |
| 2    | `curl -s -X DELETE localhost:8000/api/v1/agent/sessions/d20-race` 로 이전 기록을 지운다 (또는 매번 새 `session_id` 를 쓴다) | 앞 실행의 턴이 섞이지 않게 한다                                                                           |
| 3    | `GET sessions/d20-race` 가 404 인지 확인한 뒤 요청을 보낸다                                                                 | 시작이 빈 상태임을 확인한다                                                                               |
| 4    | 요청 두 개를 보내고 `GET sessions/d20-race` 의 `turns` 를 요청 수와 비교한다                                                | 같으면 유실 없음, 적으면 유실                                                                             |
| 5    | 두 워커 터미널에 `대화 기록을 못 불러옴`, `못 저장함` 경고가 있는지 본다                                                    | 경고가 있으면 그 실행은 Redis 문제로 무효다                                                               |

**이렇게 다시 한 결과:** 위 순서로 지운 뒤 한 번만 실행했더니 `turns` 2, 메시지 4개로 요청 수와 맞았다(위의 11번). 지우는 출력은 받지 못했지만 결과가 이번 요청 두 개만 담고 있어서 깨끗한 상태로 본다.

**일반 교훈:** 대화가 TTL 동안 남는 구조라서, 같은 `session_id` 를 쓰는 테스트는 매번 시작 전에 지우거나 새 이름을 써야 이전 결과가 섞이지 않는다. 이 문제는 락과 무관한 시험 환경의 문제이므로 유실로 오해하지 않도록 구분한다.

## 4. 해석

| 확인한 것                                                  | 의미                                                                                                                                                                         |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 같은 질문의 답이 `session_id` 유무로 갈림                  | 요청 사이에 앞 대화가 전달됐다는 간접 증거다. 요청마다 새 대화였던 Day 19 까지와 달라진 점이다                                                                               |
| 가이드 ② 의 기대와 같은 결과                               | 세션 있을 때는 기간을 이해하고, 없을 때는 되묻는 것으로 예상했고 그대로 나왔다                                                                                               |
| `d20-b` 의 `turns` 가 1, 저장된 메시지에 `d20-a` 질문 없음 | 세션이 키(`agent:conversation:<sessionId>`)별로 분리돼 저장되고, 다른 세션의 대화가 섞이지 않았다(3-3). 대화가 Redis 에 실제로 저장되고 TTL 이 걸린다는 직접 증거이기도 하다 |
| Spring 경로의 `d20-c` 가 `turns` 2, 메시지 4개 (3-4)       | `sessionId` 가 Spring → Kafka → FastAPI 로 전달되어 같은 키에 순서대로 저장된다. 직접 호출뿐 아니라 실제 서빙 경로에서도 대화가 쌓인다                                       |
| 두 번째 답이 "7일" 같은 숫자를 다시 말하지 않음            | 답은 "기간이 지나면 환불 처리가 어렵다"는 일반적인 안내다. 이어가기는 됐지만 앞 답의 세부 내용을 구체적으로 인용했는지는 이 답만으로 알 수 없다                              |

| 서버 로그                                  | `[timing] 이전 대화 0개 / 2개 메시지` 로그를 확인하지 않았다                                                                                                                                                                                           |
| 한 번씩만 실행                             | LLM 답은 매번 달라질 수 있다. 같은 실험을 반복하지 않아 이어가기와 분리가 항상 되는지는 모른다. 세션 분리는 두 세션 한 쌍으로만 봤다                                                                                                                   |
| Spring 경로의 이어가기 품질                | 3-4 의 두 번째 답이 앞 대화를 이용했는지는 비교 실험(세션 없이 같은 질문)을 하지 않아 알 수 없다. 저장이 된 것만 확인했다                                                                                                                              |
| Spring 경로의 응답 시간 단축 원인          | 건당 4~5초로 이전 측정(약 25~29초)보다 짧았지만 원인은 모른다                                                                                                                                                                                          |
| 같은 세션 동시 요청의 유실 (3-6)           | 한 번 실행해 유실을 보지 못했다. 반복하지 않았고 겹치게 만든 실험도 하지 않아 "유실이 없다"는 결론은 낼 수 없다. Day 22 에서 다룬다                                                                                                                    |
| 서버 중단 시나리오 (3-5)                   | 처리 중 Spring/프론트/워커/Redis 를 끄거나 새로고침했을 때의 동작은 코드를 읽고 정리한 예상이다. Day 16 의 워커 중단 실험을 제외하고 이번에 실행하지 않았다                                                                                            |
| 동기와 비동기의 성능 갈림 지점             | 동시 사용자 수에 따른 차이를 측정하지 않았다(k6 비교 실험 전). 3-5 의 슬롯 계산은 이해용 예시다                                                                                                                                                        |
| Spring 경로의 `sessionId` 빈 문자열, 101자 | 빈 문자열(null 처리)이나 101자(400)로 보냈을 때를 실행하지 않았다                                                                                                                                                                                      |
| 선택 ⑤~⑦                                   | `redis-cli` 로 저장된 모양, 만료, Redis 중지 중 요청은 직접 실행했다는 보고만 있고 **출력과 로그를 받지 못했다**(뻔한 결과라 대충 확인했다고 함). 무엇이 나왔는지 이 문서에 근거가 없으므로 동작은 코드를 읽은 예상으로만 남는다(DAY20_CODE_GUIDE 3번) |
| 응답 시간                                  | 이번 기록에 시간이 없다. 이전 대화가 길수록 느려지는지 재지 않았다                                                                                                                                                                                     |
