# LangChain vs LangGraph — 개념 정리

> Day2(`agent_core.py`)와 Day3(`agent_graph.py`)가 왜 다른지, 실제로 뭐가 다른지 정리한 문서.

## 한 줄 요약

**LangGraph는 LangChain과 대립하는 게 아니라, LangChain 위에 얹는 "흐름 제어 확장 도구"다.**

```
LangChain (전체 생태계)
   │
   ├── 기본 구성요소
   │     - 모델 래퍼: ChatGoogleGenerativeAI, ChatAnthropic
   │     - 도구 정의: @tool 데코레이터
   │     - bind_tools(): 모델에 도구를 연결
   │     → Day2(agent_core.py)는 이것만 사용, 반복 로직은 직접 for문으로 작성
   │
   └── LangGraph (상태 기반 흐름 제어 확장 라이브러리)
         - StateGraph: 여러 Node를 그래프로 연결
         - Conditional Edge: 조건에 따라 다음 Node를 자동 분기
         - 순환(loop)을 코드가 아니라 그래프 구조로 표현
         → Day3(agent_graph.py)는 이 위에 얹어서 사용
```

즉 두 파일 모두 **같은 모델, 같은 도구를 쓰고 있음**. 차이는 "도구를 여러 번 호출해야 할 때 그 반복을 누가 관리하느냐"뿐이다.

---

## Day2 vs Day3 코드 레벨 비교

| 항목 | Day2 — `agent_core.py` (LangChain, 수동 루프) | Day3 — `agent_graph.py` (LangGraph) |
|---|---|---|
| 사용 라이브러리 | LangChain 기본 구성요소만 | LangChain + LangGraph |
| 반복(루프) 제어 | `for tool_call in ai_response.tool_calls:` 를 개발자가 직접 작성 | `tools → agent` 엣지로 그래프 엔진이 자동 순환 |
| 상태(대화 히스토리) 관리 | `messages` 라는 일반 리스트에 직접 append | `AgentState` (TypedDict)로 명시적 선언, `add_messages` 리듀서가 자동 관리 |
| 도구가 여러 번 연쇄로 필요한 경우 | 지금 코드는 도구를 **1번만** 처리하고 끝나도록 짜여 있음 (2차 호출까지만) → 3번째 호출이 필요하면 코드를 다시 뜯어야 함 | 모델이 "도구 더 필요해"라고 판단하면 그래프가 자동으로 `agent`로 돌아가 계속 처리함 |
| 기능 확장 (예: 재시도 로직) | `run_agent()` 함수 전체를 다시 고쳐야 함 | 노드 하나(`retry_node`)만 추가하고 엣지만 연결하면 됨 |
| 코드 복잡도 (지금 시점) | 단순, 읽기 쉬움 | 상대적으로 개념(State/Node/Edge)을 먼저 이해해야 함 |

---

## 비유로 이해하기

- **Day2 (LangChain 수동 루프)** = **직접 운전**해서 목적지까지 가는 것.
  갈림길이 나올 때마다 내가 직접 판단하고 핸들을 꺾는다.

- **Day3 (LangGraph)** = **내비게이션 켜고** 운전하는 것.
  갈림길(Conditional Edge)마다 내비게이션이 알아서 경로를 판단해서 안내해준다.
  목적지(최종 답변)는 똑같이 도착하지만, 경로가 복잡해질수록(도구 호출이 여러 번 얽힐수록)
  내비게이션이 있는 쪽이 훨씬 안정적이다.

---

## 그래서 왜 지금 시점엔 결과가 똑같이 나왔나

지금까지 테스트한 질문("환불 정책이 어떻게 되나요?")은 **도구를 딱 1번만 호출하고 끝나는 단순 케이스**라서,
Day2 방식과 Day3 방식 둘 다 동일하게 잘 작동한다.

차이가 드러나는 건 **도구가 여러 번 연쇄로 필요한 복잡한 질문**일 때다.

예: "환불 정책 찾아보고, 그거 관련 리뷰도 찾아서 요약해줘"
→ 검색을 2번 해야 하는 상황

| | Day2 (수동 루프) | Day3 (LangGraph) |
|---|---|---|
| 처리 결과 | 도구 1번 호출하고 답변으로 끝나버려서, 두 번째 검색이 필요해도 처리 못 함 (코드 재작성 필요) | `tools ↔ agent`를 필요한 만큼 자동으로 순환하며 처리 |

---

## 이 프로젝트에서 LangGraph를 쓰는 진짜 이유

1. **State를 명시적으로 선언**해두면, 이 State를 그대로 Redis에 직렬화해서 저장하기 쉬워짐
   → 4주 차 "세션 상태 관리" 작업과 자연스럽게 연결됨
2. **Node/Edge 단위로 분리**되어 있어서, Self-Correction(실패 시 재시도) 같은 로직을
   노드 하나만 추가/수정하는 걸로 확장 가능
   → 6주 차 "재시도 로직" 작업과 연결됨
3. **표준 프레임워크 사용 경험**이라 "왜 이 구조를 택했는가"를 설명하기 쉬움

---

## 결론 한 줄

Day2와 Day3는 "체인 vs 그래프"라는 대립이 아니라,
**"LangChain을 손으로 직접 배선했는가(Day2), LangGraph라는 상위 프레임워크에 흐름 제어를 맡겼는가(Day3)"**의 차이다.
지금 프로젝트는 Day3(LangGraph) 버전을 기준으로 계속 진행한다.
