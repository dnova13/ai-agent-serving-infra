# Day 28 가이드 — 고부하 Breakpoint 탐색 (비동기 접수 경로)

> 상태: **①(계단 부하), ②(쉬지 않고 보내기), ④(선택, 계단 늘리기) 실행 완료**(DAY28_RESULT 3-1, 3-2, 3-3). ③ 의 비우기는 하지 않기로 했다. 아래 기대값은 모두 "확인 전 예상"이다.
> 포트: **8080 = Spring WAS**, **8000 = FastAPI 워커 1**(이번에는 끄고 시험), **6379 = Redis(redis1 컨테이너)**, 9092 = Kafka, 6333 = Qdrant.
> 앞선 결과: [DAY25_RESULT.md](DAY25_RESULT.md)(VU 300 까지 한계 없음), [DAY27_RESULT.md](DAY27_RESULT.md)(비동기 VU 20, 접수 p(95) 약 22~26ms).

**전체 목적:** Day 25 ⑥ 에서 VU 300 까지 올려도 비동기 접수(Spring → Kafka, 202 응답)의 한계 지점을 찾지 못했다. 오늘은 부하를 VU 100 에서 1000 까지 계단식으로 올리며(①), 접수 응답 시간(p95)이 기준(2초)을 넘거나 접수 성공 비율이 99% 아래로 떨어지는 첫 계단, 즉 Breakpoint 를 찾는다. 1000 까지 올려도 한계가 안 나오면 VU 당 요청 속도를 크게 올려(②) 한계를 찾는다. 어느 쪽이든 "무엇이 먼저 한계에 닿는가"(Spring, Kafka, k6 자신, 로그 출력)를 자원 사용량과 함께 기록한다.


Day 28 은 부하를 계속 올리다가 처음으로 안 좋은 현상이 나오는 지점(Breakpoint)을 찾는 실험이다.

여기서 "안 좋은 현상"의 기준은 다음과 같다.

- 접수 응답 시간 p95 가 2초를 넘는 경우
- 접수 성공(202) 비율이 99% 아래로 떨어지는 경우
- 503(Kafka 전송 실패), 연결 실패 같은 에러가 나오는 경우

| ---------------------------------------------------------------------------------------------------- | ---- |

## 2. 개념

| 항목                        | 내용                                                                                                                                                                              |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Breakpoint                  | 부하를 올리다가 처음으로 "기준을 넘는" 지점. 이번 기준은 계단별 접수 응답 시간 p(95) 2초 미만(Day 25 의 임시 기준과 같음), 접수 성공(202) 비율 99% 초과다. 처음 FAIL 이 나온 계단이 Breakpoint 다 |
| 계단 부하                   | VU 를 한 단계로 올린 뒤 일정 시간(기본 40초) 머물고 다음 단계로 올린다. 한 번에 직선으로 올리는 Day 25 의 ramping 과 달리, 계단마다 값을 따로 얻어 어디서 꺾이는지 보인다                  |
| 닫힌 모델과 요청 속도       | VU 는 응답을 받은 뒤 THINK_SEC 를 쉬고 다음 요청을 보낸다. 접수가 약 10ms 로 끝나면 VU 하나가 초당 약 1건이라 VU 1000 은 초당 약 1000건이다. THINK_SEC 가 0 이면 VU 하나가 초당 수십~100건 이상을 보낸다 |
| 접수 경로가 하는 일         | Spring 이 requestId 를 만들고 Kafka 에 `acks=all` 로 보내 저장 응답을 기다린 뒤 202 를 돌려준다(Day 20). 이 경로는 워커가 필요 없어서, 이번에는 워커를 끄고 접수만 잰다                          |
| k6 자신이 병목일 수 있음    | k6, Spring, Kafka 가 한 PC 에서 돈다. k6 의 CPU 가 포화되면 측정 한계가 서버가 아니라 k6 쪽이다. 그래서 자원 샘플러가 k6 와 Spring 의 CPU 를 같이 기록한다                                       |
| 열 수 있는 파일 한도        | VU 마다 연결(소켓)을 열기 때문에 macOS 기본 한도(256)로는 수백 VU 에서 연결이 실패한다. 실행 스크립트가 `ulimit -n 10240` 으로 올린다(그 터미널에서만 적용)                                    |
| 계단별 지표 이름표          | 요청마다 `step` 이름표(계단의 VU 수, 올리는 구간은 `ramp`, 내리는 구간은 `down`)를 붙여 요약에 계단별 값이 나온다                                                                  |


### 2-1. 이번 실험에 쓰이는 k6 태그

태그는 k6 가 측정값(지표)에 붙이는 이름표다. 같은 지표를 태그별로 나눠 볼 때 쓴다. 이번 실험(`breakpoint.js`)에서 쓰는 태그는 아래 세 가지다.

| 태그                | 누가 붙이나          | 값                                                                                                  | 쓰임                                                                                                                  |
| ------------------- | -------------------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `name`              | 스크립트(요청의 `tags`) | `POST /api/agent/requests`                                                                          | 접수 요청의 응답 시간을 다른 요청과 구분한다(이번 시험에는 이 요청 하나뿐). 계단별 응답 시간 기준의 조건에 들어간다   |
| `step`              | 스크립트(요청의 `tags`, 사용자 정의 지표의 `add`) | 계단의 VU 수(`100`, `200`, … `1000`), 올라가는 구간 `ramp`, 마지막에 내려가는 구간 `down`              | 어느 부하 구간에서 보낸 요청인지를 나타낸다. 계단별로 나눠 보려는 용도다                                              |
| `expected_response` | k6 가 자동으로         | `true`(응답 상태 코드가 200~399), `false`                                                           | 요약의 `{ expected_response:true }` 줄. 이번 시험의 접수 응답 202 는 `true` 다                                         |

`step` 의 값은 이렇게 정해진다.

| 값          | 뜻                                                                |
| ----------- | ----------------------------------------------------------------- |
| `step:100`  | 100 VU 계단에 머무는 40초 동안 보낸 요청                           |
| `step:1000` | 1000 VU 계단에 머무는 40초 동안 보낸 요청 (숫자는 그 계단의 VU 수) |
| `ramp`      | 다음 계단으로 올라가는 10초 동안 보낸 요청                         |
| `down`      | 마지막에 0 으로 내려가는 구간의 요청                               |

태그가 붙는 지표와 결과 요약에서 보이는 모습은 다음과 같다.

| 지표                                                  | 종류          | 붙는 태그                          | 요약에서 보이는 줄                                                              |
| ----------------------------------------------------- | ------------- | ---------------------------------- | ------------------------------------------------------------------------------- |
| `http_req_duration` (접수 응답 시간)                  | k6 내장       | `name`, `step`, `expected_response` | `{ name:POST /api/agent/requests,step:100 }` = 계단별 응답 시간. 계단별 p(95) 기준을 건다 |
| `http_reqs` (요청 수)                                 | k6 내장       | `step`                             | `{ step:100 }` = 계단별 요청 수                                                  |
| `accepted` (접수 성공 비율)                           | 사용자 정의   | `step`                             | `{ step:100 }` = 계단별 성공 비율. 계단별 99% 초과 기준을 건다                    |
| `status_202`, `status_503`, `status_other_5xx`, `status_0`, `status_other` (응답 코드별 개수) | 사용자 정의 | `step`                             | `{ step:100 }` = 계단별 응답 코드 개수. 값을 보이게 하는 표시용이다               |

| 항목                          | 내용                                                                                                                                         |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 태그를 붙이는 이유            | k6 는 기본으로 시험 전체를 하나로 합쳐 보여 준다. `step` 태그가 있어야 계단마다 p(95), 성공 비율, 요청 수를 따로 보고 처음 꺾이는 계단(Breakpoint)을 찾을 수 있다 |
| `ramp`, `down` 은 요약에 없음 | 요약에는 `step:100` ~ `step:1000` 처럼 계단 값만 나온다. 그래서 계단별 요청 수를 모두 더하면 전체 요청 수보다 적다                            |
| 계단별 `/s` 값                | 그 계단의 요청 수를 시험 전체 시간으로 나눈 값이라 그 계단의 실제 초당 요청 수가 아니다. 실제 초당 값은 요청 수 ÷ 머문 시간(40초)으로 계산한다 |
| k6 의 그 밖의 기본 태그       | k6 는 `method`, `status`, `url`, `scenario` 같은 태그도 자동으로 붙이지만 이번 실험의 기준이나 요약에는 쓰지 않는다                           |
| 실행 명령의 `step1`           | `bash scripts/k6/run-breakpoint.sh step1` 의 `step1` 은 결과 파일 이름(`day28-step1-k6.txt`)일 뿐 `step` 태그와 상관없다                       |

## 5. 실행과 확인

실험은 프로젝트 루트에서 실행한다. 명령은 한 줄이다(줄바꿈 없이 그대로 붙여 넣는다). 앞 실험에서 쌓인 요청이 섞이지 않도록 ① 과 ② 사이, 그리고 ② 뒤에 ③ 의 비우기를 한다.

### ① 계단 부하 VU 100 → 1000 (요청 사이 1초 쉼)

**목적:** 접수 경로가 VU 1000 까지 기준(p(95) 2초 미만, 성공 99% 초과)을 지키는지, 아니면 어느 계단에서 처음 넘는지 본다.

```bash
bash scripts/k6/run-breakpoint.sh step1
```

계단은 100, 200, 400, 600, 800, 1000 이고 각각 올리는 10초 + 머무는 40초이며, 마지막에 10초 동안 0 으로 내린다. 총 약 5분 10초다. 끝나면 k6 요약 뒤에 자원 기록이 이어서 출력된다. 두 부분을 모두 붙여 주면 된다.

| 항목                                                   | 기대값 (확인 전 예상)                                                                                                         |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| 계단별 접수 p(95) (`step:100` ~ `step:1000`)           | 모두 수십 ms 이하 (Day 25 ⑥ 은 300 VU 에서 14.71ms). 마지막 계단(1000) 쪽에서 올라가기 시작할 수 있다                         |
| 계단별 `accepted`                                      | 모두 100%. 한계가 있다면 가장 높은 계단부터 떨어질 가능성이 높다                                                               |
| Breakpoint (계단별 임계값이 처음 FAIL 인 계단)         | 없을 가능성이 높다 (Day 25 에서 300 VU 까지 한계가 없었고, 1000 VU 는 초당 약 1000건 수준). 있다면 800~1000 계단일 것으로 본다   |
| 계단별 `status_503`, `status_0`, `status_other_5xx`    | 한계가 없으면 0. 한계가 나타나면 `status_0`(연결 실패, 10초 초과)이나 `status_503`(Kafka 전송 5초 초과)이 먼저 나올 것으로 본다 |
| 계단별 `http_reqs`                                     | 계단의 VU 수에 거의 비례한다. 40초 × VU 수 정도(VU 1000 계단이면 약 4만 건)                                                   |
| 자원 기록: k6 CPU                                      | 100% 미만이면 k6 가 병목이 아니다. 1000 VU 에서 코어 하나 이상을 쓸 수 있다                                                    |

### ② 쉬지 않고 보내기 (VU 10 → 200, 요청 사이 쉼 없음)

**목적:** ① 에서 한계가 안 나왔을 때, VU 당 요청 속도를 크게 올려 한계가 Spring 인지, Kafka 인지, k6 자신인지 본다. ① 에서 이미 Breakpoint 가 나왔다면 이 실험은 하지 않아도 된다.

```bash
bash scripts/k6/run-breakpoint.sh hammer -e STEPS=10,25,50,100,200 -e THINK_SEC=0
```

계단은 10, 25, 50, 100, 200 이다. 총 약 4분 10초다. 쉬지 않으므로 VU 하나가 초당 수십~100건 이상을 보낸다.

| 항목                                          | 기대값 (확인 전 예상)                                                                                                                    |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 계단별 `http_reqs`                            | 계단이 커질수록 늘다가 어느 계단부터 증가가 둔해진다 (한 PC 의 처리 한계). 둔해지는 계단이 처리량 한계 부근이다                              |
| 계단별 접수 p(95)                             | 낮은 계단에서는 수 ms~수십 ms, 처리량이 꺾이는 계단부터 올라간다(닫힌 모델이라 요청이 줄고 응답 시간이 늘어난다)                            |
| 자원 기록 (k6, Spring CPU)                    | 먼저 100% 에 닿는 쪽이 병목 후보다. k6 가 먼저면 측정 한계가 k6 이고 Spring 의 한계는 아직 모른다                                           |
| 실패(`status_0`, `status_503`)                | 한계가 나오면 처리량 정체 뒤에 나타날 가능성이 높다. 나오지 않을 수도 있다                                                                |

### ③ 쌓인 요청 비우기

**목적:** ①, ② 에서 접수한 요청(① 은 수만 건)이 Kafka 에 남아 있으므로 다음 시험 전에 비운다.

워커가 꺼진 채로 실행한다(Kafka 그룹에 붙어 있으면 실패한다). 먼저 비우기 전의 LAG 를 본다(① 의 접수 건수 약 15.4만 건 중 얼마가 남았는지, 시험 중 워커가 읽었는지 확인하는 용도).

```bash
docker exec kafka kafka-consumer-groups --bootstrap-server kafka:29092 --group agent-workers --describe
```

이어서 비운다.

```bash
docker exec kafka kafka-consumer-groups --bootstrap-server kafka:29092 --group agent-workers --topic agent.requests --reset-offsets --to-latest --execute
```

| 항목              | 기대값 (확인 전 예상)                                                              |
| ----------------- | ---------------------------------------------------------------------------------- |
| 출력의 NEW-OFFSET | 파티션 0~2 마다 이전보다 큰 값(① 의 접수 건수만큼 늘어난 위치). 오류 없이 끝난다    |

바로 이어서 `--describe` 로 LAG 가 0 인지 볼 수 있다.

```bash
docker exec kafka kafka-consumer-groups --bootstrap-server kafka:29092 --group agent-workers --describe
```


### ④ (선택) 계단 늘리기 (VU 300 → 800, 쉬지 않고 보내기)

**목적:** ② 에서도 한계가 안 나왔을 때, 계단을 더 크게(VU 300, 400, 600, 800) 올려 한계를 찾는다. 기준(p(95) 2초 미만, 성공 99% 초과)을 처음 넘는 계단에서 시험이 멈추게 한다(`ABORT=1`). ② 에서 이미 한계가 나왔다면 하지 않는다.

**시험 전에** 워커를 모두 끄고, Kafka 디스크 사용량과 디스크 여유를 기록한다. 프로젝트 루트에서 실행한다.

```bash
du -sh docker-data/kafka
```

```bash
df -h .
```

```bash
bash scripts/k6/run-breakpoint.sh hammer2 -e STEPS=300,400,600,800 -e THINK_SEC=0 -e ABORT=1
```

계단은 300, 400, 600, 800 이고 각각 올리기 10초 + 머물기 40초이며, 마지막에 10초 동안 0 으로 내린다. 끝까지 가면 약 3분 30초이고, 기준을 넘는 계단이 나오면 거기서 멈춘다. 결과 파일 이름은 `hammer2` 라서 ② 의 결과(`hammer`)를 덮어쓰지 않는다. **시험 뒤에** 같은 두 명령으로 Kafka 디스크 사용량을 다시 기록한다.

| 항목                                          | 기대값 (확인 전 예상)                                                                                                                     |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 계단별 요청 속도                              | VU 수에 비례, VU 당 약 91~104건/초(② 의 값). 계단 300 은 약 3만, 800 은 약 8만 건/초                                                       |
| Breakpoint                                    | 없을 가능성이 높다 (② 에서 VU 200, 초당 약 2만 건까지 없었다). 있다면 `status_0`, `status_503` 이 먼저 나타나거나 p(95) 가 급격히 오른다   |
| 자원 (k6, Spring CPU)                         | ② 마지막 계단(k6 231.7%, Spring 317.2%)보다 높다. 먼저 한계에 닿는 쪽이 병목 후보다(이 PC 의 코어 수는 확인하지 않았다)                       |
| `ABORT=1` 로 멈췄다면                          | 멈춘 계단이 Breakpoint 다. 이때 k6 CPU 가 먼저 포화돼 있으면 "서버 한계"가 아니라 "이 PC 의 측정 한계"로 기록한다                            |
| Kafka 디스크 증가                             | 약 2.7GB (아래 표의 계산. 끝까지 갔을 때)                                                                                                  |

**Kafka 디스크 사용량 주의**

| 항목                       | 내용                                                                                                                                                                          |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 요청이 디스크에 쌓인다     | 접수한 요청은 Kafka 에 저장되고, 워커가 읽어 가도 바로 지워지지 않는다. 이 compose 는 보존 설정을 바꾸지 않았다(기본 보존 기간은 확인하지 않았다)                              |
| 저장 위치                  | `docker-data/kafka` (프로젝트 폴더에 연결한 폴더). Docker 볼륨이 아니라서 `docker system df` 에는 잡히지 않는다. `du -sh docker-data/kafka` 로 본다                           |
| 지금까지 측정한 값         | ①, ② 뒤 562MB, 메시지 약 209만 건이므로 한 건당 약 270바이트(계산). 이 디스크의 여유는 554GB                                                                                   |
| ④ 의 예상 증가             | 약 1,000만 건 × 약 270바이트 = 약 2.7GB (계산한 추정). 계단별 건수는 VU × 약 100건/초 × 40초로 계산했다(300 → 약 120만, 400 → 약 160만, 600 → 약 240만, 800 → 약 320만 건, 합 약 840만 건). 여기에 올리는 구간의 요청을 더했다(② 에서는 그 구간이 계단 합의 약 25%였다)    |
| 시험 전 확인               | `df -h .` 의 여유가 예상 증가(약 2.7GB)보다 충분히 큰지 본다. 여유가 부족하면 하지 않는다                                                                                      |
| 시험 중                    | 디스크 여유가 빠르게 줄어들면 `Ctrl+C` 로 멈춘다                                                                                                                               |
| ③ 의 비우기와 디스크       | ③ 은 읽은 위치만 옮기므로 **디스크 사용량은 줄지 않는다.** 디스크를 줄이려면 토픽을 지우거나 보존 기간을 줄여야 하는데, 이번 가이드 범위 밖이라 방법은 적지 않았다                 |
| 워커를 켜면                | 쌓인 요청이 많을수록 워커가 처리하려는 양도 많아진다. 다음 Kafka 실험 전에는 ③ 의 비우기를 해야 한다                                                                           |


## 6. 확인하지 않은 것

| 항목                                                                        | 상태                                                               |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 위 기대값 전체                                                              | 실행 전 (확인 전 예상)                                             |
| ④ 의 Kafka 디스크 증가(약 2.7GB), 건당 약 270바이트 | 측정값으로 계산한 추정. ④ 를 실행한 뒤 `du -sh docker-data/kafka` 로 확인해야 한다 |
| `breakpoint.js` 의 실행                                                     | 문법만 확인했다. 샌드박스에는 k6 와 Spring 이 없어 실행하지 못했다  |
| Spring 접수 경로의 로그 출력이 병목인지                                     | 미확인. 요청마다 INFO 로그를 찍으므로 초당 1000건 이상에서 로그 출력이 한계에 영향을 줄 수 있다 |
| 실제 LLM 이 아니라 가짜 LLM 기준                                            | 접수 경로는 LLM 과 무관해 영향이 없을 것으로 보지만 직접 확인하지 않았다 |


## 7. 알려진 한계

| 항목                              | 내용                                                                                                                              |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 한 PC 에서 모두 실행              | k6, Spring, Kafka(docker), Redis 가 한 PC 를 나눠 쓴다. Breakpoint 는 이 PC 의 값이고, 운영 서버의 한계가 아니다                  |
| 접수 경로만 시험                  | 워커를 끄고 접수만 잰다. 결과 조회, 워커 처리는 이번 시험의 대상이 아니다                                                           |
| 계단마다 40초                     | 짧은 시간이라 메모리 증가나 Kafka 디스크 같은 느린 한계는 보이지 않을 수 있다                                                       |
| 한 번씩만 잰다                    | 반복 측정을 하지 않아 편차를 알 수 없다. 기준 근처의 계단은 결과가 흔들릴 수 있다                                                  |
| 기준값은 임시                     | p(95) 2초, 성공 99% 는 Day 25 의 임시 기준이다. 기준을 바꾸면 Breakpoint 도 달라진다                                                |
