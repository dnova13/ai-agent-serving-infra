## 2. 개념

| 항목              | 내용                                                                                                                                                              |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HNSW              | 벡터를 층층이 쌓인 이웃 그래프로 연결해 두고, 검색 때 그래프를 따라가며 가까운 벡터를 찾는 근사 검색 방식. 전부 비교하지 않아 빠르지만 정답을 놓칠 수 있다                  |
| `m`               | 한 벡터가 이웃으로 연결하는 간선 수(Qdrant 기본 16). 크면 정확해지지만 인덱스가 커지고 만드는 시간이 길어진다                                                         |
| `ef_construct`    | 인덱스를 만들 때 후보를 살펴보는 폭(기본 100). 크면 그래프 품질이 좋아지지만 만드는 시간이 길어진다. 한 번 만들면 검색 때는 영향이 없고, 바꾸려면 인덱스를 다시 만들어야 한다 |
| `hnsw_ef`         | 검색 때 후보를 살펴보는 폭. 크면 정확해지지만 느려진다. 인덱스를 다시 만들지 않고 검색 요청마다 바꿀 수 있다                                                          |
| recall@10         | 근사 검색이 돌려준 상위 10개 중, 정확한 검색(`exact=True`, 전부 비교)의 상위 10개와 겹치는 비율의 평균. 1.0 이면 정확한 검색과 같다                                      |
| 합성 벡터         | 실제 임베딩(Gemini)이 아니라 중심점 100개 주변에 흩뿌린 768차원 벡터. 시드가 같으면 항상 같은 값이다. 의미 검색 품질이 아니라 HNSW 설정에 따른 변화만 본다               |
| 인덱스 만드는 시간 | 벡터를 다 올린 뒤 인덱스를 만들기 시작해서 상태가 green 이 되고 모든 벡터가 인덱스에 들어갈 때까지의 시간. 업로드 시간은 따로 기록한다                                  |

## 5. 실행과 확인

### ① 기본 설정에서 hnsw_ef 바꿔 보기

**목적:** 인덱스는 그대로 두고 검색 때의 `hnsw_ef` 만 바꿨을 때 recall 과 지연 시간의 관계를 본다. 이후 실험의 기준선이다.

```bash
# 컬렉션 hnsw-exp-base 를 만들고(m=16, ef_construct=100) 합성 벡터 10만 개를 올린 뒤, 인덱스가 완성될 때까지의 시간을 잰다
python -m app.experiments.hnsw_experiment build --name base --m 16 --ef-construct 100 --n 100000
```

```bash
# 정확한 검색(exact)을 정답으로 삼아, hnsw_ef 를 8~512 로 바꿔 가며 recall@10, 지연 시간(p50/p95), QPS 를 잰다
python -m app.experiments.hnsw_experiment search --name base --ef 8,16,32,64,128,256,512
```

확인 전 예상:

| 항목                  | 예상                                                                                      |
| --------------------- | ----------------------------------------------------------------------------------------- |
| recall@10             | `hnsw_ef` 가 커질수록 올라가다가 어느 값부터 1.0 에 가까워져 더는 오르지 않는다                |
| 지연 시간(p50, p95)   | `hnsw_ef` 가 커질수록 늘어난다. 10만 개에서는 수 ms 안팎이라 작은 값끼리는 차이가 잘 안 보일 수 있다 |
| 인덱스 만드는 시간    | 수십 초 ~ 수 분 (PC 사양에 따라 다름)                                                      |


### ② m 바꿔 보기

**목적:** 인덱스의 `m` 을 바꿨을 때 정확도, 속도, 인덱스 만드는 시간, 디스크가 얼마나 달라지는지 본다. `ef_construct` 는 100 으로 고정한다.

```bash
# m=8,16,32,64 각각 컬렉션을 만들어 10만 개 업로드 → 인덱스 시간 측정 → hnsw_ef=32,64,128 로 검색. --keep 은 끝나도 컬렉션을 남긴다
python -m app.experiments.hnsw_experiment sweep --m 8,16,32,64 --ef-construct 100 --n 100000 --ef 32,64,128 --keep
```

디스크 사용량은 끝난 뒤 프로젝트 루트에서 잰다(`--keep` 이라 컬렉션이 남아 있다).

```bash
# 남아 있는 실험 컬렉션별 디스크 사용량을 본다 (프로젝트 루트에서)
du -sh docker-data/qdrant/collections/hnsw-exp-*
```

확인 전 예상:

| 항목               | 예상                                                                  |
| ------------------ | --------------------------------------------------------------------- |
| recall@10          | `m` 이 클수록 같은 `hnsw_ef` 에서 높다. 작은 `m`(8)은 `hnsw_ef` 를 키워도 1.0 에 못 닿을 수 있다 |
| 인덱스 만드는 시간 | `m` 이 클수록 길다                                                    |
| 디스크             | 벡터 원본(10만 × 768 × 4바이트 ≈ 300MB)이 대부분이라 `m` 에 따른 차이는 상대적으로 작다 |


### ③ ef_construct 바꿔 보기

**목적:** 인덱스를 만들 때의 `ef_construct` 를 바꿨을 때 정확도와 인덱스 만드는 시간의 관계를 본다. `m` 은 16 으로 고정한다.

```bash
# m=16 고정, ef_construct=50,100,200,400 각각 컬렉션을 만들어 인덱스 시간 측정 → hnsw_ef=32,64,128 로 검색. 끝나면 컬렉션을 지운다
python -m app.experiments.hnsw_experiment sweep --m 16 --ef-construct 50,100,200,400 --n 100000 --ef 32,64,128
```

확인 전 예상:

| 항목               | 예상                                                                      |
| ------------------ | ------------------------------------------------------------------------- |
| recall@10          | `ef_construct` 가 클수록 높지만 100 이후로는 증가 폭이 작다                   |
| 인덱스 만드는 시간 | `ef_construct` 가 클수록 길다                                              |
| 검색 지연 시간     | 거의 같다(`ef_construct` 는 검색 때 영향이 없다)                            |

## 6. 확인하지 않은 것

| 항목                          | 이유                                                                 |
| ----------------------------- | -------------------------------------------------------------------- |
| 실제 임베딩에서의 recall      | 합성 벡터를 썼다. 실제 문서 분포와 다를 수 있다                          |
| 양자화, 필터 검색, 동시 검색  | 오늘 범위 밖이다. 지연 시간은 한 번에 한 건씩 보낸 값이다                |
| 10만 개 초과 규모             | 데이터가 커지면 `m`, `ef_construct` 의 영향이 달라질 수 있다            |


## 7. 알려진 한계

- 샌드박스 확인은 Qdrant 1.15.4, 2코어, 2만 개 규모로만 했다. 사용자 PC 의 Qdrant(Docker `latest`)와 버전·사양이 다르다.
- 지연 시간에는 파이썬 클라이언트와 REST 왕복 시간이 포함된다. 같은 PC 에서 돌려서 네트워크 지연은 거의 없다.
- recall 은 질의 200건의 평균이다. 질의 수가 적어 소수점 둘째 자리 차이는 의미가 약하다.
