# 대화 맥락 관리 고찰 — 잘라내기, 요약, 그리고 할루시네이션

> Day 20 에서 대화를 Redis 에 저장하며 나온 질문들을 정리한 고찰 문서다. 구현은 [DAY20_CODE_GUIDE.md](DAY20_CODE_GUIDE.md), 실행 결과는 [DAY20_RESULT.md](DAY20_RESULT.md).
> 이 문서는 실험 결과가 아니라 설계 검토다. 직접 실행해 확인한 것은 "현재 구조"(3번)의 일부뿐이고, 나머지는 문서와 일반 지식에 근거한 설명이다. 확인 여부는 6번에 따로 적었다.
> 포트: **8080 = Spring WAS**, **8000 = FastAPI 워커**, **6379 = Redis**.

**전체 목적:** 대화가 길어질 때 모델에 무엇을 보낼지(전부, 최근 일부, 요약)를 정하는 방법과 각각의 비용, 위험을 정리하고, 이 프로젝트가 지금 왜 "최근 10턴만 유지"를 택했는지, 요약을 넣는다면 어떻게 넣을지를 남긴다.


## 1. 문제: 모델은 앞 대화를 기억하지 못한다

**목적:** "대화가 이어진다"가 실제로는 무엇인지 확인한다.

| 사실 | 내용 |
| ---- | ---- |
| 모델은 상태가 없다 | 요청 한 번은 그 요청에 담긴 내용만 본다. 이전 요청은 모른다 |
| 이어지는 것처럼 보이는 이유 | 호출하는 쪽이 이전 질문과 답을 매 요청에 다시 실어 보내기 때문이다 |
| 우리 프로젝트 | Redis(6379)에 `agent:conversation:<sessionId>` 로 저장해 두었다가 다음 요청에 붙인다 |
| 길이의 한계 | 보낼 내용이 길수록 토큰, 비용, 지연이 늘고, 모델이 받을 수 있는 한도를 넘으면 오류가 난다 |

그래서 "무엇을 보낼 것인가"가 설계 문제가 된다.


## 2. 선택지 비교

**목적:** 긴 대화를 다루는 방법을 한곳에 놓고 비교한다.

| 방법 | 방식 | 장점 | 단점 | 이 프로젝트 |
| ---- | ---- | ---- | ---- | ---------- |
| A. 전부 보낸다 | 쌓인 대화를 그대로 매번 보냄 | 가장 단순, 정보 손실 없음 | 길어질수록 비용, 지연 증가, 한도 초과 | 쓰지 않음 |
| B. 최근 N턴만 | 오래된 턴을 버림 | 구현이 몇 줄, 추가 호출 없음 | 버린 내용은 복구 불가, 앞 내용을 가리키면 모름 | **현재 사용 (N=10)** |
| C. 오래된 것을 요약으로 교체 | N 턴을 넘으면 오래된 K 턴을 LLM 으로 요약해 1개로 바꿔치기 | 앞 내용의 큰 줄기를 유지, 이후 토큰 감소 | 요약 호출 비용과 지연, 요약 손실, 원문 복구 불가 | 미구현 |
| D. 원본 유지 + 보낼 때만 요약 | 저장소에는 원문 전부, 요청 때 요약본을 만들어 붙임 | 원문이 남음 | 요약을 캐시하지 않으면 매번 호출이 늘어남 | 미구현 |
| E. 중요 사실 별도 보관 | 주문번호, 조건 등을 요약과 별도 필드로 보관해 매번 붙임 | 요약이 틀려도 핵심은 정확 | 무엇이 중요한지 정하는 규칙 필요 | 미구현 |
| F. 서비스가 대신 요약 | Claude API 의 서버 측 compaction 등 | 직접 만들 필요 없음 | 해당 API 를 써야 함, 베타 | 쓰지 않음 (Claude API 미사용) |

실무에서는 C 또는 D 에 E 를 섞는 경우가 많다고 알려져 있다(일반적 설명이며 이번에 조사한 것은 아니다).


## 3. 현재 구조

**목적:** 지금 코드가 실제로 하는 일을 정확히 적는다.

| 항목 | 값 | 위치 |
| ---- | -- | ---- |
| 저장 내용 | 사용자 질문과 최종 답 텍스트만. 도구 호출, 검색 결과는 저장 안 함 | `d2-ai-python/app/services/conversation_store.py` |
| 최대 길이 | 10턴 = 메시지 20개(질문+답 1쌍이 1턴). `CONVERSATION_MAX_TURNS` | 같은 파일 `MAX_TURNS` |
| 넘으면 | `history[-MAX_TURNS * 2:]` 로 최근 20개만 남기고 앞을 버림 (요약 없음) | 같은 파일 `append_turn` |
| 만료 | 마지막 저장 후 3600초. 저장할 때마다 새로 계산. `CONVERSATION_TTL_SEC` | 같은 파일 `TTL_SEC` |
| 사용처 | 요청 시 읽어 이번 질문 앞에 붙이고, 답이 나오면 저장 | `d2-ai-python/app/services/agent_graph.py` `run_agent` |

예: 12턴째가 저장되면 1, 2턴이 빠지고 3~12턴이 남는다. 버린 턴은 Redis 에서 사라진다.
11턴 이상을 실제로 쌓아 확인한 적은 없다. 코드 로직에서 읽은 동작이다(6번).

10턴과 3600초는 **임시값**이다. 키가 영원히 쌓이지 않게 하고 이어가기를 확인하는 목적이며, 정식 만료 정책은 Day 24 에서 정한다.


## 4. 요약을 쓸 때 따져볼 것

**목적:** 요약을 넣으면 무엇을 얻고 무엇을 감수하는지 정리한다.

| 항목 | 내용 |
| ---- | ---- |
| 토큰 절감 | 요약이 원문보다 짧으면, 이후 모든 요청에서 보내는 양이 줄어든다. 절감은 요약 이후 요청마다 누적된다 |
| 요약 호출 비용 | 요약하는 순간 LLM 호출이 한 번 더 생긴다. 이번 실험에서 호출 한 번이 약 14초였으므로(DAY18_RESULT 3-7) 사용자 응답에 끼면 체감된다. 다른 환경에서도 그렇다는 보장은 없다 |
| 요약 손실 | 숫자, 조건, 고유명사가 빠지거나 바뀔 수 있다. 모델은 요약을 사실로 믿고 답한다 |
| 오류 전파 | 요약이 한 번 틀리면 이후 요약의 요약에도 그 오류가 이어진다 |
| 원문 복구 | 바꿔치기(C)는 원문이 사라진다. 복구가 필요하면 D 처럼 원문을 별도 보관해야 한다 |
| 요약 시점 | 응답 경로 안에서 하면 느려지고, 응답 후 백그라운드로 하면 다음 요청이 요약 전 상태를 볼 수 있어 동시성(락, Day 21~22) 문제가 겹친다 |

줄이는 방법: 요약 지시에 "숫자와 고유명사는 유지"를 명시, 중요 사실은 E 처럼 별도 보관, 답에 근거 문서를 인용하게 해서 지어낸 내용을 확인할 수 있게 한다.


## 5. 할루시네이션과의 관계

**목적:** 긴 대화의 잘못된 답이 어디서 오는지, 요약, 잘라내기가 그중 얼마나 차지하는지 구분한다.

| 원인 | 어떻게 틀어지나 | 이 프로젝트 |
| ---- | -------------- | ---------- |
| 잘라내기 | 버린 내용을 가리키는 질문에 모델이 모르는 채로 그럴듯하게 답할 수 있다 | 10턴을 넘긴 대화에서만 해당 |
| 요약 손실 | 틀린 요약을 사실로 믿고 답한다 | 요약 미사용이라 해당 없음 |
| 긴 컨텍스트 | 내용이 많으면 중간 정보를 놓치거나 섞는 경향이 있다고 알려져 있다(모델마다 다름) | 10턴 정도에서는 문제가 크지 않을 것으로 예상, 측정하지 않음 |
| 모델 자체 | 모르는 것도 그럴듯하게 이어 쓴다. 대화 길이와 무관하게 첫 질문부터 생길 수 있다 | 아래 예 |

이 프로젝트에서 본 예: DAY20_RESULT 3-3 에서 세션이 비어 있었는데 모델이 "이전 대화 내용을 다시 확인해 보니"라고 말했다. 맥락이 잘려서가 아니라 모델의 문장 습관으로 보인다(원인을 확인한 것은 아니다).
반대로 3-2 는 세션 없이 "그 기간이 지나면?"을 보내자 지어내지 않고 어떤 기간인지 되물었다.

정리: 요약, 잘라내기는 할루시네이션의 **여러 원인 중 하나**이고 전부가 아니다. 문서를 검색해 근거로 답하게 하는 RAG 는 이와 별개로 할루시네이션을 줄이는 주된 수단이다.


## 6. 업체 사례와 확인하지 않은 것

**목적:** 외부 서비스가 어떻게 한다고 확인했는지와 확인하지 못한 것을 구분한다.

| 대상 | 확인한 것 | 출처 |
| ---- | -------- | ---- |
| Claude API | 상태를 저장하지 않고 매 요청에 전체 `messages` 를 보내야 한다. 한도를 넘으면 400 오류("prompt is too long") | 아래 Sources |
| Claude 서버 측 compaction | 오래된 턴을 Claude 가 쓴 요약으로 대체하는 기능. 베타이고 일부 최신 모델만 지원 | 아래 Sources |
| Claude context editing | 요약 대신 규칙으로 오래된 도구 결과 등을 지움 | 문서에서 확인 |
| claude.ai 채팅 화면 | 문서 각주에 컨텍스트를 FIFO(먼저 들어온 것부터 버림)로 관리할 수 있다는 언급 정도. 내부에서 요약을 쓰는지는 확인 못 함 | 아래 Sources |
| GPT, Gemini | **조사하지 않음** | - |

| 이 프로젝트에서 확인하지 않은 것 | 내용 |
| ------------------------------ | ---- |
| 11턴 이상 쌓았을 때 | 실제로 앞 턴이 빠지는지 실행해 보지 않았다. 코드로만 읽은 동작이다 |
| 잘린 뒤의 답 | 버려진 턴을 가리키는 질문에 모델이 어떻게 답하는지 보지 않았다 |
| 요약 | 구현하지 않아 품질, 지연, 토큰 절감량을 측정하지 않았다 |
| 긴 컨텍스트의 성능 저하 | 10턴에서의 영향을 측정하지 않았다 |


## 7. 이 프로젝트의 선택

**목적:** 지금 B 를 쓰는 이유와, 요약이 필요해졌을 때의 설계 후보를 남긴다.

| 항목 | 내용 |
| ---- | ---- |
| 지금 B 인 이유 | 이 단계의 목표는 "Redis 에 대화를 저장해 이어가기"의 확인이다. 몇 줄이면 되고 추가 LLM 호출이 없다. 짧은 문의 챗봇이라면 최근 10턴으로도 충분한 경우가 많다 |
| 요약이 필요해지는 경우 | 긴 상담에서 초반 내용이 뒤에서도 필요할 때 |
| 도입 후보 | `append_turn` 에서 20턴을 넘으면 오래된 10턴을 LLM 으로 요약해 1개로 교체(C). 원문이 필요하면 D 처럼 따로 보관 |
| 같이 볼 것 | 요약 중 같은 세션 요청이 들어오면 읽기-수정-쓰기 경합이 커진다. 락(Day 21), 동시 요청 테스트(Day 22)와 연결 |
| 결정 시점 | 정식 만료, 보관 정책을 정하는 Day 24 전후. 지금 넣지 않는다 |
