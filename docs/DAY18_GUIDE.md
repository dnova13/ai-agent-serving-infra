# Day 18 가이드 — Kafka Consumer Group 과 멀티 컨슈머 실험

> 상태: ①~③ 재측정해 확인함, 선택 ④ 한 번 확인, ⑤~⑦ 은 하지 않음(2026-10-12). 실행하면 [DAY18_RESULT.md](DAY18_RESULT.md) 에 결과를 적는다.
> 포트: **8080 = Spring WAS**, **8000 = FastAPI 워커 1**, **8001 = 워커 2**, **8002 = 워커 3**, **8003 = 워커 4**, 9092 = Kafka, 8090 = kafka-ui.

## 1. 오늘 목표

지금까지는 워커(FastAPI 8000) 하나가 파티션 하나를 읽었다. Day 17 에서 본 것처럼 한 건에 22~29초가 걸려서 요청이 몰리면 뒤의 요청이 줄줄이 기다린다(3건에 75초). 같은 **그룹**에 워커를 더 띄우면 파티션을 나눠 맡아 병렬로 처리한다. 그 효과와 동작 방식을 실험으로 확인한다.

| 확인할 것                                                   | 실험     |
| ----------------------------------------------------------- | -------- |
| 파티션이 1개면 워커를 늘려도 소용없다                       | ①        |
| 워커 2개, 3개로 늘리면 파티션을 나눠 맡고 시간이 줄어드는가 | ②, ③     |
| 요청이 워커에 고르게 가는가                                 | ③        |
| 워커가 파티션보다 많으면 놀게 된다                          | ④ (선택) |
| 워커가 꺼지면 다른 워커가 이어받는가, 처리 중이던 요청은    | ⑤ (선택) |
| 강제 종료(`kill -9`)하면 얼마나 늦게 이어받는가             | ⑥ (선택) |
| 그룹이 다르면 같은 메시지를 각자 받는다                     | ⑦ (선택) |

## 2. 개념

| 용어             | 설명                                                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 그룹(`group_id`) | 같은 일을 나눠 하는 워커들의 묶음. 이 프로젝트의 그룹은 `agent-workers`                                                     |
| 파티션 배정      | 같은 그룹 안에서 **한 파티션은 한 시점에 워커 하나만** 읽는다. 워커가 파티션을 나눠 갖는다                                  |
| 병렬도의 상한    | 워커 수가 파티션 수보다 많으면 남는 워커는 아무 파티션도 못 받고 논다. 처리량의 상한은 파티션 수다                          |
| 리밸런싱         | 워커가 들어오거나 나가면(또는 파티션 수가 바뀌면) 파티션을 다시 나누는 것. 그동안 잠깐 처리가 멈출 수 있다                  |
| 다른 그룹        | 그룹이 다르면 각 그룹이 토픽의 모든 메시지를 따로 받는다(같은 요청을 둘이 처리). 같은 그룹이면 한 요청은 한 워커만 처리한다 |

**요청이 어느 파티션으로 가나.** Spring(8080)이 `requestId` 를 key 로 보내므로, Kafka 가 key 를 해시해서 파티션을 정한다. requestId 는 매번 다른 UUID 라 요청 3건이 파티션 3개에 정확히 1건씩 가지 않고 치우칠 수 있다(3건이 모두 다른 파티션으로 갈 확률은 27가지 중 6가지, 약 22%). 치우치면 건수가 많은 파티션의 워커가 병목이 된다(③ 에서 확인).

```
[Spring :8080] -key=requestId-> [토픽 agent.requests]
                                  ├ 파티션 0 ─┐
                                  ├ 파티션 1 ─┼─ 그룹 agent-workers: 워커 1(:8000), 워커 2(:8001), 워커 3(:8002) 가 나눠 맡는다
                                  └ 파티션 2 ─┘
```

## 3. 만든/바꾼 파일

| 파일                                                | 내용                                                                                                                                                                                                    |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `d2-ai-python/app/services/kafka_worker.py` (수정)  | 파티션 배정/회수를 로그로 남기고(`[w1] 파티션 배정 [0, 2]`), `/health` 에 `worker_id`, `partitions`, `rebalances` 를 보인다. 리밸런싱 중 commit 이 거절되면(`CommitFailedError`) 로그만 남기고 계속한다 |
| `d2-ai-python/app/services/agent_handler.py` (수정) | `[agent] 시작/완료` 로그에 `worker=` 를 넣고, 결과에 처리한 워커, 파티션, offset 을 함께 저장한다                                                                                                       |
| `d2-ai-python/app/services/agent_graph.py` (수정)  | `agent_node`, `tool_node`, `search_vector_db`, `run_agent` 에 `[timing]` 시간 로그 추가(건당 시간이 어디서 쓰이는지 확인용. 기존 줄은 `[OLD]` 주석). 결과는 RESULT 3-7 |
| `d2-ai-python/app/services/result_store.py` (수정)  | 결과 항목에 `worker`, `partition`, `offset` 필드 추가                                                                                                                                                   |
| `scripts/day17_e2e.sh` (수정)                       | `FASTAPI` 에 주소를 공백으로 여러 개 주면 워커 여럿을 한꺼번에 본다. 건수는 합산하고, 결과는 워커 주소를 차례로 물어 읽고, 워커별/파티션별 처리 건수를 출력한다                                         |

새 환경변수:

| 변수              | 기본값          | 의미                                                                             |
| ----------------- | --------------- | -------------------------------------------------------------------------------- |
| `KAFKA_WORKER_ID` | `worker-<pid>`  | 로그와 `/health` 에서 워커를 구분하는 이름. 워커마다 다르게 준다(`w1`, `w2` ...) |
| `KAFKA_GROUP`     | `agent-workers` | 소비자 그룹 이름(Day 15 부터 있던 변수). ⑦ 에서 다르게 준다                      |

**결과 저장소가 워커마다 따로다.** Day 17 의 결과 조회는 FastAPI 프로세스의 메모리라서, 요청을 처리한 워커의 주소로만 조회된다(예: 워커 2가 처리한 요청은 8000 에서 404). 스크립트는 주소를 차례로 물어서 이를 감춘다. 이 불편이 4주차에 결과를 Redis 같은 공유 저장소로 옮기는 이유다.

## 5. 준비

1. Kafka, Qdrant 컨테이너와 Spring(8080)을 켠다(이전과 같다). 이전 실험의 환경변수를 지운다.
    ```bash
    unset KAFKA_HANDLER KAFKA_COMMIT_MODE AGENT_DEBUG_DELAY_SEC KAFKA_GROUP
    ```
2. 터미널을 워커마다 하나씩 쓴다. 워커 1(8000)은 지금까지처럼 `source run.sh` 로 켜되 이름을 먼저 준다.
    ```bash
    # 8000 = 워커 1
    export KAFKA_WORKER_ID=w1
    source run.sh
    ```
3. 워커 2, 3, 4 는 터미널을 새로 열어(가상환경을 켠 상태) 이름과 포트를 다르게 해서 켠다. 포트가 같으면 `Address already in use` 로 안 켜진다.

    ```bash
    # 8001 = 워커 2 (워커 3 은 w3 와 8002, 워커 4 는 w4 와 8003 으로 바꿔서 같은 방식으로)
    cd d2-ai-python

    export KAFKA_WORKER_ID=w2
    uvicorn app.main:app --port 8002

    export KAFKA_WORKER_ID=w3
    uvicorn app.main:app --port 8003

    export KAFKA_WORKER_ID=w4
    uvicorn app.main:app --port 8004
    ```

4. 워커를 켠 뒤 `curl -s localhost:8001/health` 처럼 각 포트의 `/health` 에서 `worker_id`, `partitions` 를 본다.
5. **먼저 워커를 모두 켜고, 배정 로그가 정리된 뒤에 요청을 보낸다.** 이 그룹은 `latest` 로 읽기 때문에, 새로 생긴 파티션에 배정되기 전에 도착한 메시지는 놓칠 수 있다.

## 6. 실행과 확인

### ① 파티션을 3개로 늘리고, 워커 1개일 때 기준값 재기

**파티션은 늘릴 수만 있고 줄일 수 없다.** 줄이려면 토픽을 지우고 다시 만들어야 한다. 이 프로젝트에서는 토픽에 남은 요청이 중요하지 않아 그렇게 해도 되지만, 의도하고 하는 것이다.

1. `d3-was-spring/src/main/resources/application.properties` 의 값을 바꾼다.
    ```properties
    # [OLD] app.kafka.topics.requests-partitions=1
    app.kafka.topics.requests-partitions=3
    ```
2. Spring(8080)을 다시 켠다(Kafka 가 먼저 켜져 있어야 한다). 시작할 때 `NewTopic` 설정이 파티션을 3개로 늘린다.
3. 파티션이 3개인지 본다. kafka-ui(8090)의 Topics → `agent.requests` 에서 Partitions 가 3 이거나, 터미널에서 본다.
    ```bash
    # kafka 컨테이너 안의 도구로 토픽 정보를 본다 (컨테이너 안에서는 kafka:29092 로 접속한다)
    docker exec kafka kafka-topics --bootstrap-server kafka:29092 --describe --topic agent.requests
    ```
4. 워커 1(8000)만 켜고 `/health` 를 본다. 기대(확인 전 예상): `partitions` 가 `[0, 1, 2]` 로, 한 워커가 셋을 다 맡는다.
5. 기준값을 잰다. 스크립트의 기본값인 3건에 걸리는 시간을 적어 둔다(Day 17 기준 건당 22~29초이므로 1분 반 안팎이 걸릴 것으로 예상, 확인 전). ②, ③ 도 같은 3건으로 해서 비교한다.
    ```bash
    bash scripts/day17_e2e.sh
    ```

### ② 워커 2개

1. 워커 2(8001)를 켠다(위 5번의 3). 두 워커의 로그에 `파티션 회수` 와 `파티션 배정` 이 찍히는지 본다.
2. 기대(확인 전 예상): 파티션 3개가 두 워커에 2개와 1개로 나뉜다(어느 워커가 2개인지는 실행해 봐야 안다). 처음 켜진 워커 1은 한 번 전부 내놓았다가 다시 배정받는다.
    ```bash
    curl -s localhost:8000/health
    curl -s localhost:8001/health
    ```
3. 3건을 보낸다. 스크립트에는 워커 주소를 모두 준다.
    ```bash
    # 8000, 8001 = 워커 1, 2
    FASTAPI="localhost:8000 localhost:8001" bash scripts/day17_e2e.sh
    ```
4. 기대(확인 전 예상): `워커별 처리 건수` 가 두 워커에 나뉘고 ① 의 기준값보다 짧다. 치우치면 2개를 맡은 워커가 병목이고, 3건이 모두 한 워커의 파티션으로 가면 시간이 줄지 않는다(`동시 처리 배율` 이 1.0 부근). 한 번으로 단정하지 말고 한 번 더 돌려 본다.

### ③ 워커 3개

1. 워커 3(8002)을 켠다. 기대(확인 전 예상): 각 워커의 `partitions` 가 하나씩이다.
2. 3건을 보낸다.
    ```bash
    # 8000, 8001, 8002 = 워커 1, 2, 3
    FASTAPI="localhost:8000 localhost:8001 localhost:8002" bash scripts/day17_e2e.sh
    ```
3. 적어 둘 것: 처리 완료 시간, `워커별 처리 건수`, `파티션별 건수`, `동시 처리 배율`(건당 처리 시간의 합 ÷ 완료 시간. 1.0 이면 한 건씩 처리한 것이고, 요청이 치우치지 않고 워커가 나눠 처리할수록 커진다. 건당 시간이 흔들려도, 요청이 어느 파티션에 몰려도 병렬 정도를 비교할 수 있는 값이다). 건수가 1/1/1 이 아니면 requestId 해시 때문에 치우친 것이다. 전체 시간은 가장 많이 받은 워커의 건수에 건당 시간을 곱한 값과 비슷할 것으로 예상한다(확인 전).
4. 한 번만으로는 치우침이 우연인지 알 수 없으므로 한 번 더 돌려 건수가 바뀌는지 본다.

### ④ (선택) 워커가 파티션보다 많을 때

1. 워커 4(8003)를 켠다. 기대(확인 전 예상): 새 워커의 `partitions` 가 `[]` 이고 나머지 셋은 하나씩이다. kafka-ui 의 Consumers → `agent-workers` 에서도 멤버가 4개, 배정이 3개로 보인다.
2. 3건을 보낸다(`FASTAPI` 에 8003 까지 4개). 기대: 워커 4는 0건이다. 워커를 더 늘려도 처리량이 늘지 않는다는 뜻이다.

### ⑤ (선택) 워커가 꺼질 때: 이어받기와 처리 중이던 요청

**(a) 놀고 있을 때 끄기.** 워커 3개 상태에서 워커 3 을 `Ctrl+C` 로 끈다. 남은 두 워커의 로그에 `파티션 회수` 와 `파티션 배정` 이 찍히고, 워커 3 이 맡던 파티션이 다른 워커로 넘어가는지 본다. 끈 워커는 `consumer.stop()` 으로 그룹에서 정상 탈퇴하므로 바로 재배정될 것으로 예상한다(확인 전).

**(b) 처리 중에 끄기.** 모든 워커에 처리 시간을 길게 만드는 변수를 주고(끝나면 `unset`) 요청을 보낸다.

```bash
# 모든 워커 터미널에서 서버를 끄고 다시 켠다
export AGENT_DEBUG_DELAY_SEC=30
```

1. 요청을 3건 보낸다(`bash scripts/day17_e2e.sh 3` 은 완료까지 기다리므로, 스크립트 대신 Postman 이나 curl 로 보내도 된다).
2. 어느 워커가 `[agent] 시작` 을 찍었는지 보고, 그 워커를 `Ctrl+C` 로 끈다.
3. 기대(확인 전 예상): 그 요청은 commit 되지 않았으므로 다른 워커가 같은 requestId 로 `[agent] 시작` 을 다시 찍고 끝까지 처리한다(Day 16 의 "처리 후 commit" 결과와 같은 원리). 끈 워커가 처리 중이던 요청을 하나도 잃지 않는지 본다.

### ⑥ (선택) 그룹이 다르면

1. 워커 1(8000)이 켜진 상태에서, 다른 그룹 이름으로 워커를 하나 더 켠다.
    ```bash
    # 8001 = 다른 그룹(agent-workers-b)의 워커. 같은 요청을 이 그룹도 따로 받는다
    cd d2-ai-python
    export KAFKA_WORKER_ID=b1
    export KAFKA_GROUP=agent-workers-b
    uvicorn app.main:app --port 8001
    ```
2. 요청을 1건 보낸다. 기대(확인 전 예상): 두 워커가 모두 같은 requestId 로 `[agent] 시작` 을 찍는다. LLM 호출이 두 번 나간다.
3. 끝나면 `unset KAFKA_GROUP` 하고 8001 을 끈다. 새 그룹은 Kafka 에 남아 있으므로 kafka-ui 에서 지워도 된다.

## 7. 작성 중 확인한 것과 확인하지 않은 것

| 구분          | 내용                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 확인함        | 작성 환경의 aiokafka 0.12.0 소스에서 `subscribe(listener=)`, 동기 콜백 지원, `CommitFailedError` 존재, 기본 배정 방식(RoundRobin)과 세션 타임아웃 10초를 읽었다. 가짜 consumer 로 배정 알림이 `partitions`/`rebalances` 에 반영되는 것, 파티션 없는 워커의 `[]`, commit 거절 시 로그만 남기고 계속 도는 것을 시험했다. 스크립트는 가짜 서버 2개로 합산, 워커별/파티션별 집계, 한 워커 주소만 주었을 때의 FAIL 을 시험했다 |
| 확인하지 않음 | 실제 Kafka 에서의 리밸런싱(배정 로그, 시간), 파티션이 실제로 어떻게 나뉘는지, 요청의 파티션 분포, 워커를 늘렸을 때의 시간 단축, ⑤~⑦ 의 모든 기대. 위 "기대"는 모두 확인 전 예상이다                                                                                                                                                                                                                                       |
| 확인하지 않음 | `docker exec kafka kafka-topics ... kafka:29092` 명령 자체(작성 환경에는 Docker 가 없다). 안 되면 kafka-ui(8090)에서 파티션 수를 본다                                                                                                                                                                                                                                                                                     |

## 8. 알려진 한계

| 항목                 | 내용                                                                                                             |
| -------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 결과가 워커마다 따로 | 요청을 처리한 워커의 주소로만 조회된다. 4주차(Redis)에 공유 저장소로 옮긴다                                      |
| 중복 처리            | 리밸런싱 중에는 같은 요청이 두 번 처리될 수 있다. 걸러내기는 4주차(requestId 멱등성)                             |
| 한 번만 잰 시간      | 시간 비교는 같은 3건을 한두 번 돌린 값이다. 분포나 평균이 아니고, LLM 응답 시간 변동이 크다(Day 17 에서 22~29초) |
| 기본 배정 방식       | aiokafka 기본(RoundRobin)이다. 다른 방식(Range, Sticky)이나 협력적 리밸런싱과의 비교는 하지 않는다               |
| 단일 브로커          | Kafka 가 한 대라서 브로커 장애나 복제는 다루지 않는다                                                            |
