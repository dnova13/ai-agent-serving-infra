# Day 27 가이드 — 비동기(Kafka) 구조로 같은 부하를 다시 재서 1차 비교

> 상태: **실험은 ①, ②, ②-2, ③, ④ 를 모두 실행했다**(DAY27_RESULT 3-1~3-5). 아래 기대값은 모두 "확인 전 예상"이다. 코드는 바꾸지 않았다(3번).
> 포트: **8080 = Spring WAS**, **8000 = FastAPI 워커 1**, **8001 = FastAPI 워커 2**, **6379 = Redis(redis1 컨테이너)**, 9092 = Kafka, 6333 = Qdrant.
> 비교 대상은 [DAY26_RESULT.md](DAY26_RESULT.md)(동기). 기준선은 [DAY25_RESULT.md](DAY25_RESULT.md)(비동기, 접수만).

**전체 목적:** Day 26 에서 동기 구조(Spring 이 FastAPI 답을 기다림)는 VU 20 만으로 에러율 75%(504 22건, 502 2건, 200 8건)가 나왔다. 오늘은 같은 부하(VU 20, 가짜 LLM 5초, 워커 1대, 70초)를 비동기 구조(Spring 이 Kafka 에 넣고 202 로 바로 응답, 워커가 따로 처리)로 보내 에러율, 응답 시간, 완료 건수를 Day 26 과 나란히 놓는다. 이것이 최종 보고서의 1차 비교 데이터가 된다.


## 1. 오늘 목표

| 확인할 것                                                                                      | 실험 |
| ---------------------------------------------------------------------------------------------- | ---- |
| 비동기 경로가 한 건 끝까지 통과한다 (시작 전에 Kafka 를 비운다)                                  | ①    |
| VU 20 (결과 조회까지)에서 5xx 에러가 없고 접수(202)는 빠르다                                    | ②    |
| ② 가 도는 동안 워커의 `/health` 는 막히지 않는다 (Day 26 ③ 은 3.09초 막힘)                      | ②-2  |
| ② 직후 남은 요청(LAG)을 확인하고 비운다                                                         | ③    |
| (선택) 워커 2대로 같은 부하를 보내 완료 건수가 얼마나 늘어나는지 본다                           | ④    |


## 2. 개념

| 항목                          | 내용                                                                                                                                                                         |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 비동기 구조의 "복원"          | Day 26 에서도 비동기 경로(`POST /api/agent/requests`)는 그대로 두고 동기 경로(`/api/agent/sync`)만 추가했다. 그래서 복원할 코드가 없고, 오늘은 같은 조건으로 비동기를 다시 재는 것이다 |
| 같은 조건으로 비교            | VU 20, 70초(30 + 30 + 10), 가짜 LLM 5초, **워커 1대(8000)**, 쉬는 시간 1초. 달라지는 것은 요청이 지나가는 길뿐이다. 워커는 Day 26 과 달리 Kafka 를 읽게 켠다                    |
| 처리량은 같다                 | 워커 한 대는 한 건씩 처리하므로(가짜 LLM 5초) 비동기라고 처리가 빨라지지 않는다. 비동기가 바꾸는 것은 "기다림이 어디서 일어나는가"(HTTP 연결 → Kafka 대기열)와 그 결과(504 없음, `/health` 안 막힘)다 |
| 결과 조회(`POLL=1`)           | VU 는 접수 후 `DONE` 이 될 때까지 1초마다 조회한다. 그래서 요청을 보내는 속도가 완료 속도에 묶여, Day 26 의 동기와 같은 방식(닫힌 모델)으로 비교된다. 조회 중 404 는 대기열에서 기다리는 중이라는 정상 응답이다 |
| 워커 2대의 한계               | 토픽은 파티션 3개라 한 워커가 2개, 다른 워커가 1개를 맡는다(2:1). 워커 2대여도 처리량은 2배가 아니라 약 1.5배로 예상된다 (Day 25 의 lag 관찰에서 나온 계산)                  |

## 4. 준비

LAG 를 따로 확인하지 않고, 시작 전에 항상 비운다. 순서대로 실행하면 된다.

| 순서 | 할 일                                                                                                                              |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 떠 있는 FastAPI 워커(8000, 8001)를 **모두 끈다** (Kafka 그룹에 붙어 있으면 아래 비우기 명령이 실패한다)                              |
| 2    | 아래 "비우기" 명령을 실행한다. 쌓인 요청이 있든 없든 읽은 위치를 토픽 끝으로 옮기므로 LAG 가 0 이 된다                                 |
| 3    | 아래 명령으로 워커 8000 을 띄운다. **Day 26 과 달리 Kafka 를 읽게 켠다**(`KAFKA_CONSUMER_ENABLED` 를 주지 않음). `--reload` 없이        |
| 4    | 8001 워커는 ④ 전까지 띄우지 않는다. Spring(8080)은 Day 26 과 같은 것을 그대로 쓴다                                                    |

비우기 (워커를 끈 상태에서, 한 번만):

```bash
docker exec kafka kafka-consumer-groups --bootstrap-server kafka:29092 --group agent-workers --topic agent.requests --reset-offsets --to-latest --execute
```

워커 8000 (프로젝트 루트에서, venv 가 필요하면 먼저 활성화):

```bash
cd d2-ai-python && FAKE_LLM_ENABLED=true FAKE_LLM_DELAY_SEC=5 uvicorn app.main:app --port 8000
```

비우기는 쌓인 요청을 처리하지 않고 건너뛴다. 건너뛴 요청의 결과 조회는 계속 404 로 남지만 오늘 실험과는 무관하다.


## 5. 실행과 확인

각 실험은 앞 실험의 요청이 모두 끝난 뒤에 시작한다.

### ① 경로 확인 (스모크)

**목적:** 비동기 경로가 한 건 끝까지 통과하는지 본다.

```bash
k6 run scripts/k6/smoke.js
```

| 항목   | 기대값 (확인 전 예상)                          |
| ------ | ---------------------------------------------- |
| checks | 2/2 통과                                        |
| 완료   | 약 4~6초 뒤 `DONE`, `worker=…`, `answer=[fake]…` |

### ② 비동기 VU 20 (결과 조회까지)

**목적:** Day 26 의 동기와 같은 부하에서 비동기의 에러율, 접수 시간, 완료 시간, 완료 건수를 잰다.

```bash
k6 run -e MODE=async -e POLL=1 -e MAX_VUS=20 -e POLL_MAX_SEC=120 scripts/k6/ramping.js
```

| 항목                                           | 기대값 (확인 전 예상)                                                                          |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `accepted` (202 비율)                          | 100%                                                                                           |
| POST 접수 `http_req_duration` p(95)            | 수십 ms 이하 (Day 25 ④ 는 17.8ms)                                                              |
| `http_req_failed`                              | 0% (조회의 404 는 정상으로 둠)                                                                  |
| 5xx 에러                                       | 0                                                                                              |
| `results_done`                                 | 약 14건 (워커 1대, 건당 약 5초 직렬, 70초 안팎)                                                |
| `e2e_ms` (완료까지)                            | 수십 초. 대기열 순서에 따라 약 5초에서 70초 사이                                                |
| `results_failed`, `results_poll_timeout`       | 0 (`POLL_MAX_SEC` 를 120초로 줌)                                                               |
| 중단된 반복 (`interrupted iterations`)         | 약 18건 (시험이 끝날 때 아직 처리 중인 VU. Day 26 의 동기도 같았다)                              |

### ②-2 ② 가 도는 동안 `/health`

**목적:** 비동기 워커는 처리 중에도 `/health` 가 막히지 않는지 본다. Day 26 ③ 에서 동기는 3.09초 막혔다.

② 를 다시 실행하면서 20초 뒤부터 5초 간격으로 `/health` 를 3번 호출한다. 호출은 스크립트 `scripts/k6/health-probe.sh` 가 한다(명령을 직접 붙여 넣으면 주소 뒤에 `\;` 가 붙어 호출이 잘못된 적이 있어 파일로 뺐다). ② 의 두 번째 측정도 겸한다. 프로젝트 루트에서 실행한다.

```bash
bash scripts/k6/health-probe.sh & k6 run -e MODE=async -e POLL=1 -e MAX_VUS=20 -e POLL_MAX_SEC=120 scripts/k6/ramping.js; wait
```

시작 전에 앞 실험의 남은 요청이 없어야 하므로 ③ 의 1~2번(워커 끄기 → 비우기 → 워커 켜기)을 먼저 한다. 출력에 `health status=200 time=…` 가 3줄 나와야 한다. `404` 나 `000` 이 보이면 호출이 잘못된 것이다.

| 항목        | 기대값 (확인 전 예상)                                                                       |
| ----------- | ------------------------------------------------------------------------------------------- |
| health time | 3번 모두 0.0x초, status 200 (워커가 에이전트를 스레드에서 실행해 이벤트 루프가 비어 있음. Day 16 의 설계) |

### ③ 남은 요청(LAG) 확인

**목적:** 부하 후에 Kafka에 요청이 얼마나 쌓였는지, 그리고 시간이 지나면 줄어드는지 보는 실험입니다. 예상값은 아직 확인 전입니다.

**순서**

1. 워커 8000을 끄고 offset을 최신으로 맞춰 대기열을 비웁니다.

```bash
docker exec kafka kafka-consumer-groups --bootstrap-server kafka:29092 --group agent-workers --topic agent.requests --reset-offsets --to-latest --execute
```

2. 워커를 다시 띄웁니다. 워커는 끄지 말고 계속 켜 두세요.

```bash
cd d2-ai-python && FAKE_LLM_ENABLED=true FAKE_LLM_DELAY_SEC=5 uvicorn app.main:app --port 8000
```

3. ②를 실행합니다.

```bash
k6 run -e MODE=async -e POLL=1 -e MAX_VUS=20 -e POLL_MAX_SEC=120 scripts/k6/ramping.js
```

4. k6가 끝나면 바로 아래 명령을 실행합니다. 이것이 1번 결과입니다.

```bash
docker exec kafka kafka-consumer-groups --bootstrap-server kafka:29092 --group agent-workers --describe
```

5. 약 2분 뒤에 같은 명령을 한 번 더 실행합니다. 이것이 2번 결과입니다.

| 항목              | 기대값 (확인 전 예상)                                                                  |
| ----------------- | -------------------------------------------------------------------------------------- |
| 1번 LAG 합계      | 10 이상 (접수 약 32건 중 완료 약 13건)                                                  |
| 2번 LAG 합계      | 1번보다 줄어 있다 (건당 약 5초, 2분이면 약 20~24건 감소 계산)                           |

### ④ (선택) 워커 2대

**목적:** 워커를 한 대 더 붙이면 같은 부하에서 완료 건수가 얼마나 늘어나는지 본다.

③ 의 요청이 남아 있으면 건수가 섞이므로, ③ 이 끝난 뒤 ③ 의 1번(워커 끄기 → 비우기)을 한 다음 아래를 한다.

8001 워커를 추가로 띄운다(8000 은 그대로, 같은 환경변수).

```bash
cd d2-ai-python && FAKE_LLM_ENABLED=true FAKE_LLM_DELAY_SEC=5 uvicorn app.main:app --port 8001
```

파티션이 다시 배정되는 것을 기다린 뒤(약 10초) ② 를 같은 명령으로 다시 실행한다.

| 항목             | 기대값 (확인 전 예상)                                                                                      |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| `results_done`   | 약 21건. 워커 1대의 약 14건에 2배가 아니라 약 1.5배 (파티션 2:1 로 한 워커가 병목이 되는 계산)               |
| 5xx 에러         | 0                                                                                                          |

실험이 끝나면 8001 워커를 끈다.

## 7. 알려진 한계

| 항목                              | 내용                                                                                                                                  |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 한 번씩만 잰다                    | 반복 측정을 하지 않아 편차를 알 수 없다. 가짜 LLM 지연이 ±20% 흔들리므로 건수는 ±1~2건 달라질 수 있다                                |
| `POLL=1` 의 완료 시간은 일부만     | 시험이 끝날 때 처리 중이던 요청의 완료 시간은 잡히지 않아(중단된 반복) 완료 시간 통계가 실제보다 짧게 나온다                          |
| Day 26 과 단순 비교는 불공정       | 동기의 504 는 Spring 의 30초 제한이라는 설정값 때문이다. 비교할 때 제한을 바꾸면 에러율이 달라진다는 점을 같이 적는다                  |
