# Day 19 결과 — Redis 기본 연결과 읽기/쓰기 함수

> 구현과 실행 방법은 [DAY19_GUIDE.md](DAY19_GUIDE.md). 이 문서는 확인한 것과 확인하지 못한 것을 담는다.
> 상태: **내 환경(docker 의 `redis1`)에서의 실행은 하지 않았다**(2026-10-13). 아래 "확인된 결과"는 모두 코드를 만든 쪽의 샌드박스(가짜 Redis, 샌드박스의 `redis-server`)에서 본 것이다. 가이드 5번의 ①~④ 는 아직 실행하지 않았다.
> 포트: **8080 = Spring WAS**, **8000 = FastAPI 워커**, **6379 = Redis(`redis1` 컨테이너)**.

**전체 목적:** Day 17의 요청 결과는 FastAPI 프로세스 메모리에 있어서 워커를 껐다 켜면 사라지고, 워커가 여럿이면 처리한 워커에만 있다(Day 18). 이를 풀 공유 저장소로 Redis 를 쓰기 전에, Redis 에 접속하고 저장, 조회, 삭제, 만료 시간이 되는 기본 함수와 서버의 연결 상태 표시(`/health`)를 먼저 만든다. 실제 흐름에 Redis 를 쓰는 것은 Day 20 부터다.

## 3. 확인된 결과

(모두 샌드박스에서 본 것이다. 사용자 환경에서의 결과는 6번에 "확인하지 않음"으로 둔다.)

### 3-1. 읽기/쓰기 함수 (확인 스크립트 10개 항목)

**목적:** 저장, 조회, 덮어쓰기, 삭제, 만료 시간이 의도대로 동작하는지 본다.

| 항목                                                  | 결과                                                                                  |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 1) 연결(ping)                                         | PASS (`connected: True`, 지연 약 3~10ms. 샌드박스 값이라 사용자 환경과 다를 수 있음)  |
| 2) 한글, 중첩 dict, list, bool, null 의 저장 후 조회  | PASS. 저장한 값과 꺼낸 값이 같다                                                      |
| 3) 같은 키를 다시 쓰면 덮어씀                         | PASS                                                                                  |
| 4) 없는 키는 `None`, `exists` 가 키 유무에 맞게 반환  | PASS (2개 항목)                                                                       |
| 5) TTL 없이 저장하면 `ttl_sec` 이 `-1`                | PASS                                                                                  |
| 6) `ttl_sec=3` 이면 남은 시간이 0~3초, 4초 뒤 조회 `None` | PASS (2개 항목)                                                                   |
| 7) `delete` 는 있던 키 True, 이미 없는 키 False       | PASS (2개 항목)                                                                       |

가짜 Redis 와 실제 `redis-server` 둘 다 `10/10 통과`, `RESULT: PASS` 였다. 실제 서버에서 확인이 끝난 뒤 `redis-cli keys '*'` 로 보니 테스트 키가 남아 있지 않았다(스크립트가 끝나면 지운다).

### 3-2. Redis 가 꺼져 있을 때

**목적:** Redis 가 없어도 함수가 예외로 죽지 않고 상태를 알려 주는지 본다.

| 확인한 것                                   | 결과                                                                                                         |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `ping()`                                    | 예외 없이 `{"connected": False, "error": "ConnectionError: Error 111 connecting to localhost:6390. Connection refused."}` |
| 확인 스크립트                               | 1번 항목만 `[FAIL]`, 나머지는 건너뛰고 `RESULT: FAIL (Redis 에 연결하지 못해 …)` 와 `docker ps` 안내를 출력   |

### 3-3. `/health` 의 Redis 항목

**목적:** 서버 상태 확인에서 Redis 연결이 보이는지, Redis 가 꺼져 있어도 서버 응답이 정상인지 본다.

| 상태          | 응답                                                                                                                                      |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Redis 꺼짐    | HTTP 200, `{"status":"ok","kafka_consumer":null,"redis":{"connected":false,"error":"ConnectionError: Error 111 ... Connection refused."}}` |
| Redis 켜짐    | HTTP 200, `{"status":"ok","kafka_consumer":null,"redis":{"connected":true,"latencyMs":3.56}}`                                             |

`kafka_consumer` 는 테스트 앱에 Kafka 워커를 올리지 않아서 `null` 이다. 이 확인은 `/health` 라우터만 올린 테스트 앱이었고, 실제 서버(Kafka 워커 포함)에서 본 것이 아니다.


## 4. 해석

| 확인한 것                                       | 의미                                                                                                                         |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 가짜 Redis 와 실제 서버에서 결과가 같음         | 함수 로직이 `redis-py` 의 기본 동작에 맞게 작성됐다. 단 TTL 의 `-1`, `-2` 처리처럼 서버 버전에 따라 다를 수 있는 부분은 사용자 환경(Redis 7 alpine)에서 다시 봐야 한다 |
| 꺼진 Redis 에서도 `ping` 과 `/health` 가 응답    | Redis 장애가 서버 전체를 죽이지 않는 구조다. Kafka 에 적용한 방침(서버는 살아 있고 상태만 표시)과 같다                       |
| 접속 제한 시간 1초                              | Redis 가 꺼져 있으면 `/health` 가 약 1초 지연될 수 있다(설계상 예상. 이번에 시간을 재지는 않았다)                            |

처음에는 모듈 함수 방식으로 만들었다. 클래스(`RedisClient`)로 바꾸는 안은 검토했지만 적용하지 않았고, 함수 방식을 유지한다.


## 6. 확인하지 않은 것

| 항목                                            | 내용                                                                                                         |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 사용자 환경의 `redis1` 컨테이너                 | 가이드 5번의 ①~④(접속, 확인 스크립트, `/health`, Redis 중지 시 동작)를 실행하지 않았다                       |
| `docker exec redis1 redis-cli ...` 명령         | 가이드에 적은 명령을 실행해 본 적이 없다                                                                     |
| `redis==8.1.0` 설치                              | 사용자 파이썬(3.11.9) 가상환경에서 설치되는지 확인하지 않았다(샌드박스는 파이썬 3.13)                        |
| 실제 서버에서의 `/health`                       | Kafka 워커가 함께 떠 있는 서버에서 `kafka_consumer` 항목과 `redis` 항목이 같이 나오는지 보지 않았다           |
| `/health` 지연                                   | Redis 가 꺼졌을 때 응답이 실제로 몇 초 걸리는지 재지 않았다. Day 18 의 E2E 스크립트가 `/health` 를 1초마다 부르므로, Redis 가 꺼져 있으면 폴링이 느려질 수 있다 |
| 여러 워커가 같은 키를 읽는 동작                 | 해 보지 않았다(Day 20 에서)                                                                                  |
| 선택 ⑤ (`redis-cli` 로 저장된 모양)             | 하지 않았다                                                                                                  |
