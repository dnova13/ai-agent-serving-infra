# Day 12 가이드 — Chunking 전략 비교 실험

> 상태: 실행 완료(2026-10-10). 결과와 분석은 [DAY12_RESULT.md](DAY12_RESULT.md) 참고.

## 1. 오늘 목표

긴 문서를 **어떻게 자르느냐(chunking)** 에 따라 검색 정확도가 달라지는지 같은 질문으로 비교한다.

| 전략 | 방식 | 기대하는 장점 | 예상되는 약점 |
| --- | --- | --- | --- |
| fixed | 고정 글자 수(150자, 30자 겹침)로 자름 | 구현이 단순, 청크 크기 균일 | 문장과 사실이 중간에 잘림 |
| sentence | 문장 단위로 묶되 최대 150자 | 문장은 안 잘림 | 관련 문장이 서로 다른 청크로 갈라질 수 있음 |
| paragraph | 빈 줄 기준 문단 | 주제 단위로 이미 나뉜 문서에 유리 | 문단이 너무 길거나 짧으면 불리 |
| semantic | 문장 임베딩 후 인접 문장 유사도가 떨어지는 곳에서 자름 | 주제가 바뀌는 지점에서 자름 | 문장 임베딩 호출이 추가로 필요, 기준값(k)에 민감 |

원래 플랜의 "고정길이 vs 문장단위 vs 의미단위"에 문단 단위를 하나 더 넣었다. 문서에 문단이 이미 있으면 가장 값싼 방법이라 기준선으로 쓸모가 있다.

### 이 코드(`chunk_experiment.py`)가 하는 실험

"같은 문서를 어떻게 자르느냐에 따라 RAG 검색 정확도가 달라지는가"를 비교하는 **통제 실험**이다. 자르는 방식만 바꾸고 나머지는 모두 고정한다.

| 실험 요소 | 이 코드에서의 내용 |
| --- | --- |
| 가설 | 자르는 방식에 따라 정답 근거를 찾는 비율과 모델에 넘기는 문맥 크기가 달라진다 |
| 바꾸는 값 (독립변수) | 청킹 전략 4가지: fixed, sentence, paragraph, semantic |
| 고정하는 값 (통제) | 같은 문서 4개, 같은 질문 12개, 같은 임베딩 모델, 같은 Qdrant 설정, 같은 질문 벡터 |
| 재는 값 (종속변수) | top-1 / top-3 적중 수, 청크 수, 평균 청크 길이, 적중 시 top-1 청크 길이 |

한 번 실행할 때 일어나는 일:

1. 전략마다 같은 문서 4개를 다른 방식으로 잘라 청크 목록을 만든다.
2. 전략마다 별도 컬렉션(`chunk-exp-fixed` 등)에 청크를 넣어서 서로 섞이지 않게 한다.
3. 같은 질문 12개로 각 컬렉션에서 top-3 을 검색한다.
4. 정답 근거 문자열이 모두 들어 있는 청크가 top-3 안에 있는지 판정한다.
5. 전략별 요약 표와 질문별 순위 표를 출력한다.

판정 예: 질문이 "5만 원 넘게 사면 배송비 공짜인가요? 제주도도요?" 이면 정답 근거는 `"5만 원 이상"` 과 `"면제되지 않습니다"` 두 문자열이다. 이 둘이 **한 청크 안에** 있어야 성공이다. 청크 경계가 두 문장 사이를 자르면 근거가 두 청크로 갈라져서 실패한다. 그래서 이 실험의 핵심은 "경계가 어디에 놓이느냐"를 시험하는 것이다.

결과로 알 수 있는 것:

| 결과 | 의미 |
| --- | --- |
| fixed 가 다른 전략보다 낮음 | 글자 수로 자르면 경계에서 근거가 잘린다는 증거 |
| paragraph 와 semantic 이 비슷함 | 문단이 잘 나뉜 문서라면 단순한 paragraph 로 충분하고 semantic 은 비용만 더 든다 |
| 적중률이 같을 때 평균 길이가 다름 | 짧은 쪽이 모델에 넘기는 토큰이 적어서 유리 |
| `--size` 를 바꾸면 fixed 결과가 변함 | 청크 크기가 정확도에 주는 영향 |

한계(문서 4개, 질문 12개, 문단이 잘 나뉜 문서)는 7장에 있다. 결론은 "어떤 방식이 항상 낫다"가 아니라 "이런 구조의 문서에서는 이런 차이가 났다"로 정리한다.

### 전략과 코드의 대응

`chunk_experiment.py` 는 클래스 없이 함수로만 되어 있다.

| 전략 | 함수 | 입력 | 핵심 동작 | 영향 주는 옵션 |
| --- | --- | --- | --- | --- |
| fixed | `chunk_fixed(text, size=150, overlap=30)` | 문서 1개 | 글자 수로 자르고 다음 조각은 30글자 겹침 | `--size`, `--overlap` |
| sentence | `chunk_sentence(text, max_chars=150)` | 문서 1개 | 문장을 이어 붙이다가 150자를 넘기면 새 청크 | `--max-chars` |
| paragraph | `chunk_paragraph(text)` | 문서 1개 | 빈 줄(`\n\n`)에서 나눔 | 없음 |
| semantic | `chunk_semantic(texts, max_chars=300, k=0.5)` | **문서 전체 리스트** | 문장을 임베딩해 인접 문장 유사도가 떨어지는 곳에서 나눔 | `--sem-max`, `--k` |

보조 함수: `split_sentences`(sentence 와 semantic 이 문장을 나눌 때), `_cosine`(semantic 이 유사도를 계산할 때), `embed_texts`(semantic 이 문장을 임베딩할 때, 한도 보호와 캐시 포함).

`build_chunks(args)` 가 네 함수를 모두 부른다. 앞의 세 함수는 문서마다 호출하고 API 호출이 없다. `chunk_semantic` 만 모든 문서를 한 번에 넘기고 문장 임베딩 때문에 API 를 부른다. 8장의 429 에러는 이 함수와 청크 임베딩이 겹친 호출량 때문에 났다.

전략별 청크는 `{전략: [(doc_id, 청크 번호, 텍스트), ...]}` 형태의 딕셔너리로 만들어진다.

## 2. 왜 새 문서를 만들었나

기존 `SAMPLE_DOCS` 24개는 문서 하나가 한두 문장이라 이미 잘게 나뉘어 있다. 이 상태로는 자르는 방식이 결과에 영향을 주지 않는다. 그래서 여러 주제가 섞인 안내문 4개(환불/교환, 배송, 결제/포인트, 회원/등급, 약 1,560자)를 `app/data/long_docs.py` 에 따로 만들었다.

기존 `documents-12` 컬렉션은 건드리지 않고, 전략별 실험용 컬렉션 `chunk-exp-fixed|sentence|paragraph|semantic` 에만 넣는다. 끝나면 삭제한다(`--keep` 이면 남김).

## 3. 정확도를 재는 방법

질문 12개마다 "정답 근거 문자열(must)" 목록을 정해 두었다. 검색 top-3 청크 중 **must 의 문자열이 모두 한 청크 안에 들어 있으면 성공**이다.

| 질문 | must |
| --- | --- |
| 마음이 바뀌어서 반품하려는데 비용은 누가 내요? | 단순 변심, 5,000원 |
| 5만 원 넘게 사면 배송비 공짜인가요? 제주도도요? | 5만 원 이상, 면제되지 않습니다 |
| 포인트는 얼마나 쌓이고 언제까지 쓸 수 있어요? | 1%, 1년 |

must 가 2개 이상이면 두 사실이 인접해 있다는 뜻이다. (실험의 핵심이 청크 경계 문제를 시험하는 것이라는 설명은 1장 참고.) 청크 경계가 그 사이를 자르면 실패하므로, **경계 문제가 드러나게 설계한 질문**들이다. 질문은 문서 표현을 그대로 쓰지 않았다(Day 9 와 같은 원칙).

| 지표 | 의미 |
| --- | --- |
| 청크 수, 평균 길이 | 저장 규모와 모델에 넘기는 문맥 크기 |
| top-1 / top-3 | 정답 청크가 1등 / 3등 안에 있는 질문 수 |
| 성공 시 top-1 길이 | 길수록 모델에 넘기는 토큰이 늘어남. 정확도가 같으면 짧은 쪽이 유리 |

## 4. 실행 전에 이미 알 수 있는 것 (오프라인 확인)

임베딩 없이 자르기만 해서 "정답 근거가 한 청크 안에 들어갈 수 있는 질문 수"를 센 값이다. 검색 성능이 아니라 **상한**이다.

| 전략 | 청크 수 | 평균 길이 | 근거가 한 청크에 들어가는 질문 |
| --- | --- | --- | --- |
| fixed | 14 | 132자 | 10 / 12 |
| sentence | 14 | 110자 | 11 / 12 |
| paragraph | 15 | 102자 | 12 / 12 |

fixed 는 검색을 잘해도 질문 2개는 근거가 잘려서 못 찾는다. 실제 결과가 이 상한을 넘을 수는 없다.

## 5. 실행

프로젝트 루트(`d2-ai-python`)에서 가상환경을 켜고, Qdrant 컨테이너가 떠 있는 상태로 실행한다.

```bash
python -m app.experiments.chunk_experiment
python -m app.experiments.chunk_experiment --keep        # 컬렉션을 남겨 대시보드에서 청크를 확인
python -m app.experiments.chunk_experiment --size 200 --overlap 40 --max-chars 200   # 파라미터 변경
```

| 옵션 | 기본값 | 설명 |
| --- | --- | --- |
| `--size` / `--overlap` | 150 / 30 | fixed 청크 글자 수와 겹치는 글자 수 |
| `--max-chars` | 150 | sentence 청크 최대 글자 수 |
| `--sem-max` | 300 | semantic 청크 최대 글자 수 |
| `--k` | 0.5 | semantic 분할 민감도. 작을수록 많이 자름 |
| `--keep` | 끔 | 실험 컬렉션 유지 |
| `--show` | 끔 | 전략별로 잘린 청크를 출력하고 실험은 계속 진행 |
| `--chunks-only` | 끔 | 청크만 출력하고 종료. Qdrant 저장과 질문 검색을 하지 않아 호출이 가장 적다 (semantic 의 문장 임베딩 약 50건만 사용) |

API 호출량: 청크 약 60건(전략 4개) + semantic 문장 약 50건 + 질문 12건 = 약 120건. **무료 한도는 임베딩 분당 100건**이라 한 번에 보내면 넘는다. 처음에는 "한도 안"이라고 잘못 계산했고 실제로 429 가 났다(아래 문제 참고). 지금은 한도 보호가 들어 있어 실행에 1~2분 걸린다.

## 5-1. 옵션을 바꾸면 청크가 어떻게 달라지나

아래 예시는 `long_docs.py` 의 `guide-refund` 첫 문단(159자)에 실제 청킹 함수를 돌린 출력이다. 문서에는 없는 가상의 문장이 아니다. `[숫자]` 는 그 청크의 글자 수이다.

> 원문 첫 문단 (159자)
> 환불은 상품을 받은 날부터 7일 이내에 마이페이지에서 신청할 수 있습니다. 단순 변심으로 환불하는 경우 왕복 배송비 5,000원은 고객이 부담합니다. 상품에 하자가 있거나 다른 상품이 배송된 경우에는 받은 날부터 30일 이내에 무료로 환불해 드리며, 이때 배송비는 판매자가 부담합니다.

### 청크(chunk)란

문서를 통째로 벡터 하나로 만들지 않고, 잘라 놓은 조각 하나하나를 청크라고 한다. 청크 하나가 Qdrant 에 점(point) 하나로 저장되고, 검색하면 문서가 아니라 청크가 돌아온다. 그래서 어떻게 자르느냐에 따라 검색 결과가 달라진다. 너무 크면 한 청크에 여러 주제가 섞여 점수가 흐려지고 LLM 에 보내는 글도 길어진다. 너무 작으면 답에 필요한 문장이 둘로 쪼개져 어느 쪽에도 답이 온전히 없다.

### `--size` : fixed 청크의 글자 수

"150" 은 한 청크의 **최대** 글자 수이다. 앞에서부터 150글자를 떼어 한 청크로 만든다. 문장이 끝나는 곳을 보지 않으므로 150번째 글자가 단어 중간이어도 거기서 자른다. 문서가 150자보다 짧으면 자르지 않고 그대로 한 청크가 된다.

### `--overlap` : 앞 청크와 겹치는 글자 수 (fixed)

다음 청크는 `size - overlap` 글자 뒤에서 시작한다. 즉 앞 청크의 끝 `overlap` 글자가 다음 청크의 앞부분에 다시 들어간다. 필요한 이유는 경계에 걸린 문장을 살리기 위해서이다. 겹침이 없으면 한 문장이 두 청크로 갈라져 둘 다 반쪽짜리가 된다.

| size / overlap | 청크 수 | 잘린 모습 |
| --- | --- | --- |
| 80 / 0 | 2 | ① `…고객이 부담합` ② `니다. 상품에 하자가…` : "부담합니다" 가 두 조각으로 갈라짐 |
| 80 / 20 | 3 | ① `…고객이 부담합` ② `배송비 5,000원은 고객이 부담합니다. 상품에 하자가 …환불해 드리며,` ③ `0일 이내에 무료로 환불해 드리며, 이때 배송비는 판매자가 부담합니다.` : ②가 ①의 끝 20자를 되풀이해서 "부담합니다" 가 한 청크에 온전히 들어간다. 대신 ③은 "30일" 의 "3" 이 잘려 `0일` 로 시작한다 |
| 150 / 30 | 2 | ① 150자에서 `…이때 배송비는 판매` 로 끝남 ② `0일 이내에 무료로 환불해 드리며, …` (39자). 핵심인 "30일" 이 ① 안에는 있지만 ② 는 `0일` 로 시작 |
| 250 / 50 | 1 | 문단이 159자라 자를 필요가 없어 통째로 한 청크 |

겹침을 늘리면 경계 문제는 줄지만 같은 글이 여러 청크에 중복 저장되어 청크 수와 임베딩 호출이 늘어난다. 실제로 `--overlap 0` 으로 오프라인 계산하면 size 150 에서 12문항 중 9개만 맞는다(겹침 30 이면 10개). 이 값은 코드로 확인한 오프라인 계산이고 Qdrant 검색까지 돌려 본 것은 아니다.

### `--max-chars` : sentence 청크의 글자 수 상한

문장 단위로 모으되 합친 길이가 상한을 넘으면 새 청크를 시작한다. fixed 와 달리 문장 중간에서는 절대 자르지 않는다. 상한보다 긴 문장 하나는 쪼개지 않고 그대로 둔다.

| max-chars | 청크 수 | 결과 |
| --- | --- | --- |
| 60 | 3 | 문장마다 한 청크 `[41] 환불은 …신청할 수 있습니다.` `[41] 단순 변심으로 …부담합니다.` `[75] 상품에 하자가 …` (세 번째 문장은 상한 60 을 넘지만 쪼개지 않고 그대로 둠) |
| 100 | 2 | 1·2번 문장이 합쳐진 `[83]`, 3번 문장 `[75]` (합치면 158 이라 100 초과) |
| 150 | 2 | 100 과 동일 (세 문장 합 159 > 150) |
| 250 | 1 | 세 문장이 모두 합쳐진 `[159]` |

문장이 끝나는 곳에서만 자르기 때문에 "고객이 부담합" 같은 조각이 생기지 않는다.

### `--sem-max` 와 `--k` : semantic

semantic 은 먼저 문장 단위로 나누고 각 문장을 임베딩한다. 이어서 이웃한 두 문장의 코사인 유사도를 구하고, 그 값이 `평균 − k × 표준편차` 보다 낮은 곳을 주제가 바뀐 지점으로 보고 자른다. 누적 길이가 `--sem-max` 를 넘으면 강제로 자른다.

| 옵션 | 효과 |
| --- | --- |
| `--k` 를 낮춤 (예: 0.2) | 기준선(평균 − k·표준편차)이 평균에 가까워져서 유사도가 조금만 낮아도 자른다 → 청크가 작고 많아짐 |
| `--k` 를 높임 (예: 1.0) | 기준선이 낮아져서 유사도가 많이 떨어질 때만 자른다 → 청크가 크고 적어짐 |
| `--sem-max` 를 낮춤 | 주제가 안 바뀌어도 그 길이에서 강제로 자름 |

기본값(0.5) 실행에서는 18청크, 평균 85자였다. **`--k` 를 바꾼 실행은 하지 않았으므로 위 표는 계산식에서 나온 방향성 설명이고 실측 결과가 아니다.** 실제로 어디서 잘렸는지는 결과 문서의 "semantic 이 실제로 자른 경계" 에 있다.

### 전략별로 같은 문서를 자르면 (문서 `guide-refund` 전체, 기본 옵션 기준)

| 전략 | 자르는 기준 | 이 문서에서 나온 청크 |
| --- | --- | --- |
| fixed | 글자 수 | 문장 중간에서 끊김. 예: `…고객이 부담합` / `니다. 상품에…` |
| sentence | 문장 끝 | 문장 1~2개씩. 예: `환불은 상품을 받은 날부터 7일 …` + `단순 변심으로 …` |
| paragraph | 빈 줄(`\n\n`) | 4개 청크: 환불 신청/비용 문단(159자), 환불 불가 품목(115자), 환불 처리 시간(115자), 교환(93자). 문단 하나가 한 청크 |
| semantic | 의미 변화 | 문장 임베딩 유사도가 떨어지는 곳. 문단 경계와 다를 수 있음 |

## 6. 결과를 읽는 법

- top-1 과 top-3 의 차이가 큰 전략은 정답이 있기는 한데 순위가 밀린다는 뜻이다. top-3 를 모델에 넘기는 RAG 에서는 top-3 가 더 중요하다.
- 정확도가 비슷하면 평균 길이가 짧고 성공 시 top-1 길이가 짧은 쪽이 토큰이 적게 든다.
- semantic 이 가장 좋을 거라고 단정하지 않는다. 문서가 문단으로 잘 나뉘어 있으면 paragraph 가 같거나 더 낫고 훨씬 싸다. 이 비교가 실험의 핵심이다.
- 표본이 문서 4개, 질문 12개뿐이라 작은 차이는 의미가 없다. 1~2개 차이는 우연일 수 있다고 적는다.
- 질문별 표에서 X 가 나온 질문은 어느 전략이 왜 놓쳤는지 `--keep` 으로 청크를 열어 확인한다.

## 8. 문제와 해결

| 문제 | 원인 | 해결 |
| --- | --- | --- |
| 첫 실행에서 `429 RESOURCE_EXHAUSTED` (`embed_content_free_tier_requests`, limit 100) | 임베딩 무료 한도가 분당 100건인데, 텍스트 1개가 1건으로 계산된다. 이 실험은 약 120건을 한꺼번에 보냄. 배치로 묶어도 건수는 줄지 않는다 | `chunk_experiment.py` 에 한도 보호 추가: 최근 60초 사용량을 세어 90건 넘으면 대기, 429 가 와도 안내된 시간만큼 쉬고 최대 3번 재시도, 같은 텍스트는 캐시 |

에러 메시지 읽는 법:
- `limit: 100` 과 `PerMinute` : 분당 한도다. 하루 한도가 아니라서 1분 기다리면 풀린다.
- `Please retry in 46s` : 이 시간 뒤에 다시 시도하라는 뜻. 재시도 코드가 이 값을 읽어 쓴다.
- 한도 보호가 켜진 실행에서 "(임베딩 한도 보호: N초 대기)" 가 찍히는 것은 정상이다.

교훈: 외부 API 를 반복 호출하는 코드는 한도 계산을 먼저 해야 한다. 이 프로젝트의 주제(느리고 한도가 있는 AI 호출 제어)와 같은 문제를 작은 규모로 겪은 것이므로 보고서의 "임베딩 호출은 배치 크기가 아니라 건수 기준으로 제한된다" 재료로 쓸 수 있다.
