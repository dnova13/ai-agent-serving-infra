# 가이드 — 도구(Tool) 추가와 Conditional Edge 분기 검증

## 이 작업을 왜 했는가

Day3에서 LangGraph로 전환할 때, 도구가 `search_vector_db` 1개뿐이었다.
이 상태로는 Conditional Edge(`should_continue`)가 실제로 "여러 도구 중에서
상황에 맞는 걸 정확히 골라내는지"를 검증할 수 없었다 — "도구를 쓰느냐 마느냐"
라는 이분법만 확인 가능했기 때문이다.

실제 프로젝트가 진행되면(2주 차 이후) 도구가 여러 개(Vector DB 검색, DB 조회,
외부 API 등) 붙게 되는데, 그때 가서야 "모델이 도구를 헷갈려 하네?"를 발견하면
늦는다. 그래서 1주 차 마무리 시점에 도구를 하나 더 추가해서 분기 정확도를
미리 검증했다.

---

## 핵심 개념 — 모델은 어떻게 "알맞은 도구"를 고르는가

AI가 질문을 받으면, 등록된 도구들의 **설명(description)** 을 전부 읽고
그중 질문과 가장 관련 있는 도구를 스스로 판단해서 선택한다.

```python
@tool
def search_vector_db(query: str) -> str:
    """사내 문서/상품 리뷰 등에서 질문과 의미적으로 유사한 문서를 검색한다."""
    ...

@tool
def get_current_time() -> str:
    """현재 날짜와 시간을 반환한다. 시간/날짜를 묻는 질문에만 사용."""
    ...
```

- `"""..."""` (docstring) 부분이 **모델에게 주는 도구 사용 설명서**다.
- 모델은 이 설명을 읽고 "환불 정책 질문 → search_vector_db가 적합하겠다",
  "시간 질문 → get_current_time이 적합하겠다"를 스스로 추론한다.
- **개발자가 if-else로 분기 로직을 직접 짜는 게 아니라, 모델이 자연어 이해로
  알아서 도구를 선택**한다는 점이 핵심이다. 이게 Conditional Edge가 하는 일의
  본질 — 그래프 구조 자체는 "도구 호출 여부"만 보고 다음 노드를 정하고,
  "어떤 도구를 쓸지"는 모델이 판단한다.

---

## 처리 흐름 (전체 그림)

```
사용자 질문
    │
    ▼
[Agent Node] ← 모델이 질문 + 등록된 모든 도구의 description을 함께 봄
    │
    │  모델의 판단
    │
    ├── "이 질문엔 search_vector_db가 필요하다" → tool_calls에 담아서 응답
    ├── "이 질문엔 get_current_time이 필요하다" → tool_calls에 담아서 응답
    └── "도구 필요 없다, 바로 답할 수 있다" → 텍스트로 바로 응답
    │
    ▼
[Conditional Edge: should_continue]
    │
    ├── tool_calls가 있으면 → "tools" 노드로 이동
    │        │
    │        ▼
    │   [Tool Node] ← tool_calls에 담긴 도구 이름으로 실제 함수를 찾아 실행
    │        │
    │        └── 결과를 다시 [Agent Node]로 전달 (루프)
    │
    └── tool_calls가 없으면 → END (종료, 최종 답변 반환)
```

---

## 검증에 사용한 질문 3개와 그 이유

각 질문은 위 그림에서 **서로 다른 경로**를 대표하도록 골랐다.
하나만 테스트하면 "우연히 맞았나?" 하는 의심이 남지만, 세 경로를 모두
확인하면 분기 로직 전체가 신뢰할 만하다고 판단할 수 있다.

| 질문 | 기대하는 경로 | 실제 결과 (Gemini) |
|---|---|---|
| "환불 정책이 어떻게 되나요?" | Agent → tools(search_vector_db) → Agent → END | ✅ 정확히 분기, 7일 이내 환불 정보 반영 |
| "지금 몇 시야?" | Agent → tools(get_current_time) → Agent → END | ✅ 정확히 분기, 실제 현재 시각 반환 |
| "안녕!" | Agent → END (도구 없이 바로 종료) | ✅ 도구 호출 없이 바로 인사 답변 |

세 갈래 모두 정확히 갈렸으므로, Conditional Edge가 신뢰할 만하게 동작한다고
결론 내렸다.

## Claude provider 관련

`get_model(provider)`에서 `provider="claude"`도 코드 구조상 지원하지만,
Claude API는 유료(사용량 기반 과금)이기 때문에 **의도적으로 키를 비워두고
실사용을 보류**했다. 이 상태에서 Claude로 호출을 시도하면 인증 에러가 나는데,
`try/except`로 감싸져 있어 프로그램이 죽지 않고 "실패" 로그만 남기고
다음 질문으로 넘어간다 — 이 에러 핸들링이 정상 작동하는 것도 함께 확인했다.

나중에 필요하면 `.env`의 `ANTHROPIC_API_KEY`만 채우면 즉시 Claude로도
동일한 테스트가 가능한 구조다.
