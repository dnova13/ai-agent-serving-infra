> 모델 한 곳이 실패하거나 느려져도 서비스가 멈추지 않게 하는 폴백(서킷 브레이커)을 만들고, 실제로 되는지 확인
> **앞 모델 가짜 + 뒤 모델 실제 Claude 점검 PASS 7, 실제 모델 3단계 PASS 3 (결과는 [DAY36_RESULT.md](DAY36_RESULT.md)).**
> 코드 흐름은 [DAY36_CODE_GUIDE.md](DAY36_CODE_GUIDE.md). 앞선 결과: [DAY35_RESULT.md](DAY35_RESULT.md).
> 이 날도 **가짜 모델과 실제 모델을 둘 다 쓴다**. 가짜 모델은 폴백과 브레이커 동작을 정확히 확인하고, 실제 모델은 Gemini, Claude 가 실제로 이어지는지 소량으로 본다.

**전체 목적:** 지금은 `provider: "gemini"` 로 보내면 Gemini 만 부르고, Gemini 가 장애이면 요청이 그대로 실패한다. (1) 앞 모델이 실패하면 다음 모델로 넘어가게(폴백) 하고, (2) 앞 모델이 계속 실패하면 일정 시간 아예 부르지 않아(서킷 브레이커) 장애인 모델을 기다리느라 모든 요청이 느려지는 일을 막는다.

## 1. 오늘 목표

| 확인할 것                                                                                                         | 모델 |
| ----------------------------------------------------------------------------------------------------------------- | ---- |
| 정상일 때는 앞 모델만 쓰고 폴백이 일어나지 않는다                                                                 | 가짜 |
| 앞 모델이 장애이면 요청은 실패하지 않고 뒤 모델이 답한다                                                          | 가짜 |
| 연속 3번 실패하면 앞 모델을 건너뛴다(브레이커 열림), 없을 때보다 빠르다                                           | 가짜 |
| 쉬는 시간 뒤 한 번만 다시 시도하고, 실패하면 다시 쉬고, 성공하면 앞 모델로 돌아간다                               | 가짜 |
| 모든 모델이 장애이면 예외를 낸다, 모르는 모델 이름은 거절한다                                                     | 가짜 |
| ① Gemini 만, ② Claude 만 각각 질문이 성공한다 (기준선)                                                            | 실제 |
| ③ 폴백 `gemini>claude` 에서 Gemini(실제 호출)가 무료 한도 등으로 실제로 실패하면 질문은 성공하고 Claude 가 답한다 | 실제 |

> 위 "가짜" 점검 중 B, D, C, E 는 `fake>claude`(뒤 모델이 실제 Claude)로도 돈다(4절 ①-2). 뒤 모델까지 가짜인 `fake>fake-b` 점검은 코드에 남아 있어 무료로 다시 돌릴 수 있다.

| 이름                         | 기본값 | 뜻                                                                                     |
| ---------------------------- | ------ | -------------------------------------------------------------------------------------- |
| `MODEL_BREAKER_THRESHOLD`    | 3      | 연속 이만큼 실패하면 그 모델을 건너뛴다                                                |
| `MODEL_BREAKER_COOLDOWN_SEC` | 30     | 건너뛰는 시간(초). 지나면 한 번만 다시 시도한다                                        |
| `MODEL_FAULT_INJECTION`      | false  | true 일 때만 아래 장애 주입이 동작한다(가짜 모델 점검용. 실제 모델 단계는 쓰지 않는다) |
| `MODEL_FORCE_DOWN`           | 빈 값  | 호출 전에 일부러 실패시킬 모델 이름(쉼표로 여러 개)                                    |
| `MODEL_DOWN_DELAY_SEC`       | 0      | 장애 주입 시 실패하기 전에 기다릴 초(타임아웃까지 기다리는 장애 흉내)                  |

## 4. 실험

### ① 가짜 모델 (무료)

    python -m app.checks.model_fallback_check

PASS 8, 결과 PASS 면 통과. 몇 초 걸린다(장애 주입 지연 0.3초 × 몇 번).

### ①-2. 앞 모델 가짜 + 뒤 모델 실제 Claude (Claude 를 부른다)

    python -m app.checks.model_fallback_check --fake-claude --dry
    python -m app.checks.model_fallback_check --fake-claude --cooldown 30

`--dry` 는 뒤 모델을 가짜로 바꿔 Claude 를 부르지 않고 흐름만 본다(Claude 0번). 두 번째는 실제 Claude 를 약 32번 부르고, 코드가 40번에서 멈춘다. `ANTHROPIC_API_KEY` 가 필요하다(검색 도구는 쓰지 않는다).

**기대**

- PASS 7, 결과 PASS. 약 2분(D, C 단계가 쉬는 시간 30초씩 기다린다).
- B: 뒤 모델 claude 10/10, 앞 모델 실패 3회·건너뜀 7회. 브레이커 있음이 없음보다 빠르다.
- `--cooldown` 을 안 붙이면 쉬는 시간이 1초라서, Claude 한 번(약 1초)보다 짧아 도중에 다시 시도가 끼어 앞 모델 실패가 3회보다 늘고 FAIL 이 나올 수 있다. 쉬는 시간은 호출 시간보다 길게 둔다.

### ② 실제 모델 (Gemini, Claude 를 실제로 부른다)

    python -m app.checks.model_fallback_check --real

한 단계만 돌리려면 `--only` 를 붙인다. 안 붙이면 세 단계가 모두 돈다.

| 명령                                                                       | 도는 단계                 |
| -------------------------------------------------------------------------- | ------------------------- |
| `python -m app.checks.model_fallback_check --real --only gemini`         | ① Gemini 만               |
| `python -m app.checks.model_fallback_check --real --only claude`         | ② Claude 만               |
| `python -m app.checks.model_fallback_check --real --only fallback`       | ③ 폴백(`gemini>claude`)만 |
| `python -m app.checks.model_fallback_check --real --only fallback --n 5` | ③ 을 질문 5건으로         |

`--n` 은 **한 단계에서 보낼 질문 수**다. 기본값은 3이다. 질문은 준비된 5개(환불, 교환, 배송, 주문 취소, 환불 수수료)를 돌려 쓴다. 그래서 `--n 20` 이면 서로 다른 질문 20개가 아니라 같은 5개가 4번씩 나간다. 질문은 한 건씩 차례로 보내고 동시에 보내지 않는다. 단계마다 `--n` 건이므로 `--only` 없이 세 단계를 모두 돌리면 `--n` 의 3배가 나간다(`--n 20` 이면 60건).

질문 한 건마다 모델을 약 2번(+ 검색 임베딩) 실제로 부르므로 `--n` 이 클수록 오래 걸리고 호출이 늘어난다. Gemini 는 한 번에 100초 넘게 걸릴 때가 있어(Day 36 에서 `--n 20` 을 돌렸을 때 ① 의 질문당 평균 105초) 처음에는 `--n 3`(기본값)이나 `--n 5` 를 권한다.

이 출력의 단계는 ① Gemini 만, ② Claude 만, ③ 폴백(`gemini>claude`) 순서로 돈다(이 ①②③ 은 위 ①② 와 별개다). 가짜 장애는 쓰지 않고 Gemini 를 실제로 부른다. 질문을 늘리려면 `--n 20`(질문 5개를 돌려 쓴다).

Gemini 무료 한도는 작아서 걸릴 수 있다. 한도에 걸려 Gemini 가 실제로 실패하면 ③ 에서 Claude 로 넘어가는 모습을 그대로 볼 수 있다. 한도에 걸리지 않으면 폴백이 일어나지 않으므로 걸릴 때까지 `--n` 을 늘려 다시 돌린다.

**기대**

- ② 는 성공 n/n, 질문당 약 3~10초(Day 34.2 의 Claude 처리 시간 3.4초가 기준).
- ① 은 참고 값이라 판정하지 않는다. Gemini 가 한도에 걸리면 여기서 실패 건이 나온다(폴백이 없을 때의 모습).
- ③ 은 성공 n/n. Gemini 가 실패한 만큼 모델 호출 기록에 `error:gemini` 가 나오고, 연속 3번 실패하면 `skipped:gemini` 가 이어지며 `served:claude` 가 늘어난다. Gemini 가 멀쩡하면 `served:gemini` 만 나온다.
- Gemini 쪽 라이브러리가 한도 오류를 자동 재시도하면 실패하기까지 시간이 길어질 수 있다. 질문당 시간에 그대로 나타난다.
- 서버 장애, 응답 지연(타임아웃)은 이 실험으로 보지 못한다. 검색 임베딩도 Gemini 이므로 한도에 걸리면 도구 실패로 나올 수 있다(Day 31 의 재시도가 처리).

**실패했을 때**

- 키가 없으면 `--real` 이 건너뛴다고 출력하고 끝난다(결과는 요약만).
- ② 가 실패하면 폴백 문제가 아니라 Claude 호출 문제(키, 한도, Qdrant)다. 오류 문구를 보낸다.
