# Day 6 실행 가이드 — 1주차 마무리, retry_count 실전 검증

## 목표
1주 차 전체를 리뷰하고, 지금까지 선언만 해둔 채 미사용이었던 State 필드
`retry_count`를 실제로 그래프 흐름에 관여하도록 만든 뒤, 강제로 실패
상황을 만들어 검증한다. 마지막으로 커밋과 README 초안까지 완료한다.

(상세 테스트 과정과 로그는 `DAY6_TEST_LOG.md` 참고)

---

## 왜 이 작업이 필요했는가

1주 차 동안 도구가 1개(`search_vector_db`)뿐이었던 시점에는, Conditional
Edge가 "도구를 쓰느냐 마느냐"라는 이분법만 검증됐다. 또한 `retry_count`는
State에 선언만 해두고 실제로 증가시키거나 참조하는 코드가 없었다 —
즉 "동작할 수 있는 구조"였지 "실제로 동작을 확인한 것"은 아니었다.

Day6는 이 두 가지 미검증 지점을 실제로 채우는 작업이다.

---

## 작업 순서

### 1) 도구 추가로 분기 다양성 확보
`get_current_time` 도구를 추가하고, 서로 다른 경로(검색 필요 / 시간 필요 /
도구 불필요)를 대표하는 질문 3개로 Conditional Edge 분기를 검증했다.
→ 3개 모두 정확히 분기됨 (Gemini 기준).

### 2) retry_count를 실제로 동작시키기 — 1차 시도 (실패)

`tool_node`가 예외를 잡아서 `retry_count`를 증가시키고, `after_tools_router`가
`retry_count >= MAX_RETRIES`면 `give_up` 노드로 보내도록 구현했다.

**문제**: 강제로 실패를 유도하는 테스트 질문을 던졌더니, 최종 답변 문구가
`give_up_node`에 하드코딩한 문구와 달랐다. `give_up_node`를 실제로
거쳤는지 의심스러웠다.

### 3) 디버그 로그로 원인 진단

`after_tools_router`와 `give_up_node`에 `[DEBUG] print`를 추가해서
실행 경로를 직접 확인했다.

**결과**: `after_tools_router`는 1번만 호출되고 `retry_count=1`에서 멈췄다.
`give_up_node`는 아예 호출되지 않았다.

**원인**: 실패 시 `agent` 노드로 돌려보내 "모델이 알아서 재시도하길"
기대했는데, 모델이 1번 실패하고는 재시도 없이 스스로 사과 답변을 만들어
버렸다. 그래프 구조상 이게 가능했던 이유는, `should_continue`가
"tool_calls가 없으면 END"로 보내기 때문에, 모델이 도구를 다시 안 부르고
텍스트로만 답하면 그대로 종료돼버린 것이다.

### 4) 설계 변경 — 결정적(deterministic) 재시도로 전환

모델의 자율 판단에 재시도 여부를 맡기지 않고, **그래프가 직접 같은 요청을
반복**하도록 바꿨다.

핵심 변경:
- `AgentState`에 `pending_tool_calls` 필드 추가 — 재시도 시 원본 도구
  요청(어떤 도구를, 어떤 인자로 호출했는지)을 보존
- `tool_node`가 `state["messages"][-1]`이 아니라 `state["pending_tool_calls"]`를
  실행 대상으로 삼도록 변경 (재시도로 다시 호출돼도 실행 대상을 잃지 않음)
- `after_tools_router`: 실패 시 `agent`가 아니라 `tools`로 직접 재시도.
  재시도 여력이 없을 때만 `give_up`으로.
- 그래프에 `tools → tools` 자기 자신으로 돌아가는 엣지 추가

### 5) 재검증 — 성공

같은 실패 테스트를 다시 실행한 결과, 로그가 정확히 아래 순서로 찍혔다:
```
after_tools_router 호출됨: failed=True, retry_count=1
after_tools_router 호출됨: failed=True, retry_count=2
give_up_node 진입함 (retry_count 한계 도달, 강제 종료 처리)
```
최종 답변도 `give_up_node`에 하드코딩한 문구와 정확히 일치했다.
**모델이 개입할 여지 없이, 설계한 그래프 구조대로 정확히 실행됨을 확인.**

## 부수적으로 해결한 이슈 — Gemini API 일일 쿼터

테스트를 반복하다 `gemini-3.6-flash`의 일일 무료 요청 한도(20건)를
소진해서 429 에러를 만났다. 재시도 로직 자체가 실패 시 모델을 여러 번
호출하는 구조라서 쿼터 소모가 예상보다 빨랐다.

**해결**: 무료 티어 한도가 더 넉넉한 `gemini-3.1-flash-lite`로 모델을
교체해서 개발 중 반복 테스트를 계속 진행할 수 있게 했다.

**참고**: 5주 차 k6 부하 테스트 때는 무료 티어로는 어차피 부족할 것으로
예상되어, Google Cloud 결제 계정 연결(Tier 1, 최소 결제액/대기 기간 없음)을
그때 검토하기로 했다.

## 이번 작업에서 얻은 설계 교훈

**"모델에게 판단을 맡길 일"과 "시스템이 기계적으로 처리해야 할 일"을
구분해야 한다.** 일시적 기술 오류(네트워크 장애, API 순간 오류 등)에 대한
재시도는 모델이 고민할 문제가 아니라 인프라 레벨에서 결정적으로 처리해야
하는 영역이다. 이번에 겪은 실패(모델에게 재시도를 맡겼다가 실패)가 정확히
이 경계를 잘못 그은 사례였고, 이를 수정하면서 "언제 모델의 자율성에
맡기고, 언제 그래프가 강제해야 하는가"라는 기준이 명확해졌다.

이 구분은 6주 차 Self-Correction 고도화에서도 그대로 적용된다 —
지금 구현한 "동일 요청 기계적 반복"은 기술적 실패 대응이고, 앞으로 다룰
"실패 원인을 분석해서 다른 전략(다른 검색어, 다른 도구)으로 재시도"는
모델의 판단이 필요한 영역이라 별개로 설계해야 한다.
