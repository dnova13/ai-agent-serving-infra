# Day 25 결과 — k6 설치와 ramping 부하 시나리오

> 사용법과 기대값은 [DAY25_GUIDE.md](DAY25_GUIDE.md), 코드 흐름은 [DAY25_CODE_GUIDE.md](DAY25_CODE_GUIDE.md). 이 문서는 실행한 것과 확인한 결과를 담는다.
> 상태: 가이드 ① (k6 버전 확인), ② (가짜 LLM 으로 한 건), ③ (k6 스모크), ④ (ramping, 접수만 재기, VU 20), 그 직후의 Kafka lag 확인, ⑤ (ramping, 완료 시간까지 재기, VU 10), ⑥ (ramping, 접수만 재기, VU 300), ⑤-2 (대기 중 조회가 404 인 것 확인)를 내 환경에서 실행해 기록함(2026-10-16). 모두 실행했다. 단 ⑤ 와 ⑥ 뒤에 쌓인 요청의 비우기와 LAG 0 확인 출력은 기록이 없다(5번).
> 포트: **8080 = Spring WAS**, **8000 = FastAPI 워커 1**, **8001 = FastAPI 워커 2**. ②~⑥ 은 Spring(8080) → Kafka → 워커를 거쳤고 결과는 8000 에서 조회했다.

**전체 목적:** 실제 LLM 없이 부하를 걸기 위해 만든 가짜 LLM(`provider: fake`)이 서버 구조(Spring → Kafka → 워커 → Redis 결과) 안에서 켜져 있고, 설계한 지연(약 5초)만큼 걸려 `DONE` 이 되는지 확인하고(②), k6 로 같은 경로(접수 → DONE)가 한 번 통과하는지 본다(③). 가상 사용자를 0 에서 20 까지 올려 Spring 의 접수(202)가 빠르고 실패가 없는지 본다(④). k6 버전 확인(①)과 완료 시간까지 재는 ramping(⑤)으로 접수 시간과 완료 시간이 얼마나 다른지 본다. 마지막으로 300 VU 까지 올려 접수가 어느 부하에서 느려지거나 실패하는지 본다(⑥).

### 2-1. 시나리오 내용 (`scripts/k6/ramping.js`)

④, ⑤, ⑥ 은 같은 스크립트이고 환경변수만 다르다. 스크립트가 하는 일은 아래와 같다.

**가상 사용자(VU)가 하는 일 (한 번의 반복)**

| 순서 | `MODE=async`, `POLL=0` (④, ⑥)                                                        | `MODE=async`, `POLL=1` (⑤)                                                                  |
| ---- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| 1    | 질문 5개 중 하나를 무작위로 골라 `POST localhost:8080/api/agent/requests` (`provider: fake`) | 같음                                                                                        |
| 2    | 응답이 `202` 인지 확인(`check`), 성공 여부를 `accepted` 에 기록                       | 같음                                                                                        |
| 3    | -                                                                                    | 202 면 `requestId` 로 1초마다 `GET localhost:8000/api/v1/agent/results/{requestId}` 를 반복  |
| 4    | -                                                                                    | `DONE` 이면 접수 전부터 지금까지의 시간을 `e2e_ms` 에 기록하고 `results_done` +1, `FAILED` 면 `results_failed` +1, `POLL_MAX_SEC`(120초) 안에 끝나지 않으면 `results_poll_timeout` +1 |
| 5    | `THINK_SEC`(1초) 쉬고 처음으로 돌아감                                                | 같음                                                                                        |

`MODE=sync` 는 `POST localhost:8000/api/v1/agent/run` 에 질문을 보내고 답이 올 때까지 기다린 뒤(`POLL_MAX_SEC` 초가 요청 시간 제한) `200` 인지 확인한다. Day 26 에서 쓸 것이며 Day 25 에서는 실행하지 않았다.

질문 5개: 단순 변심 환불 배송비, 환불 신청 기간, 교환 배송비, 배송 지연, 주문 취소 방법. 가짜 모델은 질문 내용을 쓰지 않으므로 응답에는 영향이 없다.

**부하 곡선 (`ramping-vus`, 시작 VU 0)**

| 단계     | 시간(기본) | VU 변화              |
| -------- | ---------- | -------------------- |
| 올리기   | 30초       | 0 → `MAX_VUS` (직선) |
| 유지     | 30초       | `MAX_VUS`            |
| 내리기   | 10초       | `MAX_VUS` → 0        |

`gracefulRampDown` 은 5초다. VU 가 줄어들 때 진행 중인 반복에 5초를 주고, 그 안에 끝나지 않으면 중단(interrupted)한다. ⑤ 에서 반복 8건이 중단된 것이 이 때문이다.

**실행별 값과 예상 요청 수**

| 실행 | `MAX_VUS` | `POLL` | VU 시간(올리기 + 유지 + 내리기) | 반복 수 계산 | 실제 |
| ---- | --------- | ------ | -------------------------------- | ------------ | ---- |
| ④    | 20        | 0      | 300 + 600 + 100 = 1000 VU·초     | 반복이 약 1초라 약 1000건 | 985건 |
| ⑤    | 10        | 1      | 150 + 300 + 50 = 500 VU·초       | 반복이 완료를 기다려 수 초~수십 초라 건수를 계산하지 않음 | 접수 30건 |
| ⑥    | 300       | 0      | 4500 + 9000 + 1500 = 15000 VU·초 | 반복이 약 1초라 약 15000건 | 14974건 |

**재는 지표와 임시 기준**

| 지표                       | 의미                                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------------------- |
| `accepted` (Rate)          | 접수(202) 성공 비율. 임시 기준 99% 초과                                                           |
| `http_req_duration{name:POST /api/agent/requests}` | 접수 요청의 응답 시간. 임시 기준 p(95) 2초 미만. 결과 조회 요청은 이름표(`tags.name`)가 달라 제외 |
| `e2e_ms` (Trend)           | `POLL=1` 일 때 접수부터 `DONE` 까지의 시간                                                         |
| `results_done`, `results_failed`, `results_poll_timeout` | `POLL=1` 일 때 결과별 건수                                                       |
| `http_req_failed`          | k6 기본 지표. 이 스크립트는 결과 조회(`GET`)의 404 를 정상으로 두지만, 이 문서의 ⑤ 는 그 수정 전 실행이다 |

**성격과 한계**

| 항목                | 내용                                                                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| closed 모델         | VU 는 응답을 받아야 다음 요청을 보낸다. 서버가 느려지면 보내는 요청도 줄어든다. ④, ⑥ 은 접수가 즉시 끝나 VU 하나가 초당 약 1건을 보냈다 |
| 임계값은 중단 조건이 아님 | `abortOnFail` 이 없어 기준을 넘어도 시험은 끝까지 간다. 요약에 ✓/✗ 로만 표시된다                                                    |
| 쌓인 요청 정리 없음  | 시험이 끝나도 Kafka 에 쌓인 요청은 그대로 남는다(비우기는 DAY25_GUIDE ④-2)                                                            |

| 최소 완료 시간 5.02초                                              | 첫 요청이 지연 약 5초 안에 끝났으므로 ④ 에서 쌓인 요청이 앞에 줄 서 있지는 않았던 것으로 본다(④-2 의 비우기와 LAG 0 확인 출력은 기록하지 않았다) |
| `http_req_failed` 67.91% (362 / 533)                               | 접수 30건은 모두 202 였으므로 실패는 결과 조회 요청(503건) 가운데 362건이다(약 72%). 조회 API 는 결과가 없을 때 404 를 주고(Day 17 의 `results.py`), 요청이 Kafka 에서 워커에 넘어가기를 기다리는 동안은 결과 키가 없다. k6 는 기본으로 404 도 실패로 센다. 그래서 이 수치는 서버 오류가 아니라 "아직 워커가 받지 않음"의 횟수로 본다. ⑤ 의 화면에는 상태 코드 분포가 없었으나, ⑤-2 에서 대기 중인 요청의 조회가 실제로 404 로 오는 것을 직접 확인했다(3-7). ⑤ 의 362건이 전부 404 인지는 이 기록만으로는 알 수 없다 |

| ⑥ 300 VU 에서도 접수 p(95) 14.71ms, 실패 0, 14974건 모두 202      | VU 20(④: 17.8ms)에서 300 으로 15배 올려도 접수 응답이 느려지지 않았다. 가이드 5번 ⑥ 에서 예상했던 응답 지연, `503`(Kafka 전송 5초 초과), 연결 실패는 나타나지 않았다. 이 실험에서는 접수의 한계 지점을 찾지 못했다 |

| 초당 211건을 접수                                                  | Spring 이 요청마다 Kafka 전송 완료(`acks=all`)를 동기로 기다리는데도 이 속도를 받았다. 이 시험에서의 접수 처리량은 최소 초당 약 211건이다(더 받을 수 있는지는 모른다) |
| ⑤-2 의 404 → PROCESSING → DONE                                    | 요청이 접수(202)된 직후에는 결과 키가 없어 404, 워커가 받으면 `PROCESSING`, 답이 나오면 `DONE` 으로 바뀌었다. 404 는 서버 오류가 아니라 큐에서 대기 중이라는 뜻이다. `PROCESSING` 약 4초는 가짜 지연(약 5초 ±20%)과 맞는다. 마지막 요청의 404 가 약 6초였던 것은 같은 워커 앞에 1건 정도가 먼저 처리되고 있었기 때문으로 본다(워커별 건수는 기록하지 않아 추정) |
| 대기가 풀리면 결국 `DONE` 이 되는가                                | ⑤-2 의 한 건은 404 → `PROCESSING` → `DONE` 으로 정상 완료됐다. 요청은 접수(202) 때 이미 Kafka 에 들어 있으므로 404 는 사라졌다는 뜻이 아니라 줄 서 있다는 뜻이고, 워커가 집어 가면 처리된다. 다만 "결국 된다"가 정상 서비스를 뜻하지는 않는다. ① 대기 시간은 앞에 쌓인 요청 수에 비례한다(⑥ 같은 부하의 쌓인 약 15000건은 약 10시간 분량으로 계산). ② 요청이 처리 속도보다 계속 빨리 들어오면 대기열이 줄지 않고 늘기만 한다. ③ 조회하는 쪽에서는 대기 중인 요청과 없는 `requestId` 가 모두 404 라 구분되지 않고, 클라이언트가 포기하고 다시 보내면 같은 요청이 중복 처리될 수 있다. 이 구조는 접수(202)를 보장하고 처리량을 넘는 부분을 지연으로 흡수하는 대신, 지연이 얼마나 길어지는지가 한계다 |
| 접수와 처리 속도의 차이                                            | 워커 2대의 처리량은 가짜 지연 5초 기준 최대 초당 약 0.4건이다. 초당 211건이 들어왔으므로 약 500배 빠르게 쌓인다. 쌓인 약 15000건을 이 속도로 처리하면 약 10시간이 걸린다고 계산한다(14974 × 5초 ÷ 2대 ≈ 37400초, 계산값). 비동기 구조가 접수에서는 버티지만 처리 능력을 넘는 요청은 큐에 쌓일 뿐 사라지지 않는다는 것이 이 실험의 모양이다 |
| 접수 요청 응답 시간이 위 "전체" 줄과 같음                          | POLL 없이 접수 요청만 보냈으므로 전체 통계와 접수 통계가 같다                                                                          |
