# Day 25 가이드 — k6 설치와 ramping 부하 시나리오

> 상태: 코드(가짜 LLM 모드)와 k6 스크립트 작성 완료. 아래 ①~⑥ 과 ⑤-2 는 모두 내 환경에서 실행해 DAY25_RESULT 3번에 기록했다(2026-10-16). 기대값은 실행 전에 적은 "확인 전 예상"이고, 실제 값은 DAY25_RESULT 를 따른다. ④-2(비우기)는 실행 출력을 기록하지 않았다. 스크립트 문법과 흐름은 코드를 만든 쪽의 샌드박스에서 k6(v0.54.0)와 가짜 HTTP 서버로 한 번 돌려 확인했고, 실제 Spring, Kafka, 워커로는 돌려 보지 않았다.
> 포트: **8080 = Spring WAS**, **8000 = FastAPI 워커 1**, **8001 = FastAPI 워커 2**, **6379 = Redis(redis1 컨테이너)**, 9092 = Kafka, 6333 = Qdrant.
> 코드 흐름은 [DAY25_CODE_GUIDE.md](DAY25_CODE_GUIDE.md). 다음 Day 26 은 이 시나리오를 동기 구조로 돌려 504 를 재현한다.

**전체 목적:** 5주차(k6 부하 테스트)의 첫날로, k6 를 설치하고 가상 사용자 수를 0 에서 올렸다 내리는 ramping 시나리오를 만든다. 실제 LLM 은 한도와 비용 때문에 수백 건을 보낼 수 없으므로 "정해진 시간 기다리는 가짜 LLM"(`provider: fake`)을 만들어 서버, Kafka, Redis, 워커 구조는 그대로 두고 부하를 건다. 오늘은 현재 구조(비동기: Spring 이 202 로 바로 응답)의 기준선을 잡는 것까지 한다.

| ④ 뒤 Kafka 에 쌓인 요청(LAG)을 확인하고 비운다                                                         | ④-2  |

| (선택) 300명까지 올리는 계획 시나리오와, 쌓인 요청 비우기                                             | ⑥    |


## 2. 개념

| 항목                          | 내용                                                                                                                                                       |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| VU (가상 사용자)              | k6 가 흉내 내는 동시 사용자 한 명. 각 VU 는 "요청 → 응답 기다림 → 쉬기(think time)"를 반복한다. 그래서 응답이 느려지면 같은 VU 수로도 보내는 요청 수가 줄어든다 |
| ramping-vus                   | VU 수를 단계(stages)에 따라 늘리고 줄이는 방식. 오늘은 `올리기(30s) → 유지(30s) → 내리기(10s)`                                                            |
| 접수 시간과 완료 시간         | 비동기 구조에서 Spring 이 202 를 주는 시간(접수)과, 워커가 답을 만들어 `DONE` 이 되는 시간(완료)은 다르다. k6 의 `http_req_duration` 은 접수 시간이다. 완료 시간은 `POLL=1` 로 결과를 조회해 따로 잰다(`e2e_ms`) |
| 가짜 LLM                      | `provider: fake` 이면 모델 호출이 "`FAKE_LLM_DELAY_SEC`(기본 5초)±20% 기다린 뒤 고정 문장 반환"으로 바뀐다. 도구를 부르지 않아 임베딩 API 와 Qdrant 는 쓰지 않는다. 지연은 실측이 아니라 **설계값**이고, 실제 에이전트는 LLM 2번과 검색 1번이라 건당 시간이 더 길다 |
| 워커 처리 방식                | 워커 한 대는 Kafka 메시지를 **한 건씩 차례로** 처리한다(`async for` 안에서 `await`). 워커 2대면 동시에 2건이다. 그래서 요청이 처리 속도보다 빨리 들어오면 Kafka 에 쌓이고 완료 시간이 길어진다 |
| 쌓인 요청                     | 시험이 끝나도 Kafka 에 남은 요청은 워커가 계속 처리한다. 가짜 LLM 5초 기준 워커 2대의 처리량은 최대 약 초당 0.4건이므로, 수천 건을 보내면 몇 시간치가 쌓인다. 비우는 방법은 ⑥ 에 있다 |

## 4. 준비

| 항목     | 방법                                                                                                                                         |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| k6 설치  | macOS: `brew install k6`. 설치 확인은 ①                                                                                                       |
| 컨테이너 | `docker ps` 에 `redis1`, Kafka, Qdrant 가 있다. Spring(8080)이 떠 있다                                                                        |
| 워커     | **8000 과 8001 두 대**를 띄운다. **가짜 LLM 을 켜려면 워커를 `FAKE_LLM_ENABLED=true` 로 띄워야 하므로 이미 떠 있는 워커는 끄고 다시 띄운다** |
| 공급자   | 이 Day 는 `provider` 를 `fake` 로 보낸다. API 키가 필요 없다                                                                                  |

```bash
# 터미널 1: 8000 = 워커 1
cd d2-ai-python
export KAFKA_WORKER_ID=w1
export FAKE_LLM_ENABLED=true
export FAKE_LLM_DELAY_SEC=5
uvicorn app.main:app --port 8000

# 터미널 2: 8001 = 워커 2
cd d2-ai-python
export KAFKA_WORKER_ID=w2
export FAKE_LLM_ENABLED=true
export FAKE_LLM_DELAY_SEC=5
uvicorn app.main:app --port 8001
```

`--reload` 는 붙이지 않는다(`run.sh` 는 붙이므로 쓰지 않는다). 부하 중에 파일 감시가 돌면 측정이 흔들린다.


## 5. 실행과 확인

### ① k6 설치 확인

**목적:** k6 를 실행할 수 있는지 본다. 즉시.

```bash
k6 version
```

기대(확인 전 예상): `k6 v1.x.x ...` 처럼 버전이 한 줄 나온다. 샌드박스 검증은 v0.54.0 으로 했고, 스크립트가 쓴 기능(`ramping-vus`, `Trend`, `Counter`, `Rate`, 태그 임계값)은 k6 의 기본 기능이다.

### ② 가짜 LLM 으로 한 건

**목적:** 가짜 모델이 켜져 있고 약 5초 뒤 결과가 DONE 이 되는지 본다. 약 10초.

```bash
ID=$(curl -s -X POST localhost:8080/api/agent/requests -H "Content-Type: application/json" \
  -d '{"question":"환불은 며칠 안에 신청해야 하나요?","provider":"fake"}' \
  | sed -E 's/.*"requestId":"([^"]+)".*/\1/')
sleep 7; curl -s localhost:8000/api/v1/agent/results/$ID
```

기대(확인 전 예상): `"status":"DONE"`, `"answer"` 가 `[fake] 가짜 응답입니다 (지연 4.x~6.x초)` 모양, `"elapsedMs"` 가 4000~6000 근처. `status` 가 `FAILED` 이고 `error` 에 `지원하지 않는 provider입니다: fake` 가 있으면 그 워커를 `FAKE_LLM_ENABLED=true` 로 띄우지 않은 것이다.

### ③ k6 스모크

**목적:** k6 로 접수부터 DONE 까지 한 번 통과하는지 본다. 약 10초.

```bash
k6 run scripts/k6/smoke.js
```

기대(확인 전 예상): 콘솔에 `접수 NNms requestId=...` 와 `완료 5xxxms worker=w1 또는 w2 partition=... answer=[fake] ...` 가 나오고, 요약의 `checks` 가 100%. 접수는 수십 ms 안쪽일 것으로 본다(Day 14, 17 의 202 응답과 같은 구조).

### ④ ramping 시나리오: 접수만 재기 (VU 20)

**목적:** 가상 사용자를 0 에서 20 까지 올려도 Spring 의 접수(202)가 빠르고 실패가 없는지 본다. 총 70초.

```bash
k6 run -e MODE=async -e MAX_VUS=20 scripts/k6/ramping.js
```

보는 곳(요약에서): `accepted`, `http_req_duration{name:POST /api/agent/requests}` 의 `p(95)`, `http_req_failed`, `iterations`.

기대(확인 전 예상): `accepted` 가 100%, 접수 응답의 p(95) 가 임계값 2초보다 한참 아래(수십~수백 ms 로 본다), 실패 0. VU 가 1초 쉬고 접수는 거의 즉시 끝나므로 VU 하나가 초당 약 1건을 보낸다. 올리기, 유지, 내리기를 합친 VU 시간이 약 1000 VU·초라서 `iterations` 는 1000건 안팎일 것으로 본다. 끝난 뒤에도 워커는 쌓인 요청을 계속 처리한다(워커 2대, 5초 기준 최대 초당 0.4건).

### ④-2 쌓인 요청 확인과 비우기 (⑤ 전에)

**목적:** ④ 가 끝난 뒤에도 Kafka 에 처리 못 한 요청이 남아 있는지 보고, ⑤ 에 앞서 비운다. 남은 요청이 있으면 ⑤ 의 새 요청이 그 뒤에 줄을 서서 완료 시간이 부풀려진다. 약 1분.

1) 남은 건수(LAG) 확인:

```bash
docker exec kafka kafka-consumer-groups --bootstrap-server kafka:29092 --group agent-workers --describe
```

보는 곳: 파티션(0, 1, 2)별 `LAG`. 기대(확인 전 예상): ④ 가 보낸 건수(약 985건)에서 워커가 처리한 만큼을 뺀 값이 남아 있다. 가짜 지연 5초 기준 워커 한 대는 최대 초당 0.2건이다. 파티션이 3개, 워커가 2대라 한 워커가 파티션 2개를 맡으므로 LAG 이 그쪽에 두 배로 쌓이고, 그쪽이 먼저 막힌다고 본다. 이 값은 기록용이다(DAY25_RESULT 3-4).

2) 기다릴지 비울지 정한다. 기다리면 파티션 2개를 맡은 워커의 `LAG × 5초` 만큼 걸린다(985건이면 약 50분으로 계산). 처리 시간 자체를 재려는 것이 아니면 비운다.

3) 비우기: **워커 2대(8000, 8001)를 모두 끈 뒤**(Ctrl+C) 실행한다. 그룹에 워커가 붙어 있으면 위치를 옮길 수 없다는 오류가 날 것으로 본다.

```bash
docker exec kafka kafka-consumer-groups --bootstrap-server kafka:29092 --group agent-workers --topic agent.requests --reset-offsets --to-latest --execute
```

기대(확인 전 예상): 파티션 0, 1, 2 별로 `NEW-OFFSET` 이 나오고, 그 값은 각 파티션의 `LOG-END-OFFSET` 과 같다. 위 명령에서 `--execute` 를 빼면 실제로 옮기지 않고 결과만 미리 보여 준다(확인용).

4) 워커 2대를 4번 준비의 명령(`FAKE_LLM_ENABLED=true`, `FAKE_LLM_DELAY_SEC=5` 포함)으로 다시 띄우고, 1) 을 다시 실행한다.

기대(확인 전 예상): 세 파티션의 `LAG` 이 모두 `0`. 비운 요청의 결과는 `PROCESSING` 으로 남았다가 600초 뒤 사라지거나 아예 없다(Day 24 의 TTL 정책). 이 요청들은 처리되지 않으므로 이후 실험에 영향이 없다.

### ⑤ ramping 시나리오: 완료 시간까지 재기 (VU 10, POLL)

**목적:** 접수는 빠른데 완료까지 얼마나 걸리는지를 같은 시나리오에서 본다. ④-2 로 ④ 의 쌓인 요청을 비워 `LAG` 이 0 인 상태에서 한다(그렇지 않으면 ④ 의 요청이 앞에 줄 서 있어 숫자가 섞인다). 약 2~3분.

```bash
k6 run -e MODE=async -e POLL=1 -e MAX_VUS=10 -e POLL_MAX_SEC=120 scripts/k6/ramping.js
```

보는 곳: `e2e_ms` 의 `avg`, `p(95)`, `results_done`, `results_poll_timeout`. `http_req_failed` 는 결과 조회가 404(아직 워커가 받지 않음)일 때도 실패로 세므로, 스크립트를 고치기 전 실행에서는 높게 나올 수 있다(DAY25_RESULT 3-5).

기대(확인 전 예상): 접수 응답은 ④ 와 비슷하게 빠르다. VU 가 많아질수록 `e2e_ms` 가 5초에서 계속 늘어난다. 이유는 워커 2대가 동시에 2건만 처리하고 파티션이 3개라 한 워커가 파티션 2개를 맡아 요청이 한쪽으로 더 몰리기 때문이다. VU 10명이 동시에 대기하면 완료까지 수십 초가 될 수 있다고 본다(대략 `VU 수 × 5초 ÷ 처리 중인 워커 수`, 정확한 값은 재야 안다). `results_poll_timeout` 이 0 이 아니면 120초 안에 끝나지 않은 요청이 있다는 뜻이다.

### ⑤-2 (선택) 대기 중인 요청을 조회하면 404 인 것 확인

**목적:** ⑤ 에서 `http_req_failed` 가 높게 나온 이유(결과 조회가 404)가 "속도가 빨라서"가 아니라 "요청이 Kafka 에서 워커를 기다리는 중이라 결과 키가 아직 없어서"임을 한 건의 조회 기록으로 본다. ④-2 로 `LAG` 이 0 인 상태에서 한다. 약 40초.

요청 6건을 연달아 보내고(워커 2대가 동시에 2건만 처리하므로 뒤의 요청은 기다린다), 마지막 요청을 1초마다 조회해 HTTP 코드와 상태를 본다.

```bash
for i in 1 2 3 4 5 6; do
  ID=$(curl -s -X POST localhost:8080/api/agent/requests -H "Content-Type: application/json" \
    -d '{"question":"환불은 며칠 안에 신청해야 하나요?","provider":"fake"}' \
    | sed -E 's/.*"requestId":"([^"]+)".*/\1/')
done
for i in $(seq 1 30); do
  R=$(curl -s -w ' HTTP%{http_code}' localhost:8000/api/v1/agent/results/$ID)
  echo "$(date +%T) ${R##* } $(echo "$R" | grep -oE '"status":"[A-Z]+"')"
  sleep 1
done
```

보는 곳: 줄마다 `HTTP404`(상태 없음) → `HTTP200 "status":"PROCESSING"` → `HTTP200 "status":"DONE"` 순서로 바뀌는지, 404 가 몇 줄 이어지는지.

기대(확인 전 예상): 처음 몇 초에서 십수 초 동안 `HTTP404`, 그다음 `PROCESSING` 이 5초 안팎, 마지막에 `DONE`. 404 가 이어지는 길이는 마지막 요청이 어느 파티션에 들어갔고 그 워커 앞에 몇 건이 있었는지에 따라 달라진다(앞에 줄 선 요청이 없으면 404 가 한두 줄이거나 없을 수도 있다). 404 구간은 서버 오류가 아니라 대기 상태이며, 이 구간이 ⑤ 의 `http_req_failed` 로 잡힌 부분이다.

### ⑥ (선택) 계획 시나리오 300 VU와 쌓인 요청 비우기

**목적:** PLAN 의 "ramping VU(0→300)"를 실제로 돌려 본다. **접수만 재는 방식으로만** 한다(POLL 없이). 총 약 70초.

```bash
k6 run -e MODE=async -e MAX_VUS=300 scripts/k6/ramping.js
```

기대(확인 전 예상): 접수가 얼마나 버티는지가 관찰 대상이다. 300 VU 면 초당 수백 건이 Spring 으로 들어가므로 접수 응답이 느려지거나 `503`(Kafka 전송 5초 초과), 연결 실패가 나올 수 있다. 어느 지점에서 무엇이 먼저 무너지는지는 이 실험 전에는 모른다. 몇 분 안에 수만 건이 쌓일 수 있다.

끝난 뒤 쌓인 요청 비우기(④-2 와 같은 방법. 워커를 모두 끈 상태에서):

```bash
docker exec kafka kafka-consumer-groups --bootstrap-server kafka:29092 --group agent-workers --topic agent.requests --reset-offsets --to-latest --execute
```

그 뒤 워커를 다시 켠다. 비운 요청의 결과는 `PROCESSING` 으로 남았다가 600초 뒤 사라지거나 아예 없다(Day 24 의 TTL 정책).


## 6. 확인하지 않은 것

| 항목                          | 내용                                                                                                                                                            |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 실제 환경 실행                | ①~⑥ 은 아직 하지 않았다                                                                                                                                         |
| 같은 컴퓨터에서 부하를 거는 것 | k6, Spring, 워커 2대, Kafka, Redis 가 한 컴퓨터를 나눠 쓴다. VU 가 많아지면 서버가 아니라 컴퓨터 자원이 먼저 한계일 수 있어, 한계 지점을 서버 구조의 한계로만 읽을 수 없다 |
| 지연 값                       | 5초는 설계값이다. 실제 에이전트의 건당 시간은 7~29초로 흔들렸다(Day 16, 17)                                                                                      |
| 도구, 검색                    | 가짜 모델은 도구를 부르지 않는다. 임베딩 API 호출과 Qdrant 검색 부하는 이 시나리오에 없다                                                                           |
| 한 번씩만                     | 같은 조건을 여러 번 돌려 평균을 내지 않는다. 숫자는 한 번의 측정이다                                                                                              |


## 7. 알려진 한계

| 항목                          | 내용                                                                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| closed 모델                   | VU 는 응답을 받아야 다음 요청을 보낸다. 서버가 느려지면 보내는 요청 수가 저절로 줄어든다. "초당 N건을 무조건 보내는" 방식(arrival rate)은 쓰지 않았다. 필요하면 Day 28 에서 본다 |
| 임시 임계값                   | 접수 p(95) 2초, 접수 성공률 99% 는 오늘 정한 임시 기준이다. 요약의 ✓/✗ 표시를 위한 값이다                                                |
| 결과 조회 방식                | `POLL=1` 은 1초마다 조회한다. 조회 요청 자체가 워커 8000 에 부하를 더한다                                                              |
| 워커 병렬성                   | 워커 한 대가 한 건씩 처리하는 구조는 이번에 바꾸지 않았다. 처리량을 올리는 방법(워커 수, 파티션 수)은 Day 34.1 에서 다룬다                   |
