# Day 10 가이드 — 에이전트 도구를 실제 Qdrant 검색으로 교체 + RAG 비교 API

> 상태: 코드 작성 완료. `/rag/ask`, `/rag/compare` 실행 확인(2026-10-09). 에이전트·강제실패 확인은 체크리스트 참고.

## 1. 오늘 목표

1. 에이전트의 `search_vector_db` 도구를 **mock 에서 실제 Qdrant 검색**으로 교체한다.
2. Qdrant 를 쓴 경우와 안 쓴 경우의 차이를 눈으로 볼 수 있는 **별도 API** 를 만든다.

## 2. 처음 API 를 만들 때와 지금의 차이

API 의 겉모습(`POST /api/v1/agent/run`, 요청 `{query, provider}`, 응답 `{answer, provider}`)은 Day 2 때 그대로다. 안에서 일어나는 일이 달라졌다.

| 시기         | 내부 동작                                                                                     | 호출 결과에서 보이는 차이                                                   |
| ------------ | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Day 2 (처음) | 직접 짠 순서: 모델 호출 → 도구 실행 → 모델 다시 호출 (`agent_core.py`). 도구는 mock 검색 하나 | 코드가 정한 순서대로만 동작                                                 |
| Day 3~4      | LangGraph 로 같은 흐름을 State / Node / 분기 조건으로 재구성                                  | 결과는 같음. 흐름이 명시적이라 확장하기 쉬워짐                              |
| Day 5        | 도구가 `get_current_time` 까지 2개. 모델이 질문에 맞는 도구를 고름                            | "지금 몇 시야?" 는 시간 도구, 인사는 도구 없이 답변                         |
| Day 6        | 도구 실패 시 그래프가 같은 호출을 최대 2번 강제 재시도, 한도를 넘으면 give_up                 | 실패해도 에러 대신 "2번 시도했지만 처리하지 못했습니다" 가 정상(200)으로 옴 |
| Day 10       | 검색 도구가 mock 대신 실제 Qdrant 검색                                                        | 답변이 저장된 문서 내용에 근거함                                            |

### 호출할 때 체감 차이

- **내용**: 전에는 어떤 질문에도 같은 가짜 문구를 읽고 답했다. 지금은 질문마다 다른 문서를 찾아 읽고 답한다. 문서에 없는 내용은 근거도 없다.
- **호출 횟수**: 검색이 필요한 질문은 임베딩 1번 + Qdrant 검색 1번 + 채팅 모델 2번(도구 판단, 최종 답변). 응답이 느려질 수 있고 무료 한도(429)에도 더 쉽게 걸린다. 얼마나 느려졌는지는 아직 측정 전이며 k6 에서 잴 대상.
- **실패**: Qdrant 가 꺼지거나 임베딩이 429 를 내도 재시도 후 give_up 응답으로 끝난다.
- **그대로인 것**: 요청마다 새 대화(이전 질문을 기억 못 함), 응답이 끝날 때까지 기다리는 동기 방식. 세션 기억은 4주차 Redis, 비동기는 Kafka 에서 바뀌며 지금의 동기 방식이 k6 비교 기준(sync)이 된다.

## 3. 변경 1 — 에이전트 도구 교체 (`app/services/agent_graph.py`)

바뀐 함수는 `search_vector_db` 하나뿐이다. 기존 mock 은 `[OLD]` 주석으로 남기고 `[NEW]` 를 추가했다.

|                      | 이전 (Day 6~9)                 | 지금 (Day 10)                                                       |
| -------------------- | ------------------------------ | ------------------------------------------------------------------- |
| 데이터 출처          | 코드에 박힌 고정 문구          | Qdrant `documents-12` 의 문서 24건 중 가까운 3건                    |
| 질문에 따른 결과     | 어떤 질문이든 같은 문구        | 질문마다 다른 문서 ("비번" 이면 비밀번호 문서)                      |
| 외부 호출            | 없음                           | 임베딩 API 1번 + Qdrant 검색                                        |
| 도구 설명(docstring) | "사내 문서/상품 리뷰 등에서 …" | "환불, 배송, 교환, 결제, 회원, 후기 문서에서 …"                     |
| 실패 가능성          | "강제실패" 테스트로만          | 위 테스트 + 실제 장애(Qdrant 꺼짐, 임베딩 429)도 실패로 잡혀 재시도 |
| 유지된 것            | -                              | "강제실패" 분기, 재시도(MAX_RETRIES=2)와 give_up                    |

설계 이유

- **docstring 을 구체화**: docstring 은 모델이 "이 도구를 언제 쓸지" 판단하는 설명서다. 어떤 문서가 들어 있는지 알려 줘야 관련 질문에서만 호출하고 "안녕!", "지금 몇 시야?" 에는 호출하지 않는다.
- **예외를 잡지 않고 던짐**: 실제 장애가 tool_node 에서 실패로 기록되어 Day 6 재시도가 동작한다. 재시도가 가짜 실패가 아니라 실제 일시적 장애에 대한 것이 된다.

## 4. 변경 2 — Qdrant 사용 여부 비교 API

에이전트(`/agent/run`)는 모델이 검색할지 스스로 판단해서, 같은 질문에도 검색을 할 때도 안 할 때도 있다. "검색 있음/없음" 을 정확히 비교하려면 두 경로를 코드로 고정해야 해서 에이전트와 별도로 만들었다. 기존 `/agent/run` 은 바꾸지 않았다.

| API                          | 하는 일                                          | 호출                                 |
| ---------------------------- | ------------------------------------------------ | ------------------------------------ |
| `POST /api/v1/rag/ask`       | Qdrant 에서 가까운 문서를 찾아 근거로 답변 (RAG) | 임베딩 1 + Qdrant 검색 + 채팅 모델 1 |
| `POST /api/v1/rag/ask-plain` | 검색 없이 채팅 모델 혼자 답변                    | 채팅 모델 1                          |
| `POST /api/v1/rag/compare`   | 위 둘을 차례로 실행해 결과를 나란히 반환         | 위 둘의 합                           |

요청 (셋 다 같은 형태): `{"query": "...", "provider": "gemini", "limit": 3}` — `limit` 은 RAG 쪽에서만 사용(1~10).

응답 필드: `answer`, `elapsed_ms`, `llm_calls`. RAG 는 추가로 `retrieval_ms`(임베딩 + 검색 시간), `sources`(근거 문서와 유사도 점수).

### `/ask` 와 `/ask-plain` 의 차이 (= Qdrant 사용 여부)

|                  | `/ask` (Qdrant 사용)                                                       | `/ask-plain` (순수 AI)                |
| ---------------- | -------------------------------------------------------------------------- | ------------------------------------- |
| 흐름             | 질문 → Qdrant 에서 가까운 문서 3건 검색 → 문서와 질문을 모델에 전달 → 답변 | 질문 → 모델에 바로 전달 → 답변        |
| 모델이 아는 것   | 학습 데이터 + 방금 찾은 이 쇼핑몰의 문서                                   | 학습 데이터뿐 (이 쇼핑몰 규정은 모름) |
| 문서에 없는 질문 | "문서에 해당 내용이 없습니다" 라고 답하게 해 둠                            | 모르는데도 그럴듯하게 지어낼 수 있음  |
| 비용             | 임베딩 호출 + Qdrant 검색이 더 듦 (응답이 느림)                            | 채팅 모델 1번뿐이라 빠름              |

같은 것: 채팅 모델(`gemini-3.1-flash-lite`), 상담원 역할 설정, 채팅 모델 호출 횟수(1번). 다른 것은 Qdrant 검색 단계와 "참고 문서에 있는 내용만 근거로 답하라" 는 규칙뿐이다.

"순수 AI" 는 문서 없이 AI 의 일반 지식으로만 답한다는 뜻이다. 일반 상식 질문("환불이란 뭐야?")은 두 방식 차이가 거의 없고, **이 쇼핑몰만의 정보**를 물을 때 차이가 크게 난다.

### 설계 이유

- **고정 경로**: 두 방식 모두 채팅 모델 호출이 1번이라 호출 횟수·시간을 그대로 비교할 수 있고 무료 한도(429)에도 덜 걸린다.
- **공정한 비교**: 같은 모델, 같은 역할 설정. RAG 쪽에만 "참고 문서" 와 "문서에 근거해서만 답하라" 규칙을 더했다.
- **`def` (not `async def`)**: 함수 안에서 모델/Qdrant 호출이 끝날 때까지 기다리는(blocking) 코드를 실행한다. `async def` 안에서 blocking 호출을 하면 그동안 서버 전체가 멈춘다. `def` 는 FastAPI 가 별도 스레드에서 실행한다. (기존 `agent/run` 은 `async def` 라서 k6 동기/비동기 비교 때 짚어 볼 부분)
- **실패 처리**: `/compare` 는 한쪽이 실패해도 다른 쪽을 보여주려고 결과 안에 `error` 를 담아 200 으로 반환한다. 단독 API(`/ask`, `/ask-plain`)는 호출한 쪽이 상태 코드로 성공/실패를 구분하도록 **502** 로 응답한다.

## 6. 테스트 방법

터미널 두 개를 쓴다.

```bash
# 터미널 1: Qdrant 확인 + 서버 실행
docker ps | grep qdrant                 # 없으면 프로젝트 루트에서 docker compose up -d
cd d2-ai-python
source venv/bin/activate
./run.sh                                # --reload 라서 코드가 바뀌면 자동 재시작
```

```bash
# 터미널 2: 같은 질문을 방식별로 호출
curl -s -X POST http://localhost:8000/api/v1/rag/ask -H "Content-Type: application/json" \
  -d '{"query": "제주도 배송비는 얼마예요?"}'
curl -s -X POST http://localhost:8000/api/v1/rag/ask-plain -H "Content-Type: application/json" \
  -d '{"query": "제주도 배송비는 얼마예요?"}'
curl -s -X POST http://localhost:8000/api/v1/rag/compare -H "Content-Type: application/json" \
  -d '{"query": "제주도 배송비는 얼마예요?"}'
```

Swagger: `http://localhost:8000/docs` 의 `rag` 항목.

### 해석

| 관찰 | 해석 |
| --- | --- |
| RAG 의 추가 시간은 `retrieval_ms` 약 0.5초뿐 | 대부분 임베딩 API 왕복. Qdrant 검색 자체는 몇 ms |

| 두 방식 모두 3,000원 | 이 질문은 일반 상식과 정책이 우연히 겹침. plain 은 추측이라 "기본 배송비에 합산" 같은 정책에 없는 말이 섞임 |

### 개념 정리

| 질문 | 정리 |
| --- | --- |
| RAG 의 목적은 속도인가 | 아니다. 모델이 모르는 내 데이터를 근거로 답하게 해 정확도와 근거 확인을 높이는 것. 모델만 호출하는 것보다 항상 검색 시간만큼 더 걸림 |
| RAG 가 빠른 경우 | 문서 전체를 프롬프트에 넣는 방식과 비교할 때. 관련 문서 3개만 넣어 토큰과 시간이 줄어듦 |
| 사전에 학습이 필요한가 | 모델 학습은 필요 없다. 문서를 임베딩해 Qdrant 에 넣는 적재(ingest)만 필요. 문서가 바뀌면 upsert 로 반영 |
| 구성 역할 | Qdrant = 검색기(수학, AI 아님), 임베딩 모델 = 문장을 벡터로 번역, 채팅 모델 = 문서를 읽고 답변 작성 |

### 속도 개선 방안 (2초 이상이면 느리게 느껴짐)

RAG 한 번의 시간은 대부분 채팅 모델 호출이다. 검색은 0.5초.

| 방법 | 설명 | 기대 효과 |
| --- | --- | --- |
| 답변 캐시 (Redis) | 같은 질문의 답을 저장해 모델 호출 생략 | 수 ms |
| 시맨틱 캐시 | 비슷한 질문도 임베딩 유사도로 캐시 적중 | 검색 시간만 |
| 스트리밍 응답 | 생성되는 대로 흘려보냄 | 체감 첫 글자 0.5초대 |
| 더 빠른 모델 | Flash-Lite, Groq 등 | 모델 시간 단축 |
| 답변 길이 제한 | `max_output_tokens`, 짧게 답하라는 프롬프트 | 생성 시간은 토큰 수에 비례 |
| 비동기 처리 (Kafka) | 202 로 바로 받고 결과는 조회 | 대기 자체를 없앰 (k6 sync vs async 실험 주제) |
| 질문 임베딩 캐시, 클라이언트 재사용 | 검색 0.5초 중 임베딩 API 왕복을 줄임 | 소폭 |

프로젝트 연결: Redis 캐시(3~4주 차)와 Kafka 비동기(k6 비교)가 위 표의 핵심이다. 무료 Gemini 의 지연은 k6 전에 fake-LLM 지연 모드 또는 Gemini Tier 1 로 대응해야 한다(10/19 전 결정).
